One turn, end to end

A dump comes in two ways, from the composer or as an email forwarded to offload, and both become the same job. It forks once, after a cheap classifier. Everything the model does after that goes through the same two doors: a write goes to the Core API, a lookup stays inside the worker. Nothing reaches a person except through the messages table.

  • Other job kinds share the worker and are not drawn: thread.nightly (032, one model call per thread and member, booked only when something of theirs changed since their last pass, {{NIGHTLY_MODEL}}: it keeps their notes true, adds what their dumps showed, and on the default thread suggests threads), voice.forget (deletes a transcript at the provider) and the embed.* jobs (Voyage). Only dump.answer talks to a person.
  • A row typed into a section is not a turn (032). The + on a To do or Timeline heading writes the row as typed, with the section's type, and no job is enqueued: no model reads it and its title never changes after enter.
  • An email forwarded to offload is a dump that arrives by mail (026). Resend receives it and calls POST /v1/mail/resend, which checks the sender is an account's own address, keeps the text and the pictures worth keeping, and writes a message with source mail and the same dump.answer job. The worker first asks {{SORT_MODEL}} which pictures are worth reading (look.py, "Looking at the pictures"), never classifies it, and files it: an email is filed, not answered. Everything the turn writes is marked untrusted, nothing it reads can suggest a thread, and its Undo sits on the email's Activity row for a day, since nobody is at a toast.
  • Not in a thread (028). What has no home is filed in the account's default thread, which the model reads as not in a thread and a person never sees named. Filing there may carry suggest_thread_id, a thread the model had in mind and was not sure of, which the person sees as a suggestion on the row. A turn that filed only there shows Done with no pill: filed on the done event is what draws it.
  • The step before the classifier is the one thing written before any model runs. Everything else the person sees is produced by, or after, a model call.
  • A voice note is written down before anything reads the message (021). The audio is a POST /v1/blobs/audio ahead of the dump, encrypted like a photo. At the top of the job, before the classifier and under a shield the cancel waits for, the worker fetches the original, uploads it to AssemblyAI's European endpoint and nowhere else, records the provider's reference so a retry polls rather than re-sends, and posts the words to /internal/v1/messages/:id/transcript. From that write on every reader of the person's words, the classifier included, reads said(text, transcript), so a spoken order, question or answer to an open question takes the same path a typed one does. The model never receives audio. Nothing to hear settles with "Heard nothing in that one." and no model call; the transcript's delete at the provider is its own job.
  • A photo is uploaded before the dump and read once, on this turn (020). Each one is a POST /v1/blobs that encrypts and stores the original in R2 before the dump names it by id. Between the claim and the classifier the worker fetches each original over /internal/v1/blobs/:id/original, makes a 400px thumbnail and a 2048px large copy with Pillow, posts them back with the file's own date, place and device, and hands the large copy to the planner as an image block. A message with a photo never takes the answering path, whatever its words. A photo the model does not file is filed by turn-result as "A photo" before any question runs, so nothing dumped is lost to a model that did not mention it.
  • Stop is a separate route: the client marks the turn cancelled at once, the API cancels the job, the worker's cancel listener abandons the loop, and no result is posted. A stopped turn is not retried.
  • Finish it is a fresh job against the same message, with what already landed handed to the model as a block, so the resume adds to the turn rather than replaying it.

The loop every call runs in

One function, _run, serves the filing path and the answering path. What differs between them is passed in: the system prompt, the user blocks, the tool list. What is the same is where a tool result becomes the next model turn, and that is the only place it happens.

  • What "finished" means is decided after the loop, not by the model: a reply, something that landed, or something changed (a move, a tick, a share put to them). A turn that did none of those is failed. A bound refusal on look_up counts as the tool working, and so does a tool that was not offered on the turn; a tool the API refused, or one that could not be reached, makes the turn partial and the screen offers Finish it.
  • A partial turn's sentence is built from what landed, never from the model's account of itself: "Saved to Lisbon trip." naming only real threads, "Saved." when everything landed not in a thread (028), "That did not finish." when something changed and nothing was filed, "Nothing saved." otherwise.
  • The model never sees an account id, a job id or a URL it did not receive from the dump. The tool caller closes over the job id, the API derives the account from it, and the bound checks every query against the dump's own words.
  • No thinking requested, no streaming, {{MAX_TOKENS}} output tokens. The model can still think before it answers and that counts against the budget, so a call that runs out of room is asked again once at {{MAX_TOKENS_RETRY}}: at 2,048 a turn spent everything weighing where a booking went and filed nothing. A model call is one request and one response; the step line exists because the first response on the answering path takes ten to thirty seconds.

The prompt, as sent

Two system prompts, one per path, each sent as a single cached text block and each assembled once at import: what offload is and the policy both paths hold are written once in prompts/shared/ and joined into both. The person's material never goes in the system prompt: it arrives as a user turn made of separate labelled blocks, each saying where it came from and whether it may be obeyed.

answer.md, in six movements {{ANSWER_WORDS}} words · {{ANSWER_MODEL}}

  • Whose question it is. Their life, not the world: "when do the clocks go forward" is theirs, "how do you make leek soup" is not, and the whole reply to the second is Not sure. A handful of subjects get Can't search that. instead, a different sentence on purpose.
  • Answering is reading. The exact read before the fuzzy one; one question can be two reads; three reads at most.
  • The answer is the reply. Nothing wrapped around it: the list is the reply, yes is yes, the rows drawn beside it are not typed out again.
  • Markup, and when it earns its place. Bold on the word the sentence turns on, a list from two items, links only to paths inside offload.
  • No, and don't know, are different sentences. No when everything was read; could not find when a read was cut short; don't know when nothing readable holds it.
  • The web, last. The same bound as filing: their words plus their country, no composed sentence, and a refused query is a question that cannot be answered. When the thread they asked from puts them somewhere else, it asks which country.

What the answering turn is shown up to six blocks

Country, today, the thread list, the thread they asked from with its notes when there is one, the earlier turns, and the question. Everything else it wants it goes and reads, with tools that read and nothing that writes.

"A dump's context carries what already landed and the conversation so far; a question carries the question and the threads it might name, and everything else it wants it goes and reads."

Since 018 the answering turn sees the conversation's tail too, under the same ceiling, so a follow-up question can lean on the answer before it. The thread list reads the default thread as "not in a thread", as filing does.

Where a person can already be asked

Since 018 the model can ask back, with ask: one field the row it just filed needs, or which country an answer is for. It is built on the shape below, the write that waits: a control inside the reply, a row that outlives the turn, and an answer route with no model in it. What differs is that the model chose to ask, and that the options are values the server already holds. The server asks two questions of its own, and since 028 a choice can also sit on a row rather than in the conversation.

ask values, not words

Handled in the loop like say: nothing crosses to the API until the turn settles. Five fields the model may ask, date, span, time, country, and since 020 thread, which the server allows only for a photo sent with no words from outside any thread that landed by itself in the default thread (025 retired tag with tags); the sentence is a server template with the row's title in it; up to four values plus "Not that", which the server appends. Two per turn in code, the third refused. One open per conversation, closed by the next turn whatever it says. A tap is applied with no model; a typed reply is judged by a forced-tool haiku call before the classifier, and if it answers, the planner is told so in a block and files the rest. Country is the one field an answering turn may ask, when the thread it was asked from puts the person somewhere the account does not, and the pick re-runs the answer read-only with the country as an override into the same bound.

Which calendar server asks

The seventh field, calendar, since 019, and the one the model never asks: the server raises it from inside create_event when the row's thread has several writable calendars picked, or none yet while the account has approved some. The values are the calendars, the chips their names, and the model is told asked and says nothing. A tap writes the event through the same confirm-or-do path as any write, outside any transaction, picks the calendar for the thread when the thread had none, and can still turn into the write that waits. Undo of the tap is the calendar's Google-first Undo, not a field put back.

Which person server asks

022's field, person, raised by the server from inside share_thread when the name matches two of their connections. The values are those connections, worded from the database; no list of connections ever reaches the prompt. A tap puts the share to them as any share is.

Needs you, on Today 027

An open date, span, time or thread question is also a card on Today, answered with the conversation's own chips and route, for the question asked at a moment nobody had the conversation open: a forwarded email's, marked About an email. The others stay in the conversation that asked.

A suggestion on the row 028

Not in the conversation at all. Something filed not in a thread can carry one suggestion: Move to a thread, from suggest_thread_id at filing time, or Create a new one for two to ten things, from the nightly pass on the default thread ({{NIGHTLY_MODEL}}, at most {{LOOSE_CANDIDATES}} things, its ids held to what it was sent). A tap moves or opens a sheet, with Undo; the cross dismisses for good. No model runs on the tap.

say one way

A filing turn's only voice, and it ends the sentence. Nothing marks a say as expecting an answer, the turn settles as answered the moment it lands, and the next dump is a new turn that sees the sentence only as a line in "earlier in this conversation".

The write that waits server decides

Drawn above. Its shape is the closest thing to a follow-up: a reply that carries its own control, a pending row that outlives the turn, an answer route with no model in it. Calendar only, and only for consent, never for a choice.

Finish it resume

A partial turn can be picked up: same message, fresh job, and the model is handed what already landed as a block. It is the one path where a second model turn continues a first one rather than starting over, and it exists for failure, not for dialogue.

Earlier turns both paths

Both paths see up to twenty prior turns as plain "role: text" lines, under the same ceiling, since 018; the answering path saw none before it. A question and its answer are ordinary turns in that tail. A typed reply to an open question is still classified from its text, but the judge has already read it against the question first, so "14th to 17th" lands on the row before the planner sees the message.

  • What the model never sees: which option was tapped. The server applies the value and writes the label as the person's turn; the model meets it, if at all, as a line in the tail or as the "they answered your question" block on a typed reply.
  • What the server refuses whatever the prompt says: a question about a row this turn did not file, a field a thread note forbids, a sentence over 80 characters or a label over 24, a thread question outside its one condition, country from anything but a question job, calendar or person from the model at all, and any question at all on a partial turn or a stopped one.
  • What the design system commits to, kept: ask only what Undo cannot cover, never a dialog, options as words somebody would say, a choice among equals has no primary, and the way out is drawn plain.
