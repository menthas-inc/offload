1

One turn, end to end

There is one entry point for a dump and it forks once, after a cheap classifier. Everything the model does after that goes through the same two doors: a write goes to the Core API, a lookup stays inside the worker. Nothing reaches a person except through the messages table.

  • Three other job kinds share the worker and are not drawn: thread.quick_add (a row typed straight into a thread, sonnet, two tools), notes.compact (haiku) and the embed.* jobs (Voyage). Only dump.answer talks to a person.
  • The step before the classifier is the one thing written before any model runs. Everything else the person sees is produced by, or after, a model call.
  • Stop is a separate route: the client marks the turn cancelled at once, the API cancels the job, the worker's cancel listener abandons the loop, and no result is posted. A stopped turn is not retried.
  • Finish it is a fresh job against the same message, with what already landed handed to the model as a block, so the resume adds to the turn rather than replaying it.
2

The loop every call runs in

One function, _run, serves the filing path, the answering path and quick add. What differs between them is passed in: the system prompt, the user blocks, the tool list. What is the same is where a tool result becomes the next model turn, and that is the only place it happens.

  • What "finished" means is decided after the loop, not by the model: a reply, or something that landed. A turn that filed nothing and said nothing is failed. A bound refusal on look_up counts as the tool working, since this morning; a tool the API refused, or one that could not be reached, makes the turn partial and the screen offers Finish it.
  • The model never sees an account id, a job id or a URL it did not receive from the dump. The tool caller closes over the job id, the API derives the account from it, and the bound checks every query against the dump's own words.
  • No extended thinking, no streaming, {{MAX_TOKENS}} output tokens. A model call is one request and one response; the step line exists because the first response on the answering path takes ten to thirty seconds.

The prompt, as sent

Two system prompts, one per path, each sent as a single cached text block. The person's material never goes in the system prompt: it arrives as a user turn made of separate labelled blocks, each saying where it came from and whether it may be obeyed.

answer.md, in six movements {{ANSWER_WORDS}} words · {{ANSWER_MODEL}}

  • Whose question it is. Their life, not the world: "when do the clocks go forward" is theirs, "how do you make leek soup" is not, and the whole reply to the second is Not sure.
  • Answering is reading. The exact read before the fuzzy one; one question can be two reads; three reads at most.
  • The answer is the reply. Nothing wrapped around it: the list is the reply, yes is yes, the rows drawn beside it are not typed out again.
  • Markup, and when it earns its place. Bold on the word the sentence turns on, a list from two items, links only to paths inside offload.
  • No, and don't know, are different sentences. No when everything was read; could not find when a read was cut short; don't know when nothing readable holds it.
  • The web, last. The same bound as filing: their words plus their country, no composed sentence, and a refused query is a question that cannot be answered.

What the answering turn is shown three blocks

Country, the thread list, the question. That is the whole user turn. No earlier turns: the design note says the reads are the memory, which keeps the prompt a constant rather than a function of account age.

"A dump's context carries what already landed and the conversation so far; a question carries the question and the threads it might name, and everything else it wants it goes and reads."

This is the first thing a follow-up question will run into. On the filing path the model can see what was said before. On the answering path it cannot, and the reply it just gave is not in front of it either.

Where a person can already be asked

Since 018 the model can ask back, with ask: one field the row it just filed needs, or which country an answer is for. It is built on the shape below, the calendar write that waits: a control inside the reply, a row that outlives the turn, and an answer route with no model in it. What differs is that the model chose to ask, and that the options are values the server already holds.

ask values, not words

Handled in the loop like say: nothing crosses to the API until the turn settles. Five fields the model may ask, date, span, time, tag, country; the sentence is a server template with the row's title in it; up to four values plus "Not that", which the server appends. Two per turn in code, the third refused. One open per conversation, closed by the next turn whatever it says. A tap is applied with no model; a typed reply is judged by a forced-tool haiku call before the classifier, and if it answers, the planner is told so in a block and files the rest. Country is the one field an answering turn may ask, when the thread it was asked from puts the person somewhere the account does not, and the pick re-runs the answer read-only with the country as an override into the same bound.

Which calendar server asks

The sixth field, calendar, since 019, and the one the model never asks: the server raises it from inside create_event when the row's thread has several writable calendars picked, or none yet while the account has approved some. The values are the calendars, the chips their names, and the model is told asked and says nothing. A tap writes the event through the same confirm-or-do path as any write, outside any transaction, picks the calendar for the thread when the thread had none, and can still turn into the write that waits. Undo of the tap is the calendar's Google-first Undo, not a field put back.

say one way

A filing turn's only voice, and it ends the sentence. Nothing marks a say as expecting an answer, the turn settles as answered the moment it lands, and the next dump is a new turn that sees the sentence only as a line in "earlier in this conversation".

The write that waits server decides

Drawn above. Its shape is the closest thing to a follow-up: a reply that carries its own control, a pending row that outlives the turn, an answer route with no model in it. Calendar only, and only for consent, never for a choice.

Finish it resume

A partial turn can be picked up: same message, fresh job, and the model is handed what already landed as a block. It is the one path where a second model turn continues a first one rather than starting over, and it exists for failure, not for dialogue.

Earlier turns both paths

Both paths see up to twenty prior turns as plain "role: text" lines, under the same ceiling, since 018; the answering path saw none before it. A question and its answer are ordinary turns in that tail. A typed reply to an open question is still classified from its text, but the judge has already read it against the question first, so "14th to 17th" lands on the row before the planner sees the message.

  • What the model never sees: which option was tapped. The server applies the value and writes the label as the person's turn; the model meets it, if at all, as a line in the tail or as the "they answered your question" block on a typed reply.
  • What the server refuses whatever the prompt says: a question about a row this turn did not file, a field a thread note forbids, a sentence over 80 characters or a label over 24, a tag with fewer than two values, country from anything but a question job, and any question at all on a quick add, a partial turn or a stopped one.
  • What the design system commits to, kept: ask only what Undo cannot cover, never a dialog, options as words somebody would say, a choice among equals has no primary, and the way out is drawn plain.
