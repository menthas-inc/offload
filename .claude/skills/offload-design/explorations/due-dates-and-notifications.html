Due dates, and the notifications that read them

Read off main at b494d0e, after 021 and the sharing work. Three questions in order: what carries a date today and who writes it, how a person sets one, and what offload says when the day comes. Third pass. Every question this page raised has been answered and the answers are folded in and marked settled. What is left is a handoff, not a decision.

The finding that shapes the rest: the schema has carried dates since 001 and no person has ever been able to write one. Every date in the product was inferred by a model from something somebody dumped. There is no field, no picker, no gesture and no way to clear one on any of the three surfaces. Notifications are the forcing function, because a notification fires off a date, and a date nobody can correct is a notification nobody can stop.

2. One field, called When

and the row's type decides what it writes

A person does not hold three date columns in their head. They hold one question, when, and sometimes a second, for how long. The row already knows which column that means.

  • Duration already exists and needs no column. occurs_end_at is the pair's other half and create_event already falls back to one hour when it is missing. The field offers Ends at, not a length, so the value written is the value stored.
  • A date with no hour stays all-day, which is attrs.all_day and the existing isBareDate path. Adding an hour clears it. This is the one part of the model a client can get wrong in a way nobody notices for months.
  • settled A due date may carry an hour, and dates.ts's comment is now wrong. That comment says a due date has no time anybody expects to see. "Call the clinic at 9" and "rent by Friday" are both tasks, and the first one has an hour that matters, so the hour is optional on every type. Code owes an amendment to that comment, not a new column: the value already fits.
  • The hour is what makes a row sub-day, and nothing else changes. An hour clears attrs.all_day; removing it sets it again. A task with an hour still sorts and reads as a task, and the digest still announces it in the morning rather than at the hour, which is section 7's rule.
  • Repeats is set in the same sheet and is the one recurrence control there is. It follows Google Calendar's preset list and Custom dialog, which the current repeats column cannot hold, so it becomes an RRULE: see the last cell of section 5.
  • No new glyphs. Everything here uses calendar, clock, bell, compass, check, chevron-down, chevron-right, x, sunrise and moon, all of them already vendored. The set stays at 84.

The costdecided: it becomes a rule
Settled: recurrence becomes an RRULE. This list does not fit the column and the gap is not small. repeats is an enum of day, weekday, week, two_weeks, month and year, with repeats_until beside it. That holds four of the seven presets and none of Custom.

What has nowhere to go today: an interval (every 2 weeks exists as a value, every 3 does not), a set of weekdays (Monday and Thursday is unsayable), a monthly anchor (the 25th versus the fourth Friday, which is the difference between two real rules), and an occurrence count.

One column holding an RRULE, RFC 5545, rather than four new columns. Three reasons: it is exactly the expressiveness this dialog needs and no more; it is what Google speaks, so 019's connector stops translating and starts passing through; and the six current enum values map into it losslessly, so the migration is a mechanical one-way rewrite with no data to reconcile.

The existing values, for the migration: day is FREQ=DAILY, weekday is FREQ=WEEKLY;BYDAY=MO,TU,WE,TH,FR, week is FREQ=WEEKLY, two_weeks is FREQ=WEEKLY;INTERVAL=2, month is FREQ=MONTHLY and year is FREQ=YEARLY. repeats_until becomes UNTIL.

What stays true either way: a repeating row is still one row, the calendar still draws it on every matching day, and this sheet still cannot edit a single occurrence.
  • This is the largest thing on the page and it came from a preset list. Worth saying plainly: adopting Google's recurrence vocabulary was a schema decision wearing the clothes of a menu, and it has been taken.
  • The model's tools inherit it too. add_content and add_note take repeats as the enum; they would take a rule string instead, which is a better fit for what a model reads out of "every other Tuesday" and currently has to round to something wrong.

7. The two digests

no per-item pushes

One send in the morning for today, one in the evening for tomorrow. A due date is not an alarm; it is something to plan around, and something that pushes the moment it becomes true teaches people to swipe it away.

A date does not get announced. A reminder does. is_reminder gates both sends, so a row is in a digest only where the model read the dump as asking to be told, and most dated rows are silent. "Rent is due Friday" is a fact about rent; "remind me to pay the rent Friday" is a request. The flag is the difference and it has been sitting in the schema unread since 001.

Two consequences, and the second is a risk worth naming. Most mornings send nothing at all, which makes an empty digest the normal state rather than an edge case. And a person can set a date but cannot ask to be reminded of it: the flag has no person-facing writer, so the only way to be told about something is to have phrased the original dump as a request. That is a coherent position, and it is also the first thing somebody will write in about.

System settingsSounds, the lock screen, and turning offload off entirely.
  • The hour rows sit under the switch they belong to and grey out with it, rather than living in a third group about time.
  • Labels match the notification titles word for word, so the switch that stops Due today is called Due today.
  • The hour is in the account's zone, which is the section 3 default, not the device's. A digest that moves when you fly is a digest that arrives at 3am.
Androidthe same five, as channels
Each switch above is a NotificationChannel, so Android's own app settings shows the same four and can turn each off outside the app.

due_today · Due today
coming_tomorrow · Coming tomorrow
people_requests · Connection requests
shared_activity · Added to a shared thread

A channel cannot be renamed or re-enabled by the app once it exists. The ids above are permanent from first install, and a channel the person switched off stays off however the app is updated. Worth getting the names right once.
  • The in-app switch and the channel have to agree in both directions, so the page reads the channel state on open rather than trusting a stored preference.
iOSan asymmetry worth stating
iOS has no per-category switches in Settings. The system offers allow or do not allow, plus delivery style and scheduled summary. There is no Android-style list.

So on iOS the in-app page is the only place a person can refuse one kind and keep another, which makes it load-bearing rather than a convenience.

The existing rule holds underneath: a denied system permission gets nothing, no second ask, and Settings gains one line saying what is off and how to turn it back on.
  • Categories are still registered on iOS, but for actions rather than for switches: the one-item digest and the share request are the two that carry any.

9. The bell

a record of what was sent, and of what was not

Both Today screens carry a bell with a comment saying it is there for the day notifications land. It opens Activity: everything offload has told you, in order, plus the things it decided quietly and never told you about. That second half is what makes it worth building, because a product whose rule is "a decline looks like silence" accumulates a lot of silence, and none of it is currently recoverable.

This is a reversal of a decision from 022 and worth saying so plainly. That work refused a notifications page on the grounds that it would be "a page that exists to hold a dot", and it was right: a request answered on its own card leaves nothing for a list to show. What changes is that there is now a record with content in it, some of which exists nowhere else in the product, and which is the only way to read your notifications when notifications are off.

recommended
  • A sent row and an unsent row are the same row with a different lead. Filled circle for something that reached the phone, hollow for something that did not, plus the mark. One shape, so the list reads as one record rather than two lists stapled together.
  • NOT SENT is a fact, not an apology. Amber where a setting caused it, plain grey where the product chose silence by design. The amber one is the only row that is arguably actionable, and tapping it opens the setting that suppressed it.
  • The digest row holds what was said, not what is true now. The wording is stored verbatim, so a digest that named five things still reads that way after three are ticked. The notification itself opens Today; this row is the record of it, and the two are different taps on purpose.
  • No Due sheet. A forward-looking "what is due" view is the Timeline's job and building a second one was the weaker half of the earlier draft.
  • A dot, never a count. Something new since you last opened it. A number here would make this an inbox to clear, and nothing in it is a task.
  • Thirty days, then it purges. The same figure as the invite expiry, which keeps one retention number in the product rather than two. So this is a recent record, not an archive, and the empty state has to be true of an account that has simply been quiet for a month as well as one that is new.
What goes in itfour kinds, and one of them is new
Sent, and about datesThe morning and evening digests, exactly as they were worded.
Sent, and about peopleA connection request, and somebody adding to a thread you share.
Silent by designAn invite that expired. A calendar write still waiting on them. A question that went unanswered and closed.
Silent by settingA digest a switch suppressed, or one the system permission refused.
  • The third kind is the one that does not exist anywhere today. An expired invite, a calendar write nobody approved, a question that timed out: each was a deliberate silence, and each is currently unrecoverable by the person it concerned.
  • The fourth kind is why this survives a person turning notifications off. That was the request, and it is also the honest answer to iOS having no per-category switches: whatever the system allows through, the record is complete.
  • settled A decline is recorded. The people work made a decline indistinguishable from silence, and that rule holds where it was aimed: nothing is sent, nothing interrupts, and re-requesting stays rate limited on the server. A line in a record somebody opened deliberately is not a notification.
  • So it is worded flatly and offers nothing. "Ana declined Berlin in October", and underneath, that nothing was sent at the time. No retry, no explanation, no softening: a no that arrives with a button is a no the product is arguing with.

  • everything on this page is now settled Nothing below is a question. The four items are consequences of the calls made, and each one is a thing code has to decide how to do rather than whether.
  • The gate is the headline. is_reminder decides what is announced, so the digest job's query is due_at in range and is_reminder = true. Everything else in this design works whether that flag is on or off; the volume of notifications does not.
  • The filing prompt now carries a decision it has never had to make. Marking is_reminder was free when nothing read it. It is now the difference between a person being told and not being told, which makes it worth a principle and an eval case, in the same way principle 04 governs the dates themselves.
  • A person cannot ask to be reminded. The flag has no person-facing writer by decision, so the bell mark in section 4 reports it and nothing sets it. If that proves wrong it is one switch in a sheet that already exists, which is a cheap thing to be wrong about.
  • Nothing is sticky. The model may move a date a person set, where the dump states a new one, so the change mark and the Activity row are the whole defence. Both already exist.
