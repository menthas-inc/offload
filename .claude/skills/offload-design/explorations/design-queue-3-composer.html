10 · A turn that failed, and a turn that half worked

web, then the phones · raised 2026-09-03

A dump can fail outright, or file some of what you dumped and not the rest. No kit draws either. Both are inline and persistent rather than toasts, because a toast clears itself after eight seconds and would take the only way forward with it. The words differ because the situations are opposites: one has nothing in a thread and everything in the composer, the other has the reverse.

  • Never both at once. A finished turn offers Undo, a partial one offers Finish it. Asking somebody to choose between finishing and undoing inside eight seconds is not a choice.
  • Finish it is not a re-send. Part of the dump is already in a thread, and sending it again would file that part twice.
  • Both carry role="alert", where the Undo toast is role="status": a confirmation is announced without interrupting, a failure interrupts.
  • The two share one treatment, small secondary type under the turn with an inline action, and differ only in the words and the action's colour.

  • A, as built. Quietest of the three, and it reads as offload's own aside rather than as an error box in a conversation. The cost is that a failure looks a lot like a normal turn on a busy screen, and the only thing marking it is a coloured word.
  • B, the system's own inline-err treatment, which exists in the kits for the failed-dump case and is what a reader would expect to see reused. Unmistakable. The cost is weight: a tinted card inside a conversation is the loudest object on the screen, and the failure is usually transient.
  • C, the turn carries it. The failure is attached to the thing that failed, which is the tightest possible connection, and it costs one line. The cost is a clay border on a message somebody wrote, which reads as though their words were the problem.
  • The recommendation is B for failed and A for partial. They are genuinely different: a failure needs finding, since nothing happened and the person may have walked away; a partial turn already has a visible reply saying what did happen, so the line under it is enough. That splits one treatment into two, which is worth writing down as a rule rather than leaving to each screen.
Recommended: B for failed, A for partial

11 · The reply that links to the threads it wrote to

all · raised 2026-09-03

A reply saying "Added to Flat admin" now carries Flat admin as something you can open, built from the content rows the turn actually produced rather than from the words in the sentence. No kit draws it. It matters more than it looks: it is the first time the composer does something other than talk.

In the app now Composer.tsx, moss pills under offload's turn

  • Moss, and it has to be. These are "offload did this, you didn't" made clickable, which is moss's stated job, and one of its listed uses is thread references in a reply.
  • Done means something was done. The tick is gated on the same record the links come from, so a question that got an answer and a request that was refused no longer wear one.
  • The pills and the toast cannot disagree, because both read the content rows the turn produced.

Filed both. The brackets went with the bookshelf build, and Ana’s invoice note is a memory on Flat admin.
Bthe names in the sentence become the links
  • A, pills under the sentence. The destinations are a list you can scan and tap, at a 26px height that clears a touch target on the phones, and the pills come from the record so they are true even when the sentence is loose. The cost is repetition: the reply names the threads and then the pills name them again.
  • B, link the names in place. No repetition, and it reads like prose rather than a receipt. The cost is real and it is the reason A was built: matching a name in a sentence to a row in the record means matching on text, and offload naming a thread it did not write to is exactly the failure this is meant to prevent. It also gives a phone a 14px tap target inside a paragraph.
  • The recommendation is A, with one refinement: when the reply names exactly one thread, the pill is the only mention and the sentence drops the name. That removes the repetition in the common case without ever matching on text.
Recommended: A, with the single-thread refinement

12 · A theme switch and a type-size control

all · raised 2026-09-04

Two controls at the foot of the nav, beside Settings, and neither is in any kit. Light and dark, and larger text. The type scale is now a token here, so the app can stop defining it, but nothing in the design system says where these controls live or what they look like.

In the app now Preferences.tsx, two quiet icon buttons in the sidebar foot
Settings
NOWmoon flips the theme, scan-text toggles 1.15
Body at 100%Body at 115%

Type scales, layout does not. The sidebar stays 248px, the pane stays 520px, radii and icons stay literal. Larger text used zoom first, which pushed the right-hand pane off a laptop screen.

NOW[data-type="large"] overrides the eight size tokens
  • Both are kept on the device, in localStorage, not on the account. Theme falls back to the system preference on a fresh browser, which is a small contradiction of the closed decision that light is the default for a new account.
  • Two states each, not a scale: dark or light, 100% or 115%.
  • The glyphs are moon and scan-text, and scan-text is doing a job no label explains.

  • A, as built. One tap from anywhere, which suits a control people flip by time of day. The cost is two unlabelled glyphs, and scan-text does not say "bigger text" to anybody who has not been told. It also puts an accessibility control behind an icon with no name.
  • B, named rows in the same place. Still one tap, and the label says what it does and what state it is in. The cost is two more rows in a nav that is otherwise threads, and it makes the foot of the sidebar a small settings panel.
  • C, a Settings page. Where the ten Settings pages already live, with the system's own SegmentedControl and room to grow into a real type scale later. The cost is three taps to flip the theme, on the one preference people change most.
  • The recommendation is B in the nav and C as well. The pair belongs in Settings because that is where somebody looks for it, and the nav keeps a labelled shortcut because that is where somebody uses it. Both read the same stored value, so there is no second source of truth. If only one can be built, B: an unlabelled accessibility control is the defect worth fixing first.
Recommended: B, and a Settings page too
