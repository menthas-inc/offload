7 · A swipe deletes, a long press opens the rest

mobile, android · raised 2026-09-05

No kit draws a content row action on any platform. SwipeRow reveals a delete and nothing else, with the trash glyph and the clay ground written into the component. Web's action set is authorship-conditional, so a fixed gesture map is wrong for half the rows. The phones answered with two gestures.

  • The sheet has no disabled state on purpose. It lists what this account may actually do and omits the rest, because a control that is drawn and refused teaches a rule that is not true. Sam's row shows Edit and Archive and no Delete.
  • A row that is not yours does not park open at all. The pan settles back rather than revealing a control the server would refuse.
  • 320ms long press, 12px horizontal activation, 8px vertical failure, so a scroll never opens either thing.
  • The stated cost: archiving is the commonest action and now takes two gestures, a press and a tap.

  • A, as built. One gesture per certainty: the swipe does the destructive thing it was drawn for, the sheet handles everything conditional. The cost stands: two gestures for the action people take most.
  • B, two actions in the swipe. Archiving becomes one gesture and the sheet disappears. The cost is that the reveal now has to be authorship-aware in its own width, and a two-button reveal on a 390px screen leaves 190px of row, so the title truncates while the row is open. It also puts a destructive control under a gesture that people learn by accident.
  • C, swipe archives and the sheet deletes. Matches how often each is used and makes deleting deliberate, which suits the only irreversible thing in the product. The cost is that it contradicts SwipeRow as designed, and every other swipe in the product still deletes, so the same gesture would mean two things depending on the list.
  • The recommendation is A. It is the one that keeps the gesture's meaning constant across the product, and the extra tap on archive is a real but small cost. C is the better answer if the phones later show that archiving outnumbers deleting by a wide margin.
Recommended: A, and govern the sheet

8 · Glyph, the icon contract React Native needs

mobile, android · raised 2026-09-05

The governed Icon is DOM-shaped: it masks an SVG file with currentColor and takes a basePath, which is a URL. React Native has neither. The phones named theirs Glyph, which the adherence lint approved of, and this system owes it a contract.

Options
  • A, govern Glyph as a second contract with the same 80 slugs and the same sizes, and say in the readme that color replaces inheritance on that platform. Two files, Glyph.d.ts beside Icon.d.ts, and the difference is documented rather than discovered. The cost is two contracts to keep in step, and a component that means the same thing under two names.
  • B, widen Icon so color is optional everywhere and the source is either a path or a URL. One name across the product. The cost is a web contract carrying a prop it never needs, and basePath is meaningless on a phone, so the contract would describe two things loosely instead of one thing exactly.
  • C, leave it as a logged divergence. Costs nothing today and means every new client invents its own name for the same object, which is how a set stops being a set.
  • The recommendation is A. The lint already treats them as different components and it was right to. What this system owes is the contract, not a rename.
Recommended: A, a second contract

9 · Filter or group, inside a widget

web, phones · raised 2026-09-03

M3ThreadWidgets.jsx draws ChipRow, a single-select filter above a flat list. The product owner asked for grouping, which is headed sections. Only grouping was built, because shipping both without deciding which is primary is how a screen ends up with two ways to do one thing. The kit has to decide.

  • The group heading is the weakest thing in the feature by the codebase's own account, because it is the only part with no drawn precedent. SectionHeader is 21px over an ink rule, far too heavy for a sub-group inside a section that already has one, so this was built from Chip's vocabulary instead: 12.5px, accent, lowercase, small mark.
  • The unnamed group has no heading at all, or "Everything else" when there is more than one group. Not "Other" and not "Untagged": both are labels offload would be inventing for content nobody categorised.
  • A widget is a view, never a store. Every row in it is a row in the list below, filtered, so nothing here costs a query.

  • A, groups only. Nothing is hidden: every row in the widget is on screen and the tags are the structure. It also needs the group heading properly designed, since it is currently improvised from chip vocabulary. The cost is height on a thread with many tags, and no way to see only one of them.
  • B, filter only. What the kit drew. Compact and familiar, and it answers "show me the receipts" in one tap. The cost is that a filter hides things, and on a screen whose whole promise is that nothing needs filing, a control that hides two thirds of a widget is the wrong default.
  • C, both, with grouping primary. The chip row becomes a view switch rather than a filter, which is two controls collapsed into one and keeps the answer to "which is primary" written on the screen. The cost is a control on every widget that most threads never need.
  • The recommendation is A, and the design work is the group heading rather than the choice: a real sub-heading rank between SectionHeader and body, which the system does not have and which several other screens would use.
Recommended: A, plus a sub-heading rank
