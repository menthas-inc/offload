Design queue 1: the thread page

Six things the web thread page has in code that no kit draws. Each one shows what the app does today, read from apps/web/src/components/panes/Thread.tsx and Memories.tsx, then the options. Everything below is drawn at real size in the design system's own tokens, so what you pick is what gets folded into the kits.

1 · The memories section

web, mobile, android · raised 2026-09-04

A thread holds up to ten standing rules about itself. The author of one gets Delete, everybody else gets Mute, and offload's own get a sparkles glyph. Nothing in any kit draws this, so it was built from the Chip contract with the kits as shape reference.

In the app now Memories.tsx, chips in a wrapping row
Memories 4
Ana pays by bank transfer, not… Book the flights before hotels Keep receipts for everythingSam No calls before 10amMuted Add
NOWchips, truncated at the chip
  • The chip is doing a job it was not built for. Chip is nowrap with no max-width and no ellipsis, every label in every kit is under twenty characters, and a memory runs to 200. The width cap and the ellipsis live in the screen, not in the component.
  • Authorship is the name after the text, in a lighter weight. MemoryChip's small dot was the nearest precedent and it marks who a memory is about, so it was not borrowed.
  • At ten the Add control disappears and a sentence takes its place: "This thread already holds ten. Delete one to add another." Chip now has disabled, so greying it out is available for the first time.
  • An empty section draws nothing, which means a thread with no memories has no way to type the first one. That was deliberate and it is flagged below.

  • A, keep chips and put the rule in the component. Chip gains a maxWidth and an ellipsis, and the disabled Add is drawn rather than replaced by a sentence. Cheapest, and it matches what shipped. The cost is that a memory is a sentence read through a 260px window, so most of them end in an ellipsis and the section becomes a set of things you have to click to read.
  • B, rows. A memory is a rule in a sentence, so it is set as one: full text, wrapped, the sparkles glyph for offload's own, the author's name under it. Reading the section stops requiring clicks. The cost is height, ten rules is a tall block above "Everything in here", and it loses the visual difference between a memory and a piece of content, which the chip carried for free.
  • C, chips with a cap. Keeps the compact look on a busy thread and admits the truncation problem instead of solving it. The cost is a second click to reach a memory that is not in the first two, and "2 more" is a control that says nothing about what it holds.
  • The recommendation is B, with the section hidden when empty as now. The chip was chosen when the nearest precedent was a chip row; the honest reading of the contract is that this is a list of sentences. If you want the compact look kept, A is the one to fold in, and then Chip should own the ellipsis so no screen re-invents it.
Recommended: B, rows

2 · A memory, open

web · raised 2026-09-04

Clicking a memory edits its full text. The editor opens inside the chip, which grows to hold it, animated on grid-template-rows from 0fr to 1fr. It used to sit at the foot of the section, which read as editing the last memory whichever one you clicked.

In the app now Memories.tsx, the chip becomes a container

NOWopens in place, one action plus Cancel and Save
  • One destructive control, never two. Delete and Mute are the same intent at different strengths: if you may delete, Mute is a worse version of it, and if you may not, Mute is the whole of what you have. Muted wins over both, so a quieted memory offers Unmute whoever is asking.
  • The focus ring needed 5px of room inside the animation clip, the first value that clears a 2px ring at 2px offset. Removing the ring was tried and reverted: the rule says it is never removed.
  • 200 characters, counted live. Enter saves, shift-Enter is a new line, Escape closes.

  • A, the pill becomes the container. What shipped. The thing you clicked is visibly the thing you are editing, which is the whole reason it moved off the foot of the section. It needs a real contract: a chip that can be a container is not a chip any more, so this is a MemoryEditor in the system with the chip as its closed state.

  • If you pick rows in section 1, B is nearly free: the editor becomes the row expanding, and there is no pill to grow.
Recommended: A if chips stay, B if rows win

all · raised 2026-09-03

Every kit draws an archive tool on a row. No kit draws where an archived thing goes or what it looks like when it gets there. The app invented both, and the control has already moved once.

4 · A finished task, in place

all · raised 2026-09-03

A ticked task sinks to the bottom of its list rather than leaving it, and stays visible struck through. No kit draws a completed task at all. The reasoning is already settled: something you did this morning disappearing is how you end up wondering whether you did it, and the tick is the reward for the work.

In the app now Widgets.tsx, a real checkbox and a line through
To do 4
Book the airport transferFri 12 Sep
Confirm the apartment codeSam
Flights bookedyou · this morning
Renew the passportyou · 28 Aug
NOWstruck through at 55%, sunk to the bottom
  • Any member may tick or untick. A thread's contents belong to everybody in it and neither direction destroys anything, so this is not authorship-gated the way delete is.
  • Both directions get a toast, "Ticked off" and "Back on the list", inside the same eight seconds.
  • The strike-through carries 55% opacity on top of the line, which is the same mechanism section 3 has a problem with.

Atertiary ink, line at 1px, no opacity
To do 2 2 done
Book the airport transferFri 12 Sep
Confirm the apartment codeSam
Flights booked, Renew the passport
Bdone collapses to one quiet line
  • A, as built with the opacity removed. Tertiary ink and a hairline strike, which reads as finished without dimming the row into the page. One rule to add to the system and it applies to any list with a checkbox in it.
  • B, the finished ones collapse. A long-running thread accumulates ticks, and after a fortnight the to-do widget is mostly history. Collapsing them keeps the widget about what is left while still proving the work happened. The cost is that the tick's reward is smaller: the row you just ticked leaves the list within a second.
  • The recommendation is A. B solves a problem threads do not have yet, and it can be added later as a cap: collapse only once more than five are done.
Recommended: A

5 · Row tools, drawn as conditional

all · raised 2026-09-03

Every kit puts trash-2 on every row. OFF-3 says a member can never delete what is not theirs, so in the app the control is conditional and the server computes the flag. The kits should draw both cases.

In the app now Thread.tsx, three tools for the author, two for everyone else

NOWthe row asks in its own place, then eight seconds
  • The tools are always visible, not hover-revealed: two rows side by side show a different number of controls, which is the point.
  • Delete asks first, in the row's own place, so the question never covers the thing it is about. That is a confirm and an undo, which is more than OFF-6 asks for, and deliberate: this is the only control in the product that destroys something.
Options
Tram 28 route mapSam · 12 Aug
Aabsent, as built
Tram 28 route mapSam · 12 Aug
Ba More menu holds whatever this row allows
  • A, absent. A control that is drawn and refused teaches a rule that is not true, and this is the position the phones already took for the same reason. Two rows showing different tools is a little uneven, and that unevenness is honest.
  • B, everything behind one More glyph. Every row looks identical and the menu holds only what you may do. It also gives the row somewhere to put move, share and anything later. The cost is a click before any action, on the tools people use most.
  • The recommendation is A for edit and archive, B as well for anything beyond them, which is exactly what section 6 is about.
Recommended: A

6 · What the pane head holds

web · raised 2026-09-04

WThing.jsx passes tools={[["maximize-2","Open full"],["ellipsis","More"]]}, and the app has never built the More menu. Instead the pane head has grown: rename, archive, Open full, plus the faces and Share. The kit should say what is in the ellipsis, or agree there is not one.
