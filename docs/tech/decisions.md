## Provenance

offload starts from superparent's stack rather than from nothing, because most of those decisions were good and none of them were free. What follows is what carried over, what changed, and why. Where a decision is inherited unchanged it says so, so nobody re-derives it.

## Clients

- ✅ **Expo (React Native) for both phones, with a deliberate native escape hatch.** Inherited from superparent. The escape hatch is new and it is the reason for three rules that are not negotiable: the API contract is platform-agnostic and OpenAPI-described; business logic lives behind the API or in plain TypeScript with no React imports; design tokens ship as generated JSON, never as `StyleSheet` objects. The likely future is native iOS with Android staying on Expo, not a full rewrite of both.
- ✅ **The two mobile kits are genuinely different and the code should admit it.** The design system ships an iOS kit and a Material 3 kit with different navigation motion and different component chrome. Use `.ios.tsx` / `.android.tsx` where a component really differs and `Platform.select` for a constant. Do not build one component with a pile of conditionals.
- ✅ **One Next.js app, three route groups** (`(marketing)`, `(app)`, `(admin)`). Inherited from superparent. The admin group gets its own layout with the moss navigation, so it is never mistaken for the app.
- ✅ **Online-first with a durable outbox.** Changed from superparent, which was online-first with nothing local. A dump must never fail, because dumping happens on a train. Writes queue locally (SQLite on mobile, IndexedDB on web) and sync when there is signal, showing as pending. Reads still need a connection. *Rejected: full local-first sync (Legend-State, PowerSync). It solves a problem we do not have yet, and shared threads make the conflict story worse, not better.*
- ✅ **TanStack Query v5 for server state, Zustand for ephemeral UI only.** Inherited. The boundary stays strict.
- ✅ **Push via Expo Push.** Inherited. *Gotcha, also inherited: tickets report accepted, not delivered. Instrument an app-side receipt callback or notification health is invisible.*
- ✅ **Undo is a flag flip.** Nothing is destroyed while the toast is up, and the purge happens after the eight-second window. The design system's prototype does exactly this and the reason it gave is the right one: it is what makes undo cheap.

## Backend

- ✅ **Two planes: TypeScript Core API plus Python agent plane.** Inherited from superparent, and it held up there.
- ✅ **Fastify, not NestJS.** Changed. Nest's structure was genuinely useful for agentic implementation, but it is a lot of ceremony for one developer, and `zod` plus `fastify-type-provider-zod` gives us the parts we wanted: validated DTOs, generated OpenAPI, clear module boundaries.
- ✅ **Single writer.** The Core API owns the canonical schema, the migrations and every canonical write. The Python plane reads through SQLAlchemy read-models and writes derived artifacts through a Core API internal endpoint. Inherited, and it is the decision that keeps validation and encryption in one place.
- ✅ **Kysely plus hand-written SQL migrations.** Inherited. The model is unstructured-first, so migrations copy data, which is where a declarative-diff ORM stops paying for itself. *Prisma and TypeORM rejected, same reasoning as superparent.*
- ✅ **UUIDv7 primary keys.** Inherited. Time-ordered, non-enumerable.
- ⚠️ **Data model is not designed yet** and it should be its own spec before any table exists. What is already fixed by the product: `thread` holds `content`, a `memory` is separate and polymorphic, a `connection` is a person you can share with, a `grant` is thread-level and one-permission. Name them exactly that in table, field, route, type and prop, from the first migration. The design system's fixture calls a thread a `space` in places; that is prototype residue and it is not a schema.

## Ownership, sharing and tenancy

- ✅ **Authorship plus membership, not tenancy.** Changed from superparent entirely. superparent had a household tenant and a `household_id` on every row. offload has personal accounts and per-thread sharing, so the boundary is an authoring `account_id` on every content row plus a `thread_members` row per person in a thread. There is no tenant and there is no thread owner.
- ✅ **Threads have members, not an owner (2026-08-27).** The creator is the first member and nothing more. *Supersedes a draft of spec 001 that gave `threads` an `owner_account_id` and then needed a rule for transferring it when the owner left. The design forbids the distinction outright, "no roles, no viewer and editor", so an owner column was a role smuggled into the schema. Dropping it removes the transfer rule, collapses `grants` into `thread_members`, and turns "My threads" from a `UNION ALL` of owned and granted into one indexed lookup. `created_by_account_id` stays as an informational column because the UI wants to say who started it; it carries no permission.*
- ✅ **A thread dies with its last member.** Deleting a thread other people are in means leaving it. When the last member leaves, the thread and its things are deleted, since nothing can reach them. *This is the only path that destroys another person's things and it is correct, because by then nobody is left who could read them.*
- ⚠️ **The word "delete" now does two things**, depending on whether anyone else is in the thread, and the kits draw one control. Raised in the design system's log.
- ✅ **One permission, enforced per row by author.** A grant means they can add to a thread and can never delete what is yours. That is a per-row check on the author of the thing, not a per-thread role. No viewer and editor, no roles, no public links.
- ✅ **Sharing never lets anyone new into offload.** A share targets an existing account, matched by email or username. Someone without an account goes through the waitlist. Carried straight from the design system's closed decisions.

## Privacy and encryption

- ✅ **Content is durable, egress is not (OFF-1).** Changed from superparent, and it is the deepest change. superparent's identity was never persisting content. offload's identity is persisting it. The hard line moved from storage to egress.
- ⛔ **Superseded 2026-08-26: per-account envelope encryption of content columns and blobs, with the root key held outside the database.** Dropped in favour of the cold-storage-only entry below, after the root key moved into the database and vectors stayed plaintext, which left the database half of it defending against nothing while costing a decryption path on every read. *Kept because the reasoning is the starting point if database encryption is ever revisited, which is GA item 2 below.*
- ✅ **Encryption is scoped to cold storage only (2026-08-26).** Blobs in R2 are encrypted with a key R2 does not hold. Database content, including titles, notes, transcripts, memories and retrieval vectors, is plaintext in Postgres, protected by the provider's disk encryption and by access control. *This supersedes the earlier decision to encrypt content columns. That version encrypted the database while keeping the unwrapping key in the same database and the vectors in the clear, which was real complexity on every read for almost no defence. A narrow claim that is true beats a broad one that is not, and OFF-2 now states the narrow one.*
- ✅ **The honest consequence, written down so nobody rediscovers it in an incident.** A database dump exposes all text content. Encrypting a blob protects the media, not what the media says: a voice note's audio is encrypted while its transcript is a plaintext column, and the same holds for screenshot text and image descriptions. Anyone reasoning about the privacy posture should start from those two sentences.
- ✅ **Retrieval stays ordinary.** pgvector with an HNSW index, plaintext vectors, normal Postgres full-text search alongside. No per-account decrypted cache, and any embedding model is available, bounded only by pgvector's indexable dimension ceiling recorded under Infrastructure. *The alternative was benchmarked on 2026-08-26 before it was dropped: decrypting a 10,000-thing account took 21ms and a similarity query 1.4ms, so it was viable on compute, but the corpus could not be fetched per query (41MB at 1024-dim float32) and so it required a warm per-account cache plus embeddings truncatable to 256 or 512 dims. Those numbers are kept because they are what a reversal would need.*
- ✅ **Root key lives in the database through alpha and beta (2026-08-26).** No separate KMS provider and no extra vendor while the only content at risk is our own. Since the key now protects blobs rather than the database, the two sit in different providers, Railway and Cloudflare, so a compromise of either one alone is not sufficient. That is a genuine, if modest, separation, and it is more than the previous configuration had.
- ✅ **The key schema is migration-ready from the first migration.** Each layer is stored separately: the object; its wrapped object key; `thread_keys`, one wrapped copy per member; `account_keys`, one per account with a `wrapped_by` column naming the root that wrapped it, for example `db:v1` and later `aws-kms:<arn>`; and the root itself behind a `RootKeyProvider` interface with one implementation per custody choice. Moving custody later is one rewrap job over `account_keys` alone, proportional to accounts, with no thread key, object key or object ever touched. *Without the `wrapped_by` column and the interface this stops being cheap, which is why both exist before there is any code.*
- ✅ **Four key layers: root, account, thread, object (2026-08-26).** The root wraps each account key. An account key wraps a copy of the thread key for every thread that account is in, so a thread key exists once and each member holds their own wrapped copy of it. The thread key wraps a per-object key. The object key encrypts the blob. It is one wrap-and-unwrap operation applied consistently, so it is one helper and three small columns, not four mechanisms. *There is no unsorted case to handle: a dump lands in the account's default thread, so an object key is wrapped by a thread key from the moment it exists.*
- ✅ **Why the thread layer.** Co-ownership is a property of a thread, so the thread is the natural key unit and the model should say so rather than have the code reconstruct it object by object. Sharing becomes rewrapping one small key for the new member. *Supersedes an earlier per-account decision that treated sharing as purely an authorization check.*
- ✅ **Why the object layer underneath it.** Without it, moving content between threads means downloading, re-encrypting and re-uploading the blob, and the eight-second Undo window (OFF-6) means holding both copies while it is open. With it, a move rewraps 60 bytes and Undo rewraps them back. *This matters more here than it would elsewhere: the design system's philosophy is that structure appears afterwards and can always be corrected, so re-filing is the correction path for the feature that defines the product, not an edge case.* It also means handing a key to a client grants exactly one object, which keeps every upload-path option open.
- ✅ **Account deletion, resolved.** Deleting an account destroys its account key and its wrapped copies of thread keys. Private content goes with it. Shared threads survive untouched, because the other members hold their own wrapped copies of the same thread key. No blob is ever re-encrypted and no dead account's key is retained. *This was the question that decided the layout: with the account key encrypting blobs directly, the only alternatives were keeping a departed person's key forever or rewriting every shared object.*
- ⚠️ **The product must say this before someone shares, and the design does not currently cover it.** The share sheet states one permission, that they can add to it and can never delete what is yours. It says nothing about what happens when a member deletes their account, and the answer, that their things stay in the thread, is exactly the kind of thing a person should agree to in advance. Raised in the design system's own log under Open.
- ✅ **Blobs go through the Core API and we do the encrypting (2026-08-27).** The client POSTs a file, the API mints the object key, encrypts with AES-GCM and streams the ciphertext to R2. *This closes the SSE-C tension by removing SSE-C: we never use it. R2 stores opaque bytes and never receives a key at all, which is strictly stronger than SSE-C, where Cloudflare is handed the key on every request. OFF-2 is upgraded accordingly, from "a key R2 does not hold" to "a key R2 never sees".*
- ✅ **Why not the two zero-egress options, yet.** Pre-signed upload with the object key on the client is free forever and scales without us, but it puts binary key material and header signing into three clients, which is where this class of bug lives. A Cloudflare Worker in front of R2 is the best long-term shape, and it is a third deployment target, a second place holding keys, and a new authorisation surface. Both are premature while the bill is a dollar.
- ✅ **The trigger is a number, not a feeling.** Railway charges $0.05/GB egress and R2 charges none, and upload and download each pay it once. That is roughly $1 a month at alpha, $67 at a thousand active people, and $675 at ten thousand. Move to direct-to-R2 when the monthly egress bill exceeds the engineering, which is somewhere in the low hundreds of active accounts.
- ✅ **`blobs.encryption_scheme` makes that move painless.** Every object records how it was sealed, so a later scheme runs alongside the current one: new objects use it, existing objects keep working, and nothing is ever re-uploaded or re-encrypted.
- ✅ **Key backup is an operational requirement, not a nicety.** Losing the root key loses every blob, and with self-encryption there is no provider who could help even in principle.
- ✅ **Connected-app content is process-and-forget (OFF-4).** Inherited from superparent's SP-1, scoped down to connected apps only. Derive and discard, keep a source reference for on-demand re-fetch. *If batching ever forces a buffer, it inherits superparent's full control set: volatile store only, per-account key, hard TTL, no disk persistence, atomic purge after processing, size ceiling at ingest, privacy-policy disclosure.*
- ✅ **No retention on user-facing content (2026-08-27).** Things, media, conversations and memories are kept until the person deletes them. *Supersedes an earlier entry in this file that carried the design's 60-day conversation rule across as a promise to implement. It is a divergence from the design and it is logged there, because the Settings kit draws a "Keep conversations for" page that this makes vestigial unless it becomes a Forever-only display.*
- ✅ **Retention applies to our data, not theirs.** Analytics events, application logs, traces and Langfuse metadata get a short clock. *This is the honest version of data minimisation here: deleting someone's photos on a timer is not privacy, it is losing their things; not keeping six months of logs about how they used it is. The specific windows are still to be set, per stream, when analytics is built.*
- ✅ **A useful consequence: a memory can always show its sources.** Because raw content never ages out, the provenance the design draws on a memory stays true forever. It removes the state we would otherwise have needed, where offload knows something and cannot say why.
- ⚠️ **The obligation moves to storage growth.** Nothing shrinks, so per-account storage only rises. That is a cost line to watch rather than a correctness problem, and it should have a number attached once there is real usage.
- ✅ **No content in Langfuse.** Metadata-only tracing: ids, model, tokens, latency, tool names, outcomes. This is what makes Langfuse Cloud acceptable rather than self-hosted.
- ✅ **The privacy policy is general, and the companies have their own page (2026-10-05).** Owner: "generalize when it helps", so ordinary product work does not make a line untrue. The policy promises outcomes (what you delete is deleted, promptly, backups within 30 days; no training; no sale) and names kinds of companies; `/privacy/companies` lists them with its own date, and a material change to how content is handled is emailed in advance. Controller named (Behrooz Afghahi, an individual), **US only** (no EU or UK sections; store listings restricted, `going-public.md` item 22), rights for everyone in the US, a health section, Do Not Track, a section for people not on offload, and Google's Limited Use statement with no staff read of Google data outside it. First run's ticks now accept the terms and name AI services from other companies (Apple 5.1.2(i)); `CONSENT_VERSION` moved to 2026-10-05. Sources: the legal review and claim audit of 2026-10-05.

## Agent and LLM

- ✅ **Structured outputs as a hard contract (OFF-5).** Inherited. Pydantic schema via `output_config.format`, one repair-and-revalidate retry on failure, then raise, and log every failure.
- ✅ **Task tiers, not per-call-site model choice.** `sort` = Claude Haiku 4.5 (`claude-haiku-4-5`), `converse` = Claude Sonnet 5 (`claude-sonnet-5`), `reason` = Claude Opus 5 (`claude-opus-5`). *Amended by 004: a dump no longer hits a `sort` one-shot. It hits the planner, a tool-calling loop, because a structured verdict cannot recover from a tool that fails and tools are the architecture every later capability arrives on. The cost argument transfers rather than disappearing, since every dump still takes this path, and the optimisation to reach for is a cheap structured pre-pass in front of the planner rather than a cheaper planner. Recorded because replacing a decided architecture quietly is the failure this file exists to prevent.*
- ✅ **Adaptive thinking plus effort on the two upper tiers.** `thinking: {type: "adaptive"}` with `output_config.effort` as the depth control. `budget_tokens` is removed on these models and returns a 400: do not carry that pattern in from older code.
- ✅ **Thin harness over the Anthropic SDK, no LangChain.** Inherited. Prompts as code in git, mirrored to Langfuse for inspection, eval-gated in CI.
- ✅ **Prompt-injection boundary (SEC-1).** Dumped content and connected-app content are untrusted data. They travel in user-turn content blocks and never in a system prompt. The system prompt states the rule.
- ✅ **Per-account token ledger in Postgres**, categorised by job, with a soft alert and a hard reject before the call. This is exactly what the admin panel's Costs and Limits pages read, including its rule that a cap can slow down, drop to the cheaper tier, or stop, and that dumps are always still saved.
- ✅ **Prompt caching on the frozen system prompt and stable per-account context**, verified with `usage.cache_read_input_tokens`. Batch API for anything off the request path.
- ✅ **Embeddings: Voyage 4 (2026-08-27).** Best retrieval quality available, Matryoshka widths so the dimension stays ours, $0.06 per million tokens with 200M free on the v4 generation, and a first-party reranker to reach for rather than a second integration. MongoDB-owned, so real data terms. *Cost is not the deciding factor and it is worth saying why: at roughly 250k tokens per account per year, alpha is about 30 cents a year and ten thousand accounts is about $150. A self-hosted container costs more than that from day one, so self-hosting would have been the expensive option, not the cheap one. The one real argument for it was avoiding a second company that processes content, and that is what we are paying.*
- ✅ **Stored as `halfvec(1024)`.** Voyage 4's default width, kept in half precision: 2KB per vector instead of 4KB, no measurable quality loss on normalised vectors, and comfortably inside pgvector's 4,000-dimension `halfvec` index ceiling. A heavy account's 20,000 things come to about 40MB of vectors.
- ✅ **Retrieval on pgvector**, roughly 400-token chunks with breadcrumb prefixes, HNSW index, alongside Postgres full-text search for exact terms. *Gotcha, inherited: store raw chunks separately from vectors so a provider or model change is a re-embed, not a data loss. Cheap for us, because content is never purged.*
- ✅ **Dense embeddings do not understand negation, and no provider fixes that.** On the NevIR benchmark, standard embedders score **below random**: MPNet 8.1% and Jina 14.6% against a 25% baseline, and a negation-specialised model still only reaches about 40%. The cause is structural rather than a vendor failing: contrastive training puts topically related text together, and "Lisbon" and "not Lisbon" differ by one token of truth value and nothing of topic. **The fix is a reranker, not a different embedding model**, because a cross-encoder attends over query and document together; rerankers score 15+ points above the best embedder on the same benchmark. Add one when precision demands it, without changing provider.
- ✅ **Three choices already insulate us from it, and none was made for this reason.** Search is a tool call, so Claude plans the query and emits structured filters against real columns (`done_at`, `thread_id`, `kind`, `occurs_at`) and the embedding only ever sees the positive part. Retrieval feeds an LLM that reads the text, so a negated memory retrieved for its own topic is correct behaviour and a false positive costs tokens rather than correctness. And the sorter is a structured Claude call rather than a nearest-neighbour lookup, which is the one place misfiling would have been silent.
- ✅ **The rule that follows: cosine similarity may shortlist, it may never decide.** Anywhere a distance threshold makes a decision with no LLM in the loop, negation is a live bug. The concrete case in this product is deduplication, where a thing and its negation look nearly identical: if dedup is built, it needs an exact check or a model reading both, never a distance threshold.
- ✅ **Reversible by default, confirmed when outward facing (OFF-6).** Changed from superparent's propose-don't-execute. offload acts and offers Undo. The reversible allowlist starts as: create, update, soft-delete a thing; create or rename a thread; move a thing between threads; write or forget a memory. Everything else is outward facing until listed here, which explicitly includes sharing a thread with a person, since that is a message to someone. **Amended 2026-09-03 by 005: `archive` and `restore` join the list.** **Amended again by 006: `edit_content`, `move_content`, `complete_content`, `archive_content` and `rename_thread` join it as model actions.** *Corrected 2026-10-02: 006 said "all inside 004's whole-turn Undo", and that was never built. The turn's Undo reverses what the turn created, the labels it set and the answers it applied; a change these five make to a row or thread that existed before the turn stays after Undo. See the open item below.* **And by 007: ticking, reprioritising and `set_thread_preference`, all reversible by writing the previous value back.** **And by 008: writing, editing, muting and unmuting a memory. "Forget" leaves the list: offload has no delete for a memory and no tool for one, so the only thing that removes one is a person.** **And on 2026-09-16: moving a note within its section, which is a reprioritise on the notes table, reversible by writing the previous number back; dragging a To do row is the reprioritise already listed.** **And by 025 (2026-09-27): labels, on the three terms in "Labels, decided during 025".** **And by 036 (2026-10-04): soft-deleting a photo row, or a thread as its last member, now ends in its file.** The photo is condemned on the row's own eight seconds (the thread's 15 second restore window for a thread), Undo puts it back, and the purge destroys the object only once no live row carries it. Before this, deleting a photo row never deleted the file, since its message still held it, and the privacy page's *goes from file storage as soon as you ask* was untrue for photos from 020 to 036. **And by 026 (2026-10-01): a mail turn.** An email forwarded to `over@to.offload.club` is filed by a turn that writes exactly what a dump's turn writes, inside 004's whole-turn Undo, and nobody is at a toast when it lands, so the Undo is held on the email's Activity row for 24 hours instead of eight seconds. A mail turn is never answered and answers no open question. Archiving takes something out of a thread's active list without destroying it and is available to every member, which is what makes a shared list usable; without it a co-owned list fills with rows only their author can clear.
- ⚠️ **A model's change to something filed before its turn is not undone by the turn's Undo, which falls short of OFF-6 (2026-10-02).** `undoTurn` soft-deletes the content and notes a turn's messages produced, undoes its labels and restores answers from `questions.previous_value`. Nothing records the previous value when `edit_content`, `move_content`, `complete_content`, `archive_content`, `rename_thread` or `set_thread_preference` writes, so pressing Undo leaves that write in place. Each can still be reversed by hand from the row or thread, but not from the toast, and OFF-6 asks for the toast. Kept on the allowlist knowingly, as an exception the product owner accepted on 2026-10-02 instead of building the restore. The fix, when it is built, is a turn-scoped record of prior values written server-side by each tool and put back by `undoTurn`, on the `questions.previous_value` pattern, never taken from a client body. 030's `place_prior` is that record for three place fields only; when it lands, this item names those three as undone.
- ✅ **A tool that declines is not a tool that failed (2026-09-15).** The harness counted every `ok: false` result as a failed tool, which made the turn partial, replaced the model's own reply with "That did not finish." and offered Finish it. For a lookup the 016 bound refused, all three were wrong: the bound refusing is the tool working, a resume repeats the refusal exactly, and the model had often already answered with what it found. A refusal now carries `declined: true`; the loop still hands it back as an error for the model to read, and only a genuine failure (unavailable, unknown thread, invalid arguments) makes a turn partial. Every refusal also logs its label and outcome, since two refused lookups used to leave no line at all and then report `failed=['look_up', 'look_up']`.
- ✅ **An answer to a question offload asked is applied through `edit_content`, with no model in the loop (2026-09-16, 018).** A tap sends an option index; the server holds the value, checks the target is a row this account filed in the asking turn, records the field's previous value, and writes the one field as `edit_content` already does, inside a turn of its own so 004's Undo restores it. A typed answer is judged by the sort model with a forced tool and value checks in code, then applied the same way, before the planner sees the message. The write is on the reversible allowlist already; what this adds is that the trigger may be a tap rather than a dump. **The country override enters the provenance bound exactly as the account's country does:** a closed value from a list of about 250, never a word anybody wrote, admitted to `_from_the_dump`'s haystack as code and name. Nothing else about the bound moves. The privacy page's line on this is "A search may carry your approximate location", chosen by the product owner the same day.
- ✅ **The To do fold is the member's, on `thread_members.hide_done` (2026-09-15).** It shipped for a few hours as a third key in `threads.attrs`, which made it co-owned. The two keys that stay there are about how the thread is arranged and belong to it; the fold is about what you have read and belongs to you. The clients still read one `preference` object: the server composes the viewer's fold into it, and `readPreference` never produces it from `attrs`, so the stale copy is ignored and 0044 drops it.

## Narrow re-review, 2026-08-31

`security-reviewer` re-run over the surface reshaped since the last review: dump-as-message, blob reparenting, refcounted deletion, and analytics pseudonymisation. Every finding verified against the file before acceptance. Four were real defects and two of them would have silently destroyed or leaked data.

- ✅ **No `ON DELETE CASCADE` from `messages` to `blobs`.** T8 specified a cascade while the impl-spec three sections away specified refcounting, and the migration author would have had to pick. The cascade is the too-eager failure in the exact shape the spec warns about: account deletion hard-deletes messages, so a photo filed into a shared thread would vanish from that thread. `ON DELETE SET NULL`, and the purge job does the refcount.
- ✅ **`identity_merged` carries `subject_id`, never `account_id`.** An older entry in this file, written before the pseudonym decision and never reconciled, said the event carries a real account id. The only place it could have gone is inside `properties`, which erasure never touches, so **one event type would have silently defeated the entire shredding scheme** while every other event was correct.
- ✅ **A sort result's destination thread is re-validated server-side.** Moving content checks membership of the destination; creating one from a dump did not. The thread comes from a model reading untrusted dump content, so trusting it is trusting the caller for an access decision (SEC-2), and OFF-5 validates the shape of a model's output, never its authority.
- ✅ **`messages` and `people` join the purge sweep.** Both carry `deleted_at` with no scheduled hard delete, which is the failure this spec names in its own opening convention: an undone dump, transcript included, would have lived in Postgres forever. `people` is the same class of bug the previous review caught for `blobs` and `memories`, missed on one table.
- ✅ **Thread death names its cleanup.** `thread_keys`, `blob_keys` and `content_blobs` rows are deleted explicitly when a thread loses its last member. *Left implicit, a stale link keeps a blob's refcount above zero forever, so an object nobody can open is also one nothing will ever delete.*
- ✅ **Undo reconstructs a dropped wrap** by re-wrapping from a surviving scope, which is why dropping one does not violate the eight-second guarantee. The purge job, not the delete path, removes the last wrap.
- ⚠️ **OFF-4 is unresolved for connector-sourced messages, and the seam exists now.** `messages` is kept indefinitely with its full text, which is right for something a person handed over and wrong for something pulled from a mailbox. Nothing distinguishes a forwarded email from an automated pull, and both land in the same keep-forever row. The connector spec must give connector-sourced messages a discard path or reserve those `source` values for person-initiated shares.
- ✅ **The `source` overload is naming only, not security.** Confirmed: separate columns, separate tables, disjoint value sets, no shared enum or validation path. *One preventative note carried forward: never define a single shared Postgres enum or a CI rule keyed on the column name `source` across both, since that would conflate an OFF-4 provenance signal with an analytics emitter tag.*
- ✅ **What the reviewer found sound**, worth recording because it is the part that was reshaped hardest: blob authorization resolving dynamically through `content_blobs`, `messages` and `thread_members` rather than a denormalised column; revocation on leave and account deletion; pending invitees holding no key until accept; and delete authorization being per-row by author with edit open to any member, with no per-thread role masquerading as the rule.

## Domain and hosts, 2026-08-31

## Naming, 2026-08-31

- ✅ **`kind` was doing too many jobs, so three of them were renamed.** It appeared on six tables meaning six different things, which is how a reader stops reading the word and starts guessing.
  - `threads.kind` (`now|always`) is now **`always_on`**, a boolean. *An enum of exactly two values is a flag wearing a costume.* The design's own words are "for now" and "always on", so the flag is named after the one it is true for (OFF-7: vocabulary in identifiers, not just copy).
  - `content.kind` and `messages.kind` are now **`type`**. Both answer "what is this", which is what `type` means and `kind` only implies.
  - `content.source_kind` and `messages.source_kind` are now **`source`**. It pairs with `source_ref` and reads as one idea.
- ✅ **Three `kind` columns survive on purpose**, because each is a category rather than a type of thing: `memories.kind` is which chip group a memory appears in, `notifications.kind` is who caused an interruption, and `jobs.kind` is which job to run. Renaming those to `type` would be worse, not better.
- ⚠️ **`source` now means two different things in one database.** On `content` and `messages` it is how a dump arrived (`person|share|gmail|calendar|browser`). On `analytics_events` it is which system emitted an event (`core-api`, `agent`, `mobile`). Both are defensible in isolation and the collision is real. Worth resolving before either is built.

## Grouping inside a thread, 2026-08-31

> ⛔ **Tags, the grouping this section weighed, were retired on 2026-09-27 by 025.** A thread is grouped by labels a person can see, name and correct; see "Labels, decided during 025". The reasoning below about lists stays.

Raised by the product owner against a real case: a shared "Home" thread holding static information, a calendar connection, and several distinct to-do lists, one perpetual (groceries), one recurring (repairs), one bounded (a project lasting a few months).

- ✅ **The design is flat inside a thread, and that is checked rather than assumed.** The kits give a thread one unnamed task list (`contents: { home: { tasks: [...] } }`) and use tags plus filtered widgets as the only sub-grouping, exactly as the file grid already does with `Photos`, `PDFs`, `Brackets`, `Receipts`, some typed and some derived by offload. The product owner's "Home" already exists in the kits as **Flat admin**: house icon, always on, shared. *(The kit fixture spells that `kind:"always"`; our column is `always_on`.)*
- ✅ **Left flat for now, to be decided against real usage (2026-08-31).** Build the flat model, live with real threads, and see whether tags actually feel insufficient before adding a third level to a product whose pitch is that you never file anything.
- ✅ **The retrofit is genuinely cheap, and I said otherwise when framing the choice.** Adding lists later is a new table plus a nullable `content.list_id`. No key changes, because a list would inherit its thread's membership and its thread key, and sharing is per thread. That is additive, unlike the blob reparenting that made the dump question urgent. *Correcting the record: I described this as "easy now and awkward once there is data", which overstated it.*
- ✅ **What tags do not give**, recorded so the comparison is not re-derived: a name you navigate to rather than a filter; ordering, which a grocery list wants and a tag has no notion of; and a lifecycle, which is the strongest signal, since `threads.always_on` exists precisely because a container that ends differs from one that never does.
- 🔶 **The reading that needs no new concept:** a bounded project is its own thread with `kind: now`, so it ends and archives like any finished thing, while perpetual lists are tags inside an `always` thread. What it gives up is the umbrella: the project sits beside Flat admin rather than inside it.
- ⚠️ **The signal that tags were insufficient**, worth naming so "decide later" does not become "never decide": wanting to reorder within a grouping; wanting a grouping to end independently of its thread; or **catching yourself creating threads that are really lists, just to get a lifecycle**. That last one is observable in the data and is the one to watch.
- ⚠️ **Thread-scoped configuration is a real gap, deferred to the connector spec.** Preferences and a connection belonging to a thread rather than to a person, "this calendar is Home's", have nowhere to live: settings are account-level and connectors are account-level and deferred. A thread-scoped calendar is meaningless until connectors exist at all, so it is settled there. Thread preferences are smaller and can ride along. *Static information is already partly covered by thread-scope memories.*

## Processing, threads, tools and context

Recorded 2026-08-27 from the product owner's technical direction. Detail in `architecture.md` (processing modes, threads, tools) and `context-and-memory.md` (compaction and retention).

- ✅ **Two processing modes: interactive and scheduled.** Interactive means someone is waiting: the composer, a question, a tool call. Scheduled means offload is pushing: hourly, daily, nightly compaction, briefs, connected-app pulls, retention purges. *Named this way rather than "async and batch", because both are asynchronous internally, and because "batch" already means Claude's Batch API in this file. The two do line up: scheduled work is exactly the work that can use the Batch API at half price, since nobody is waiting.*
- ✅ **The queue is admission control, not durability.** Interactive requests go through the job table so concurrency and request volume can be bounded globally and per account, which is the same lever the token ledger and the admin panel's Limits page pull. Without it, a burst of dumps is a burst of uncapped Claude calls.
- ✅ **Scheduled work must never starve interactive work.** One table, but priority and deadline differ, so the queue is not FIFO. An interactive job also needs a deadline and a defined behaviour when it misses one.
- ✅ **`thread_id` is NOT NULL on content, and every account gets a default thread, named Miscellaneous (2026-08-27, the brand owner's call).** One-offs, and things that never earn a home, live there: a link sent from a phone to a laptop, a note with nowhere to go. A dump lands there and the sorter moves it if it belongs somewhere better. *There is deliberately no unsorted state, because a partially-placed thing is a case every query and every screen would have to handle. It also removes a special case from the key hierarchy: an object key is always wrapped by a thread key.*
- ✅ **Everything is a tool, including navigation and settings.** The composer is a tool surface, not a chat, which the design system already states. Three consequences: tools execute in two places, server-side for data and client-side for navigation, so the response envelope carries client actions as well as text; every tool declares its OFF-6 tier on the definition, so adding a tool forces the reversible-or-confirmed question; and past roughly a few dozen tools the registry itself threatens the context budget, so the long tail moves behind Anthropic's tool-search tools with `defer_loading: true`.
- ✅ **Volume and access is a required impl-spec section.** Records per account, fan-out, growth, read and write patterns, and every sort and filter a screen needs, written before the schema. Pagination, indexes, denormalisation and partitioning must follow from stated numbers. Format in `docs/specs/README.md`, enforced by `/plan-feature` and checked by `project-lead`. *Estimates are fine; blanks are not. This is preventative: the failure it avoids is a slow home screen whose fix is a refactor rather than an index.*
- ✅ **Context is compacted, not accumulated (OFF-8).** Raw content and conversations are stored as given; memories, preferences and thread standing are continuously compacted and are what a prompt carries. Prompt assembly enforces a budget per tier. Full reasoning in `context-and-memory.md`.
- ✅ **Raw and derived are both kept indefinitely.** The tier split in `context-and-memory.md` is about what a prompt carries, not about what survives. Compaction bounds the prompt; it does not delete the things it compacted from.
- ✅ **An interactive answer arrives whole, after the thinking state. No token streaming (2026-08-27).** The queue carries the response, so there is no second channel between the agent plane and the client, and no reconnection or resumption cases. The kits show a thinking state and then an answer, which this matches. *Revisit only if long answers actually feel slow; keep the response envelope shaped so a streamed variant would not change the client contract.*
- ✅ **Three memory scopes: account, thread, person (2026-08-27).** One polymorphic `memories` table with a scope discriminator and a nullable subject reference. It is what all three kits already draw: the Memories tab is account scope, a thread's standing blurb is thread scope, and the person screen's "what offload knows about them" is person scope. Compaction runs per scope with its own budget, which is where OFF-8's bound is actually enforced.
- ✅ **Connector seams now, connectors later (2026-08-27).** A thing carries a nullable source reference and a source-kind discriminator from the first migration, so it knows whether it came from a person or from Gmail, without any connector being built. *Two columns, and it keeps a later migration off the busiest table. Deliberately mild speculative generality, accepted because the alternative touches `content` after it is large. Source, connector state, token custody and OFF-4's process-and-forget path are all out of scope until the connector feature is specced.*
- ✅ ~~What a row looks like before it is sorted is still open, and it is design's call.~~ **Closed by 028 (2026-10-01):** there is no unsorted row. Content is created by the planner and `fileUnfiled`, already in a thread, and the default thread is now a state, *Not in a thread*, drawn as itself. A thing is in Miscellaneous between being dumped and being sorted, so its thread metadata changes shortly after it appears, and the Today screen has no drawn state for that. Raised in the design system's log. *The name half of this was answered on 2026-08-27.*

## Auth and identity

- ✅ **Better Auth, self-hosted**, sessions in our Postgres. Changed from superparent's Auth0. offload has two social providers and an invite gate we own anyway, so a hosted identity platform is machinery and per-user cost we do not need. *Accepted cost: more of our own code to get right, and no hosted admin console. The admin panel we are building covers the part we care about.*
- ✅ **Apple and Google only.** No password, no email OTP. Order flips by platform, per the design: Apple leads on iOS, Google on Android, Apple first on web.
- ✅ **Invite only, waitlist is the gate.** A valid provider login for an un-promoted identity gets the no-invite screen. Never auto-provision. Waitlist and auth endpoints are enumeration-safe: uniform response and timing whether or not the account exists.
- ✅ **The gate is widened on purpose, by a review code (2026-10-05, 039).** Store reviewers sign in with their own Apple or Google accounts, often a relay address, so no emailed invite can reach them (going-public 21). Staff make a code in the panel (a note, 5 uses, 30 days unless changed; at most 50 and 90), shown once and kept as a SHA-256 of 60 random bits. It is typed under *Have a code?* on the sign-in screen and rides with that one sign-in: beside the token on a native sheet's request, and in Better Auth's OAuth state (`additionalData`, kept server-side for that attempt) on a browser's, never a cookie of its own. It is redeemed in the providers' `mapProfileToUser`, the one point after the provider has said who this is and before Better Auth looks for an account: a verified, un-promoted address is promoted through `promoteIn`, the Waitlist page's promotion, in one transaction with the use it spends and an audit entry (`code.redeemed`, against the code's maker), and Better Auth then finds an invited account and signs it in through the gate's own hooks. Still never auto-provision: the account is made by promotion, not by Better Auth, and only for an address the provider verified. An identity already in ignores the code; a bad one ends at the refusal with `reason: code`. The limit is a conditional update plus a check constraint. Tries: 10 an hour per address, 20 per IP. `switch.review_codes`, on by default, turns it off when the waitlist ends: no client draws the entry and sign-in ignores a code. Owner, 2026-10-05, replacing a first build that took the code on the refusal screen and needed a second sign-in. Considered and turned down: a fixed demo account (a second way in that outlives the review), and minting a session outside Better Auth (it would trust an address the provider may not have verified).
- ✅ **One account, many provider identities**, linked on verified email, so Apple and Google reach the same account. Inherited from superparent, and the same limitation applies: Apple Hide My Email relay addresses cannot be matched and those logins will not link. Document it in the product.
- ✅ **Account lifecycle `waitlist → invited → active → disabled`.** Promotion creates the account before first login so authorization always has a scope. `invited → active` flips when the authenticated person finishes first run, never on an admin action alone. `disabled` blocks new sessions and kills live ones.
- ✅ **Admin is a seeded verified-email allowlist**, app-layer, with two roles: support gets waitlist and people, owner also gets costs, limits and staff. Always at least one owner, and nobody can edit themselves out. Inherited from superparent and matched to the design system's admin spec.
- ✅ **Connected-app OAuth tokens live in a separate vault from login**, encrypted at rest, read only by the service that needs them. Inherited.

## Infrastructure

- ✅ **Railway for compute**, four services in one project. Changed from superparent's GCP plus Pulumi, which is the right answer at 10k DAU and the wrong one at ten. Everything is a plain container, so leaving is a deploy-pipeline rebuild and nothing else.
- ✅ **Railway Postgres to start, Neon as the known destination (2026-08-26).** Everything in one place: one vendor, one bill, one status page, one private network, one set of secrets, and a database that is already there when the services are. At alpha the value of that is concrete and daily, and the value of anything Neon does better is hypothetical. *Reverses an earlier decision in this file that chose Neon for per-PR branching.*
- ✅ **What we are giving up, and what replaces it.** Railway has no database branching, so migrations are tested against a **seeded database** instead: a `seed` script that produces realistically shaped data at realistic volume, run against an ephemeral Postgres container in CI. Before a genuinely risky migration on production, restore a PITR copy into a scratch Railway service and run it there first. That is manual branching, and it is good enough while the volumes are small.
- ✅ **The trigger for moving to Neon is named, so it is a decision rather than a drift.** Move when a migration's behaviour on real data starts to matter more than the convenience of one vendor: a backfill over enough rows that lock duration and runtime are real questions, which the unstructured-first model makes inevitable. Seeded data cannot answer that, and branching is the cheap way to. *Also move if Railway's acknowledged private-networking latency spikes turn out to affect us.*
- ✅ **Keep the exit cheap, deliberately.** It is Postgres either way, so moving is a dump, a restore and a connection string, but only if nothing depends on where it runs. Connect by a plain `DATABASE_URL`, use no Railway-specific database feature, keep the schema and migrations provider-agnostic, and never let a Railway-only capability into the data path. *This is the whole reason the shortcut is affordable and it stops being true quietly.*
- ✅ **Verified 2026-08-31: Railway's managed Postgres carries pgvector 0.8.6.** So there is no trade between the extension and the managed backup story, which is what the concern below was actually about. `create extension vector` succeeds on the standard `railway add --database postgres` service. *Checked on an empty database rather than assumed, because the cost of being wrong is a data migration.*
- ✅ **Provision from a pgvector-enabled Postgres template.** pgvector is an ordinary open-source Postgres extension, not a vendor or a service, but the binary has to exist on the server: `CREATE EXTENSION vector` cannot install it. Railway's base Postgres template does not always carry it, and the failure is a documented one people hit, `Missing vector.control file`. Choose one of Railway's pgvector templates at creation time. *Same shape as PITR below: trivial at the start, irritating afterwards.*
- ✅ **Indexable dimensions are capped well below the storage limit, and it constrains the embedding choice.** HNSW and IVFFlat index `vector` up to 2,000 dimensions, `halfvec` up to 4,000, `bit` up to 64,000. A 3,072-dimension model therefore cannot be indexed as `vector` at full width; it needs `halfvec` or truncation. Carry this into the embedding decision rather than discovering it when the index fails to build.
- ✅ **Enable PITR on day one.** Railway's point-in-time recovery archives WAL via pgBackRest with roughly a four-week window, but it **only covers the period after it is switched on**, so switching it on later leaves a hole that cannot be backfilled. Two other sharp edges worth knowing: restoring a backup deletes every backup newer than it, and backups only restore within the same project and environment.
- ✅ **Nightly logical dump to R2**, which is the one real cost of consolidating. Compute and data now live with the same provider, so a Railway-level failure or an account problem takes both at once. A `pg_dump` on a schedule, written to R2, puts a restorable copy with a different company for almost nothing. *Availability is not the concern here, since if Railway is down offload is down regardless. This is about the data surviving Railway, not about serving traffic.*
- ✅ **Same region, private networking, and measure it.** Services and the database in one region, connected over `*.railway.internal` rather than the public proxy URL. Railway targets under 10ms internally and has acknowledged spike issues, with users reporting anything from 1ms to 100ms, so treat the private-network latency as something to watch rather than something given.
- ✅ **The client address is the leftmost `X-Forwarded-For` entry, and `trustProxy` stays `true` (2026-10-06, security review of 039).** The review read `true` as "the leftmost entry, which a client can write" and proposed a hop count of one. Measured instead of assumed: requests to Railway's own echo service (`utilities-us-east.up.railway.app/raw`, edge `jfk1`, the edge `api.offload.club` answers from, `server: railway-hikari`, no CDN headers) sent with a forged `X-Forwarded-For` and `X-Real-IP` arrived as `X-Forwarded-For: <client>, 152.233.47.67` and `X-Real-Ip: <client>` every time. The forged values were dropped, and the second address is the edge itself (RIPE: CDN77 New York). So the leftmost entry is the client and cannot be forged, and a hop count of one would take the edge's address for every request, putting the whole waitlist and the review code tries in one bucket. Railway's statements disagree with each other and are why this was measured: staff wrote in 2024 that the rightmost value is the trustworthy one, in March 2026 that the edge appends and the leftmost is real, and in June 2026 that the edge strips the header and the first value is the connecting IP; only the last matches what the edge does today. Railway's docs name `X-Real-IP` as the client's address, and staff said in March 2026 that it was wrong while a Fastly path was active, which is why it is not the one read. `offload.club` has no Cloudflare proxy in front. `test/auth-client-address.test.ts` holds the shape. **Revisit if a CDN is put in front of the API, or if Railway's routing changes:** rerun the echo request.
- ✅ **Cloudflare R2 for blobs.** Zero egress fees, which matters when the content is images, and a different company from the database, which is what the nightly dump above relies on. *The transfer path itself is still open, see the SSE-C entry under encryption: pre-signed direct upload was the original intent and it is in tension with server-held keys.*
- ✅ **No Redis. The queue is a Postgres table (2026-08-26).** A hand-rolled `jobs` table drained with `SELECT ... FOR UPDATE SKIP LOCKED`. *Reverses an earlier choice of Upstash, which was carried over without being examined.*
- ✅ **The reason is correctness before it is simplicity.** The product's core flow inserts a `content` and enqueues its sort job. In Postgres those are one transaction. With an external broker they are a dual write, and both failure directions are real: the insert commits and the enqueue fails, so a thing is silently never sorted; or the enqueue succeeds and the transaction rolls back, so a worker picks up a job for a row that does not exist. Making the queue a table removes that failure mode instead of mitigating it.
- ✅ **Hand-rolled rather than a library, because the queue is cross-language.** The Core API (TypeScript) produces jobs and the Python worker consumes them. `pg-boss` is TypeScript only. `pgmq` is an extension, so it needs a binary on the server, which is the same provisioning trap as pgvector. A plain table with `SKIP LOCKED` needs nothing installed and behaves identically from both languages. *It needs the usual parts specified properly when it is built: visibility timeout, attempt count with backoff, a dead-letter path, and an idempotency key so at-least-once delivery is safe.*
- ✅ **Volume is not close to the limit.** Alpha is a handful of jobs a day. Even at 10,000 daily accounts dumping 20 pieces each, that is roughly 2 jobs per second, and Postgres queues are documented handling thousands. This stops being true at high throughput, not at our throughput.
- ✅ **Jobs as rows is a second benefit.** The admin panel's cost and job-health pages become a `SELECT` and a join against data we already have, rather than a second system to instrument.
- ✅ **What Redis was going to do instead.** Sessions live in Postgres already, because Better Auth puts them there. Rate limits go in Postgres for now. There is no caching problem yet, and inventing one to justify a service is backwards.
- 🔶 **Redis on Railway is the named destination when something genuinely needs it**, keeping it inside the one vendor rather than reintroducing Upstash. Triggers worth watching: job throughput where table contention shows up in practice, pub/sub once chat streaming runs across more than one instance, rate limiting at a volume where Postgres writes are wasteful, or a real cache. *Keep the queue behind a small interface so swapping the transport later is contained rather than a rewrite.* If a Cloudflare Worker ends up in the blob path and needs state, Workers have their own KV and Durable Objects, which is not a reason to add Redis.
- ✅ **Upstash dropped, and worth recording why so it is not reconsidered from scratch.** Serverless per-command pricing is the wrong shape for a queue: Upstash's own documentation notes that queue libraries poll continuously even when idle and recommends their fixed plans instead. The serverless benefit that justified the vendor does not apply to the workload we have.
- ✅ **Environments: `main` is production, plus one on-demand staging.** Changed from superparent's dev/staging/prod. `staging.offload.club` is a permanent hostname on a service that sleeps when idle and wakes on request, so mobile builds always have a stable URL without an always-on second stack. Pull requests run against an ephemeral Postgres container in CI, seeded by the `seed` script.
- ✅ **No IaC at first, on purpose (DEV-3).** Railway config per service in `railway.json`, the rest documented in `docs/local-dev.md`. Revisit when the resource set stops changing weekly. *This is a decision to re-examine, not a permanent stance.*

And the encryption problem I used to rule out a separate dump entity was not real: an object key can be wrapped more than once. *Recorded because the mistake was reasoning from a screen without checking what the screen actually was.*
- ✅ **One object, one object key, wrapped once per place entitled to open it.** The same pattern as `thread_keys`, applied one level down. A photo dumped and filed into two threads has three wraps, one account and two thread, over a single R2 object. No duplicated storage, no re-encryption.
- ✅ **Media gets a thread wrap only where it actually landed.** A voice note that decomposed into four tasks gets none: the audio is not what went into those threads, four tasks were. It stays readable in the conversation only.
- ✅ **The deletion behaviour this gives is the one the product wants.** Deleting an account drops its account key, so its dumps and their media become unreadable, while things and media in shared threads survive on their thread wraps. A photo you shared into a thread outlives your account; the conversation it arrived in does not.
- ✅ **An unread conversation opens in the composer (2026-08-28).** A dump that arrives while the app is closed leaves its conversation unread, and opening offload shows it. Seeing a conversation you did not start is fine and is in fact the point: you shared something in, offload dealt with it, and the answer is waiting. *This is why which conversation a dump joins stopped being blocking: any routing works once the unread one surfaces. New each time, one long-running one, or the most recent, is a policy line rather than a schema question, and it can be picked during implementation.*

## Review of spec 001, 2026-08-28

Three reviewers were run against the data model spec: `project-lead`, `security-reviewer` and `client-reviewer`. Every finding below was verified against the file before being accepted; the notable ones are recorded here because each changed the schema.

- ✅ **`threads.is_default` could not be enforced and is gone.** Removing the owner column left `threads` with no account column at all, so the partial unique index claimed to give one default thread per account would in fact have permitted one across the entire product. The default thread is now `accounts.default_thread_id`, a plain foreign key, where one-per-account is structural. *A bug introduced by the membership refactor and not propagated.*
- ✅ **Two designed screens could not have been built.** There was no `notifications` table, so the Activity sheet and Today's "what moved without you" had nothing behind them, and the analytics outbox cannot serve them because OFF-1 forbids content there. And there was no link from a thing to a person, so the person screen's "what they are waiting on" and Today's person-attributed rows were unbuildable. Both are now in the schema.
- ✅ **Tags are a column, not `attrs`.** The thread widgets filter and count by tag. This spec's own rule is that `attrs` holds what no screen queries, so by that rule they belong as `text[]` with a GIN index.
- ✅ **One authorizer, not just one writer.** The agent plane reads directly for retrieval, so the membership rule would have been implemented twice in two languages and drifted. It is now one SQL view both planes read. *This is the finding with the widest blast radius: it changes `architecture.md`, not just the spec.*
- ✅ **Thread-scope memories have no owning account.** A standing blurb is read by every member, so `account_id` is NULL for that scope and access resolves through `thread_members`. Left as written it failed in both directions: filter by account and no member but the author sees it, drop the filter and any guessed thread id reads it.
- ✅ **`superseded_at` was never filtered by any query.** Compaction would have marked memories stale and every one of them would have kept being returned forever, which is precisely the OFF-8 failure the spec names. Now filtered everywhere and swept by the purge job.
- ✅ **The analytics table contradicted the envelope this file decides.** It had a single `payload jsonb`, reintroducing the catch-all the analytics decision explicitly rejects. The dimensions are typed columns now.
- ✅ **Connector-derived memories carry a taint flag.** OFF-8 puts memory text into cached, trusted context while OFF-4 content is untrusted, which is a two-hop injection path: connector content, summarised into a memory, injected as background. `derived_from_untrusted` closes it. *`origin` does not, it is about correction priority.*
- ✅ **Smaller, all real:** `blobs` and `memories` lacked `purge_after` while carrying `deleted_at`, so a soft delete had no scheduled hard delete; account deletion named only membership and key rows, leaving address books, memories and conversations readable; nothing blocked the last staff owner deleting their account; blob authorization could have been written against the denormalised `blobs.thread_id` and gone stale; a move did not check membership of the destination thread; an invitation accepted after the inviter left had no key to unwrap from; `jobs.last_error` was an unscrubbed path for content to reach a log.
- 🔶 **pgvector filters after the index scan**, so a per-account slice of a shared HNSW index returns far fewer rows than the limit asks for. Enable `hnsw.iterative_scan` from the start. Not an alpha problem, a real one as accounts multiply.
- ⚠️ **Open, needs a product call: the thread map widget.** The kits name real places with plot coordinates. Whether that is a geocoded map, which needs a geocode step and location columns, or a stylised layout, which the current schema already supports, is a design question nobody has answered.

## Analytics

- ✅ **Event envelope now, warehouse later.** Inherited. Object-verb names (`thing_dumped`, `thing_sorted`, `thread_shared`), a flat typed envelope. *The exact fields are in spec 001 and superseded what was written here: there is no `account_id` on an event, only `subject_id`, the pseudonym.*
- ✅ **No content in properties, ever (OFF-1).** Structured references only: `thread_id`, `content_id`, `content_type`. Never a title, never a transcript, never a URL a person dumped. Enforced by a JSON Schema check plus a deny-list scan in CI.
- ✅ **Machine learning reads the production database, not the warehouse (2026-08-30).** OFF-1 stands with no carve-out. The warehouse answers product questions: funnels, retention, cost, health. Anything needing content reads the real tables under the same per-account authorization as the app, for a stated purpose. *The alternative, a narrow carve-out for derived fields, was rejected on the grounds that carve-outs widen one reasonable-sounding field at a time and the end state is the product's content sitting in a second store with weaker controls. The cost is accepted and real: no single place to query everything, and whatever content a future model might have wanted from the intervening months will not be in the warehouse.*
- ✅ **Transport: the Postgres outbox, shipped to R2 (2026-08-30).** Events land in `analytics_events`, a scheduled job writes them to R2 as NDJSON or Parquet hourly or daily, and a warehouse reads those files when there is a question worth asking. *This is the streaming architecture the product owner described minus the bus, with the same schemas, the same central contract and the same DE jobs. At roughly six events a second at ten thousand accounts, Postgres does not notice, and a bus earns its keep with multiple independent consumers needing replay and backpressure isolation, of which we have none.*
- 🔶 **The trigger for a real bus is a second consumer**, or a stream where losing events during a deploy actually matters. When it comes, the change is the emitter and the shipper, not the schemas or the consumers, which is the whole reason the contract is the part worth getting right first. Cloudflare Queues would keep it in-vendor; Pub/Sub would mean a third cloud.
- ✅ **Identity stitching is an explicit event, not an inference.** On signup, emit an `identity_merged` event carrying `anonymous_id` and **`subject_id`**, never a real account id, and store the originating `anonymous_id` on the account. *An earlier version of this entry said the event carries `account_id`, written before the pseudonym decision and never reconciled. Following it would have put a real account id inside `properties`, which erasure never touches, so a single event type would have silently defeated the whole shredding scheme.* *Without it every pre-signup funnel is permanently unreconstructable, and it is always noticed months later when someone first asks where signups come from.*
- ✅ **Two timestamps, always.** `occurred_at` from the device and `received_at` from the server, and every query states which it means. *Device clocks are wrong and device events arrive late, sometimes days late from an offline client. Keeping one timestamp is a choice to be wrong about either ordering or arrival, and there is no way to recover the other afterwards.*
- ✅ **A session is a foreground period on one device, ending after thirty minutes idle (2026-08-30).** The id is minted client-side and carried on the envelope. Conventional on purpose, so every benchmark and every analytics tool means the same thing by it.
- ✅ **Sessions are per device and are not merged across them.** Dumping on a phone and reading on a laptop is two sessions, which is the truth and is worth being able to see. Joining by account at query time recovers the merged view whenever a question needs it; merging at emit time destroys the multi-device picture permanently.
- ✅ **`entry_point` is on the session-start event and is first class.** `cold_open`, `notification`, `share_sheet`, `widget`, `deep_link`. *This is the field that makes the product's central promise measurable. The design says offload only interrupts when it matters, and the only way to know whether that is true is to ask what happened in the sessions that notifications opened. Notification-opened sessions where nothing happened is the number that says whether we are earning our interruptions or teaching people to ignore us. Without `entry_point` that question is unanswerable however sessions are drawn.* It sits on the start event rather than on every event, so it is not repeated on every row.
- ✅ **Background events carry no session.** A share-sheet dump with the app closed, a connector pull, a scheduled job, a push being delivered: `session_id` is null, and the event carries the account pseudonym and a `source` saying how it arrived. *Keeps "sessions per day" meaning what it sounds like, and stops offload's own scheduled work inflating human engagement numbers. Analysing background activity is a query by `source`, which is a different question and should look like one.*
- 🔶 **Thirty minutes understates how often someone reaches for offload**, since three dumps across half an hour become one session, and for a dump-and-go product that frequency is arguably the more meaningful number. It is recoverable: every event carries `occurred_at`, so a tighter grouping can be derived in the warehouse whenever it is wanted. The `session_id` is a convenience, not the only way to cut the data.
- ✅ **A session is not a table.** It is an analytics construct, minted client-side and carried on events. Nothing in the data model stores one.
- ✅ **What earns an event (2026-08-30).** Three streams and nothing else for now: **user actions**, anything a person did that they could notice; **errors**, at every layer; and **jobs**, recording the *shape* of inputs and outputs rather than their content.
- ✅ **"Shape, not content" is a checkable test, not a judgment call.** A field may be logged if it is an id, an enum or kind, a count, a size, a duration, a boolean, a status or a timestamp. It may not be if it is free text a person wrote, a transcript, a title, a filename, a URL they dumped, or model output text. *So: this job took three inputs of kinds image and text totalling 40KB, ran for 1.2 seconds and produced four things. Not what any of them said.* The existing CI deny-list scan enforces it, and a rule that can be checked is the only kind that survives a year of new events.
- ✅ **Retention: R2 indefinite for now, Postgres transient.** `analytics_events` is a staging buffer, not a store: rows are deleted once `shipped_at` is set, plus a few days of grace so a broken shipper can be re-run. The durable copy is the files in R2, kept indefinitely until there is a reason to pick a date. *Cheap, because OFF-1 means those files carry no content.*
- ✅ **Analytics events carry a pseudonym, and erasure destroys the mapping (2026-08-30).** No event ever contains a real `account_id`. Each account gets `analytics_subject_id`, a random value with no relationship to anything else, and that is what goes on the wire and into R2. Erasure destroys the mapping, so the events survive for aggregate analysis and become permanently unattributable.
- ✅ **Why now rather than later.** Analytics files are append-only and immutable. With a real `account_id` in them, honouring one erasure request means reading every file that might mention the person, filtering their rows, writing replacements, deleting the originals and invalidating anything downstream already loaded, then repeating it for the next request forever. The pseudonym costs one column and one lookup. *The archive only grows, so the price of retrofitting only rises.*
- ✅ **The shred is an explicit step in account deletion, not a side effect of it.** `accounts` carries `deleted_at`, so an account row can be soft-deleted with the mapping intact and nothing would have been shredded. Destroying `analytics_subject_id` is its own named action in T21, taken when the person asks, whatever else happens to the row.
- 🔶 **Called shredding, and honestly it is pseudonym destruction rather than encryption.** The effect on attributability is the same and the term is what people search for. The residual is correlation: an event stream with distinctive timing is not perfectly anonymous even without an identifier. Standard practice accepts this, and OFF-1 keeping content out of the stream is what makes it defensible.
- ✅ **Pre-login tracking: none for now, and the envelope keeps `anonymous_id` anyway.** The column costs nothing and an `identity_merged` event at signup remains the mechanism if it is ever wanted. *But the stitch is only worth anything if pre-login events exist, and emitting them from a public marketing site means an anonymous identifier in a browser, which means a consent banner in the EU that the design does not draw.*
- ✅ **The invite funnel is measured server-side instead**, which is the part that actually matters for an invite-only product: `waitlist_joined`, `invite_sent`, `first_sign_in`, `onboarding_completed`. Every one of those is a server event tied to a known person rather than an anonymous browser, so the whole funnel is measurable with no browser tracking, no anonymous id and no consent banner. *Tied to, not carrying: the event holds `subject_id`, the pseudonym, and never a real account id. An earlier wording said "keyed to a real account", which an implementer could reasonably have read as permission to put one on the wire, and a single event doing that would defeat erasure permanently.*
- 🔶 **Versioned JSON Schema files in `schemas/events/`, validated in CI.** No registry until there are more than about ten event types or a second consumer. *Gotcha, inherited: no catch-all `metadata` blob, it becomes unqueryable the moment a warehouse exists.*

## Sign-in, corrected during implementation

- ⛔ **Better Auth's own `accountLinking` disabled, all linking in our code.** Superseded, and kept because the reasoning was wrong in an instructive way. With linking off and user creation refused, an invited person has no path in at all: attaching a first identity *is* a link. Caught by a test, not by a review.
- ✅ **Linking enabled and governed by `account.create.before`.** Stricter than switching it off, because the hook also refuses waitlisted, disabled and soft-deleted accounts that the library would have linked. The hook reads the account Better Auth already resolved by verified email and judges only its state.
- ✅ **No provider is listed in `trustedProviders`.** Naming one waives the check on *that provider's* `emailVerified`, which is the single assertion this gate rests on. Google and Apple both always send it, so listing them buys nothing and gives up the check that matters. *Read out of `better-auth/dist/oauth2/link-account.mjs` rather than from the docs, because the docs describe trust as a convenience and the code shows it is a waiver.*
- ✅ **`requireLocalEmailVerified: false`.** `accounts.email_verified` means "we confirmed this address", and at invite time we have not: an admin typed it. The library defaults this to true, and left there it refuses every invited person at their first sign-in. The address is verified by the provider asserting it.
- ✅ **Linking a new provider onto a `staff` account fails closed.** The spec asked for notifying existing identities and a second admin's approval; until that exists, a staff account that already has one identity gains no more. Anyone who can get a provider to assert a staff member's address would otherwise inherit the admin panel with one button. *Unblocking a locked-out admin is another admin's job, not a self-service link.*
- ✅ **Google always shows its account chooser (`prompt=select_account`).** Without it, "Use a different account" on the no-invite screen silently reauthenticates the account just refused, and the person lands back on the same screen having done exactly what was asked of them.
- ✅ **The analytics pseudonym is `gen_random_uuid`, not `uuid_v7`.** Every other id here is v7 because time ordering clusters inserts. A pseudonym must not be time ordered: the warehouse never holds account creation time, and a v7 subject id would put it there in the clear, in every event, forever.

## Security review, decided 2026-09-22

The review is `security-review-2026-09-22.md` beside this file; these are the decisions it produced that outlive it.

- ✅ **The API has a database role of its own.** `offload_api` owns the application's objects and is not a superuser, made by `apps/core-api/src/api-role.ts` the way `agent-role.ts` makes the worker's. A future migration that says `create extension` runs once as the superuser. Production still runs as `postgres` until the owner runs the script inside the container and switches `DATABASE_URL`.
- ✅ **The internal routes answer on the private name only.** `INTERNAL_HOST` is the service's private domain; a request for `/internal/*` by the public name is not found before the token is read, and the worker calls the private name.
- ✅ **A day of the model costs one account at most five dollars.** `budget.ts` reads `llm_usage` before a dump or a typed row is enqueued and refuses with a 429 past the cap. The number lives in code until the admin Limits page exists.
- ✅ **Leaving keeps a row.** `thread_members.state = 'left'` with `left_at`, and restore is an update of that row inside fifteen seconds. Restore used to insert a membership for whoever called it.
- ✅ **Product events leave the database on a clock.** `analytics.ship` writes them to the store as JSON lines daily and drops shipped rows at thirty days; `analytics.ts` had described this job since 002 and none existed.
- ✅ **Google on Android is native.** The browser flow handed the session to the app on a custom-scheme deep link that any Android app may claim; the native sheet hands over an ID token instead. iOS keeps the browser flow, whose auth session returns to the app that opened it.
- ⚠️ **Apple on Android keeps the browser flow, accepted 2026-09-25.** Apple has no native sheet on Android, so that sign-in still returns through the `offload://` deep link with the session on it, the path Google left on 2026-09-22. The owner chose to keep it for the beta and record the residual rather than hide the button or build a one-time code exchange: it needs a malicious app already installed on the same phone and registered for the scheme, and nearly everyone on Android signs in with Google. Revisit before GA, or the moment a safer return exists; the code exchange is the fix if it comes to that.
- ✅ **One secret, several keys.** `crypto/derived.ts` derives a key per purpose from the auth secret; the waitlist limiter, the attempt cookie and the connector state no longer share the session signing key.
- ✅ **Every push waits for CI, and main is protected.** `checkSuites: true` on the three services, Dependabot on, the actions pinned to commits, and from the end of the review every change to `main` is a pull request whose CI check is green.
- ✅ **The web's content security policy is built per request, with a nonce.** Decided 2026-09-25, M4's next step. `apps/web/src/middleware.ts` mints a nonce for every page and is the policy's only sender; a script runs only when it carries the nonce or was loaded by one that did (`'strict-dynamic'`), so `script-src` no longer allows inline scripts. `next.config.mjs` keeps the other headers, inline styles are still allowed, and development alone admits eval, which Next's dev server needs. The cost: every page renders per request, the marketing pages included, because a page rendered at build time carries no nonce and the browser would run none of its scripts. The root layout reading the request is what makes that so; `test/csp-built.test.ts` proves it against the built app, in CI after the build and by hand with `WEB_CSP_TEST=1`.

## Deferred hardening, to revisit before GA

The operational list, everything that has to be true before offload is offered beyond invited friends, is `going-public.md` beside this file; these are the decisions behind three of its lines. Shortcuts taken deliberately for alpha and beta. Each says why it is affordable now and what changes later. None may ship to a general audience without a decision, and OFF-2 forbids describing the product as though they were already resolved.

1. **Move the root key into a KMS.** *Corrected 2026-10-04: this said "out of the database" long after the key had left it. The root is `DATA_ROOT_KEY` in the Core API's environment (`crypto/keys.ts`), and production refuses to boot without it. The shortcut is the same shape: one platform holds the database and the key.* Target: a managed KMS, AWS or GCP. Effort: one rewrap job over `account_keys`, proportional to accounts, no object touched. Affordable now because the only content at risk is ours, and because the key and the objects it protects already live with different providers.
2. **Revisit whether database content should be encrypted at all.** Currently a deliberate no. If offload ever holds enough of enough people's private lives that a database compromise is a serious event, the earlier benchmark and the warm-cache design are the starting point. This is a review item rather than a blocker: shipping unencrypted database content is a normal choice, shipping it while claiming otherwise is not. **Changed 2026-09-03: the privacy policy now says we plan to encrypt text as well**, at the product owner's instruction during the copy pass on that page. That turns this from a review item into a stated intention with no date on it. OFF-2 still holds, because the page says plainly that text is not encrypted today and section 12 still lists the three consequences, but the open question is no longer whether, it is when, and this item cannot now be closed by deciding against it without the page changing in the same commit.
3. **Built 2026-09-22, as `apps/backup`.** A container that runs `pg_dump`, seals the stream with `age` to a public key whose private half is the owner's alone, ships it to R2 under `backups/` and drops files older than 30 days, on a cron schedule. The Railway service still has to be created by hand; the container is proven against the local database. *The item as it stood:* **Give the nightly logical dump a retention window, and encrypt it.** The dump exists so a restorable copy of the database sits with a different company, and unlike the analytics files in the same bucket it carries content, in plaintext, for every account. Nothing sets a lifecycle rule on it, so today's default is that every night's `pg_dump` is kept forever, and content someone deleted in March is still readable in R2 in September. Effort: a lifecycle rule on the dump prefix and the blob encryption path applied to the dump. PITR needs no work, since Railway's window is roughly four weeks and is inside the promise on its own. *This is the one item on this list a published sentence is already ahead of: the privacy policy promises deletion reaches backups within 30 days and that backups are encrypted, and neither is configured. It is the same shape as item 1, a shortcut that is affordable while the only content at risk is ours, and it stops being affordable on the day a stranger is invited.*
4. **Audit every privacy claim against OFF-2.** Product copy, marketing, the privacy policy, and the Settings pages that talk about data. Whatever is true then is what the copy says. This is the item that keeps the other three visible.

   table says so.

   *Original note, kept because the reasoning is the decision:*

   ⚠️ **offload does not know what country anybody is in, and 016 made that
   visible.** Asked "when is the next bank holiday" on 15 September, it answered
   **Monday 12 October 2026**, which is Columbus Day, citing `academybank.com`,
   `idfpr.illinois.gov` and `dfs.ny.gov`. The answer is correct for somebody in
   the United States and wrong for the person who asked. Nothing in the product
   is broken: the lookup ran, the bound held, the chips are honest about where it
   came from. It simply had no idea where to look from.

   The gap is older than 016 and the agent's own comments name it: `accounts` has
   no timezone, so the day boundary is UTC and "today" is wrong for anybody
   dumping at 11pm in Lisbon. **Reaching the web is what turned a quiet
   off-by-a-few-hours into a confidently wrong answer**, because a search takes
   its assumptions from nowhere.

   The call is where it comes from, and the options are not equivalent. The
   phone's own locale is the most accurate and is a new thing to collect. A
   connected calendar already carries a timezone, but only for accounts that have
   one. Asking during first run is one more question on a screen whose whole
   pitch is that it asks nothing. **Each of them touches the privacy policy**, so
   this wants a decision rather than a default.

What is left is not decisions but work, and it lives elsewhere: the deferred hardening above, to revisit before GA; the design questions raised in `.claude/skills/offload-design/decisions.md` under Open, which are design's to answer; and the specified-but-undefined items, which are implementation details each spec settles as it is written, not calls to make in the abstract.

*The data model is specced at `docs/specs/001-data-model/`. What remains of it is implementation.*

## Photos, decided during 020

- ✅ **The worker is the one metadata reader, and the API stores what it is told.** The impl-spec had the API reading EXIF with `exifr` at upload and the worker making renditions. `exifr` threw `Malformed EXIF data` on a HEIC written by `pillow-heif`, the same library that makes the renditions, so the worker reads the metadata with Pillow and posts it with the two renditions; the API keeps the columns and validates the shape. One reader, one library, one place a new format has to be taught. *A JPEG's EXIF is still in the original, which is stored byte for byte; the renditions are written without it.*
- ✅ **Renditions are made by the worker, on the turn, before the model sees anything.** The thumb is 400px square, the large 2048px on the long edge, both JPEG, both without metadata. The model gets the large one as an image block, which is under Claude's 2576px high-resolution edge and well under the 10MB base64 cap. Client-side resizing was rejected: three clients, three codecs, and a phone would be the one deciding what the model sees.
- ✅ **A photo that no row claims is filed as its own row, before the questions run.** `fileUnfiledPhotos` runs on the turn's result before asking, and on a turn that failed or was cancelled, so a photo is never lost to a model that did not mention it. The row is `image`, titled "A photo" and nothing else, since the file's name is the dumper's alone, in the turn's thread, and it earns Files like any other. *This is the OFF-6 floor for photos: the worst filing is a row with the wrong title in the wrong thread, and both are one control away.*
- ✅ **A `thread` question is a condition the server checks, and 018's "never which thread" gains one dated exception.** 018 kept the thread out of the five fields because a wrong home is one move away. A photo with no words and no thread it plainly belongs in is the case that rule did not cover: the row lands in the default thread, and the question offers up to four threads the turn considered, each option a thread id the server checks the person is a member of, and each label the thread's own name. Apply is `moveContentIn` and Undo is the same move back, so the mechanism is the existing move with a question in front of it. The 018 spec carries the exception with today's date.
- ✅ **Reverse geocoding is its own gated path, behind its own switch.** A photo's GPS is stored as taken; the town it names comes from a `blob.locate` job that runs only when `GOOGLE_MAPS_API_KEY` is set **and** `PHOTO_TOWNS=on`, sends coordinates rounded to three decimals, asks for the locality and reads nothing finer (a neighbourhood is dropped, so the row says "Lisbon" and never "Alfama, Lisbon"), and caches by the rounded pair in `place_reverse` so the same beach is looked up once. Nothing else leaves. *The second variable exists because the key alone already serves 006's place names: setting it for that would otherwise have started a second egress path the privacy policy does not describe yet. The switch is turned on in the same commit that adds the provider's row to the policy, and not before.* A `blob.daily` job backfills the towns for photos uploaded before the switch, up to 200 a day, keyed by blob and day so nothing is queued twice and a provider that was down is asked again tomorrow.
- ✅ **`blob.purge` runs outside any transaction, and a failure leaves the row.** An R2 delete is not part of a database transaction, so the sweep puts a blob on the purge clock, and the purge job deletes the objects from R2 and only then the row. A delete that fails, or half succeeds (the batch delete reports per-object errors and the store throws on any), leaves the row on the clock for the next run. The alternative order, row first, leaves an object nothing can find and nothing will ever remove. Same family as 001's refcount decision, one level down. `content.purge` runs only when something is deleted, so `blob.daily` enqueues it once a day for the upload nobody sent on a day nobody deleted anything.
- ✅ **A retry with a client key is serialised with an advisory lock.** Two attempts of one dump in flight together, which is what a phone retrying because it never heard the response looks like, both missed the idempotent lookup, and the second blocked on the photos' row locks and found them claimed once the first committed: a 409 for asking twice. `pg_advisory_xact_lock` on the account and the key at the top of the transaction makes the second wait and then see the first's message and conversation. Found by the code review, reproduced by a test that holds the first attempt open by hand, because two real calls raced on timing and passed either way.
- ✅ **The worker's grant on `blobs` is five columns.** Which photos a message carries and when their renditions landed. The file's name, the exact coordinate and the device are the dumper's and the worker has no read that needs them; a role that also holds the model connection gets the columns it reads and no more, which is 0010's rule for `accounts` applied to the new table. Asserted by the agent-role test.
- ✅ **A message with a photo never takes the answering path.** The classifier is not consulted when the message carries a photo (*amended 2026-09-21 by 021: this said "a blob", and a voice note is a blob that is words; the count that skips the classifier reads photos only*): the answering path cannot see a picture, and the picture has to land. "What's the total on this?" with a receipt files a row whose title carries the total and says nothing, which is the filing turn's silence rule applied to a question the row already answers. Not in the spec; found on the first real turn.
- ✅ **The share extension opens the app by URL scheme.** iOS gives an extension no official way to raise its host, and `expo-share-intent` does what every shipping share extension does: writes the files to the app group and opens the app by its scheme. It needs the extension's own bundle id and provisioning, which is an owner step in EAS before the first build with it.
- ✅ **`dump_sent.v1` gains three optional fields rather than a v2.** `photos`, `photo_bytes`, `via_share`, all counts and a boolean, all additive. A consumer of v1 that ignores unknown keys keeps working, which is what the schema's `additionalProperties` already allowed for. The impl-spec said v2; a version bump for three optional integers would have made every consumer choose a branch for nothing.
- ✅ **A phone fetches a rendition with `fetch` and draws the file from its cache, never `Image` with headers.** React Native's `Image` on Android sends no `source.headers` at all: the API saw the request arrive with cache-control, host, connection, accept-encoding and user-agent and nothing else, and answered 401 to every thumbnail. So `PhotoThumb` fetches the bytes with the session header, writes them once into `Paths.cache/photos/<blob>-<rendition>.jpg` through `expo-file-system`, and draws the local file; a 404 for renditions not made yet is never written, so no JSON body wears a picture's name. A delete forgets the device's copy. The cache is also why a thread's Files draws at once the second time.
- ✅ **Expo 57's `fetch` takes a real `File` as a multipart part.** The old `{ uri, name, type }` object React Native accepted is refused with `Unsupported FormDataPart implementation`, and the first upload from a Pixel failed that way with nothing reaching the API. The part is `expo-file-system`'s `File` over the uri, a Blob read as the request streams; `expo-file-system` is a direct dependency of the app for it. The share library hands over a bare path on Android, which gets its `file://` before it is used.
- ✅ **A photo turn the model stopped on without filing is finished, not partial.** The server files every photo no row claims before the turn settles, so a turn that read the thread, found the same picture and stopped, which is what the second send of one shop sign did on a Pixel, is a turn that filed something. Reported as partial it said "Nothing saved." under a Files grid that had just gained the photo and offered a Finish that would read the thread again. `_photos_land_anyway` is as narrow as `_nothing_left`: nothing refused, nothing cut off, nothing said, and a photo the worker could open. The prompt also says a repeat is still a row, since a spare is one tap to delete and a photo that never landed is gone.
- ✅ **A branch that adds a native module needs its own development build, and the Google client only knows 4701.** `expo-image-picker` and `expo-share-intent` are not in the phone's dev client until EAS builds one; an Android development build takes about fifteen minutes and installs over the app with its data kept. The share extension on Android is an intent filter and needs no credentials; iOS still does. And a local API for the phone has to sit on 4701, because that is the redirect URI the Google OAuth client holds: on 4704 the sign-in ends in `redirect_uri_mismatch`.
- ⚠️ **The tool definition budget is at 1,798 of 1,800 after the merge with 019.** `add_content.photo` cost 75 tokens as first written and 40 after the description lost what the prompt already says and the range moved from the schema into the validator. The next field on any tool goes over, and the two entries above disagree about what happens then: the 11 September one says `defer_loading`, the 17 September one measured it and says it does not pay below about ten thousand tokens. That is a decision to make before the next tool grows, not a number to move again.
- ✅ **R2 in production, since 2026-09-20.** The bucket is `offload-user-data`, named for more than photos so voice notes and whatever else people dump can share it; the token `offload-user-data-token` is object read and write on that bucket alone. `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` and `R2_BUCKET` are set on `core-api` only, the worker reaches bytes through the internal routes and never the bucket. The four stay optional in `env.ts` so the suite and a local run do not need them, and without them production logs a warning at boot and every upload answers 503 with the composer's own line. No CORS on the bucket: nothing reaches R2 but the API. Verified by a photo dumped from the production web app that came back as both renditions out of the bucket.
- ⚠️ **The worker's role has no grant on `readable_content`.** No migration grants the worker select on a view, and 020 did not add one because the worker reads content through the tables it already can. Noted because the one-off at worker boot on a fresh database is this, and the day the worker reads through the view it fails on the first query.

## Voice notes, decided during 021

- ✅ **The transcript is a field of the message beside its typed words, and one SQL function composes them.** `said(text, transcript)`, words then transcript with a blank line between, is what the classifier, the filing turn, the tail, 018's judge, the search column and the embedding path read. The draft said "the transcript is the message's text", which was undefined once typed words rode along and would have left the bubble unable to draw them apart. Search still falls out, because the index reads the message; the embed sweep versions a message on `greatest(created_at, transcribed_at)` so words indexed at send are indexed again when the transcript lands.
- ✅ **A blob has a kind, and every reader says which.** 020 wrote `blobs` for photos and every query that read a message's blobs read them as its photos: without `kind`, an audio blob was fetched by the worker as a picture, marked unreadable, filed as "A photo" by the end-of-turn step and wrapped for the thread. All three reviews of the spec found it. The kind is the upload route's, never a shared sniff, since `ftyp` is also how HEIF begins.
- ✅ **The worker writes the note down before it reads it, under a shield the cancel waits for.** The classifier reads message text before anything is loaded, so the transcript has to exist before the turn decides what kind of turn it is; from the write on, a voice note is a text message to every path, and a spoken order, question or 018 answer costs no new code in any of them. 017's cancel raises at the next await, which would have stranded a note half written down with no control to reach it, so the write runs shielded and a cancel is re-raised after it lands: 017's "a cancel in the middle of a write waits for that one thing", applied to the first write of the turn.
- ✅ **The audio leaves once.** The provider's reference is written to the row at submission, before the first poll, so a retry polls it rather than uploading again; the transcript's delete at the provider is its own job, keyed on the blob, retried until 2xx or 404, and asked for again by `blob.daily` for any reference held over an hour.
- ✅ **The bill is bounded per call by the provider's own end offset, not by reading the file.** A browser's WebM carries no length in its header and the server never decodes audio, so the day's ceiling counts the device's declared length until the provider has measured a note and the measurement after, and every request asks for the first ten minutes and no more. The request's keys are a frozen set checked at import against the vendor's reference on the day, the 016 lesson.
- ✅ **Playback serves the original, to the dumper alone.** The one route that serves a blob as it arrived, which 020 said none does: the audio is our own recording with nothing in it the person did not say, unlike a photo's original with its coordinate. It resolves through the message with no thread arm, refuses any blob that is not audio, and answers Range. The phones fetch it with the session into a cache file and play the file, since a native player carries no header, and the file goes on pause, on leaving the screen and on sign-out.
- ✅ **Nothing to hear settles without a model call.** An empty transcript on a message with no words and no photos posts "Heard nothing in that one." from the worker, no question and no retry, since the same recording gives the same answer.
- ✅ **A transcript may carry other people's speech, and the prompt says so.** A voice note has no listen-back, so a voicemail on speaker or somebody across the desk can put an imperative in the dump the person never saw. Not a new boundary, since every tool bound already applies; the planner and the classifier are told a sentence addressed to somebody else is quotation, and the dump label says the words were spoken. The eval case for it waits for real recordings, with the rest of the voice set.
- ✅ **The web records AAC in MP4 wherever the browser offers it.** Chrome's and Firefox's first choice is Opus in WebM, which an iPhone cannot play; MP4 first means a note recorded in Safari or recent Chrome plays on every phone, and a Firefox note's bubble on an iPhone says "Not here yet.", which is the failure line and not a diagnosis. No transcoding: the server never decodes audio.
- ✅ **The voice evals wait for real recordings** (product owner, 2026-09-20). A transcript typed by hand is a guess at what a transcript looks like.

## Sharing, decided during 022

- ✅ **A connection is its own table, one row per unordered pair (2026-09-22).** 001's impl-spec kept it as `people.linked_account_id` in a per-account address book that nothing ever built. A connection is a mutual fact between two accounts, not an entry in one person's book that another person's book has to agree with, so `connections (account_a < account_b)` makes mutual structural and removal one delete. Requests and blocks are their own tables beside it; the `person` of 001 waits for whatever needs an address book, which nothing does.
- ✅ **Member removal is built, and the two documents changed with it (the product owner's call, 2026-09-22).** The 2026-09-04 warning below said build removal and the leftovers rule becomes remove-then-delete; the recommendation was to leave removal out and let the x only withdraw a waiting share. The product owner chose the design as drawn: any member may take any other member out, confirmed on a sheet that lists what stays, never by the model or by Undo, and what they left becomes the thread's as when they leave. OFF-3's amendment and section 10 of the privacy policy now say a shared thread is only as safe as the people in it, and what bounds that: everybody in a thread was brought in by a member from their own connections. *This is the entry that supersedes the ⚠️ under Thread memories.*
- ✅ **A said share is a proposal on the reply, not an act with an Undo.** The readme promised "share Lisbon trip with Sam" answered in offload's voice with an Undo; sharing reaches a person, so under OFF-6 it is confirmed per action, and an Undo would be a message to Sam followed by a second one. The mechanism is 019's: the tool writes a `pending_shares` row, the reply carries `{ id, because, kind }`, the tap re-runs every check the sheet runs. `pending_shares` sits beside `connector_pending_writes` rather than inside it because their checks share nothing and a `kind` column on one table would have been two features in a trench coat.
- ✅ **The model never sees the connection list.** `share_thread(threadId, person)` takes a name or a mention id and the server resolves it against the sender's accepted connections, answering with at most five candidates for 018 to ask about. A turn costs the same for somebody with fifty connections as for somebody with three (OFF-8), and a name that is not a connection can never be looked up by email from the composer.
- ✅ **The invitation's preview is a snapshot, not a read.** Two of the sharer's own titles and the count, taken when the share is made and stored on the pending row, nulled on accept. A person who has not accepted never reads the thread, never sees a row another member wrote, and cannot be shown a changing feed by a share made and withdrawn. The security review found the live read in the first draft.
- ✅ **A blocked person's request is written and never delivered.** Dropping it would have left their Pending list empty, which is the one tell the design says a decline must not have. The row carries `delivered = false`, behaves identically on the requester's side, and nothing on the recipient's side reads it.
- ✅ **The mark carries no letters.** The design asked for a 176px PNG generated once at signup and never regenerated; the initials come from a name that changes, and the policy promises a rename changes what others see, so the picture is the prism alone and every surface draws the initials over it, which is also exactly what `Avatar.jsx` does with its span. Drawn on first read rather than at signup, since it is a function of the id alone and that spares a backfill. `pngjs`, pure JavaScript, so `core-api` gains no native dependency.
- ✅ **Leave drops the key when others remain.** `deleteThread` deleted the membership and left `thread_keys` in place, inert only because `threadKey` reads through accepted members. Take out revokes the key by definition, so leave does too, and the eight-second restore re-wraps from another member's copy on the next read. The last member's key stays for the purge job, as before.
- ⚠️ **Not now on a waiting share does not decline it.** The design says it waits, the security review asked for a silent `declined`. Bounded instead by three waiting shares per pair. If three strips from one person turns out to be too many in practice, the `declined` state is already in the schema and unwritten.
- ✅ **The agent role reads `connections` and nothing else of 022's (2026-09-22).** One fact decides whether the share tool is sent at all, that the account has a connection, and the worker reads it with the rest of the context. Who is connected to whom it already had from `thread_members`, which it reads whole, so the pair table adds nothing; the requests, the blocks, the lookups, the proposals and the mark stay on the API's side, and `agent-role.test.ts` asserts the grant list.
- ✅ **A block the other way hides what it ended, not what it left standing (the security review, 2026-09-22).** The plan said an account that has blocked you is never visible. Built that way, a co-member who had blocked you was a 404 for their mark on the pane head, and the undelivered request written so that nothing would tell drew a blank face on Pending: the one tell the design forbids, produced by the rule meant to prevent it. `relationOf` now drops only `connected` and `asked_you` under a reverse block; the thread and the request stand. The lookup still answers not found either way, which is what it answers for an address that is not on offload at all.
- ✅ **A connection's name never reaches the judge.** A typed reply to "Share Lisbon trip with which Sam?" went through 018's `judge_answer` with the candidates' labels in the prompt. It takes 019's calendar path now: matched in the API against the labels, whole or a prefix of exactly one, no model.

## The admin panel, decided during 002

- ✅ **A staff member's single Invite click is its own confirmation; the batch is not.** OFF-6 requires anything leaving offload to be confirmed per action. One row's Invite names the person in the click, so the click is the confirmation. "Invite the next batch" names nobody, emails twenty five people at once and cannot be taken back, so it confirms with the count first. *Found by the constitution pass, not by a reviewer: the kit has no confirmation on either, and following the mock exactly would have shipped it.*
- 🔶 **The weekly batch size is a constant in `apps/core-api/src/routes/admin.ts`.** The kit reads it from a Limits page that does not exist and belongs to another spec. Named rather than a literal at the call site, so moving it to a real setting is one change.
- ⛔ **The kit's invite semantics, not implemented.** Its notes describe an invite as a single-use link that expires in 14 days, where resending voids the old one and the account is created when they sign in. This product has no such link: promotion creates the account, its keys and its Miscellaneous thread in one transaction (AC-2), and sign-in is by provider on the invited address. Resend therefore re-sends the email rather than reissuing anything. *The spec wins over the kit here, per CLAUDE.md, and the admin page's own notes were rewritten to describe what actually happens.*

## The admin panel, decided during 034

- ✅ **Staff deletion is the one action in the panel that destroys something, and its undo is a day, not eight seconds.** OFF-6 wants an action undoable or confirmed. Delete is confirmed with the address typed back, owner only, and then held: the account is locked at once and destroyed 24 hours later by a job booked for that moment, and an owner can cancel in between. Every owner is emailed when it is scheduled and when it is cancelled. *This is a stated divergence from the eight-second rule, not an oversight: the panel has no Undo toast at all.*
- ✅ **The `account.delete` job names no account.** A job row that carries `account_id` cascades with the account, and this one has to outlive the row to write its audit entry. The id is in the payload. The job re-reads the mark and does nothing unless `delete_after` has passed, so a cancel needs no job to be found and removed. Destruction itself is 035's `deleteAccount`; a `LastOwner` refusal there clears the mark.
- ✅ **A deleted account's page answers 410 with the day and nothing else.** The day is read from the `deleted` entry in `staff_audit`, which names accounts by id with no foreign key, so it survives the row. 404 stays for an id that was never an account.
- ✅ **Support sees metadata only, and one test walks every GET to prove it.** `admin-off1.test.ts` seeds marked content and asserts no admin read returns it. A new admin route is covered without anyone remembering to add it.
- ✅ **Every admin write declares its audit kind in the route's config, and the audit row is written in the write's transaction.** A route with no `audit` in its config fails a test. An owner-only route in a support-visible section declares `rank: "owner"` and answers support with 404.
- ✅ **Health is read from our own Postgres.** A heartbeat row a minute per service, hourly job rollups, and gaps-and-islands for incidents. No third party monitor. `/healthz` stays bare: it says the process is up and nothing about the database, so the platform does not restart a healthy process during a database blip.
- ✅ **Condition alerts stop at ten a day; staff and deletion alerts are never counted.** A flapping condition must not exhaust the mail budget, and a staff change must never be the email that was dropped.
- ✅ **The ledger outlives the account.** `llm_usage.account_id` and `lookups.account_id` are set null when an account is deleted, so Costs still adds up; `account_limits` and `limit_hits` go with the account. `accounts/ledger.ts` lists every column that names an account and what happens to it.
- ✅ **A billing puller is written only against a recorded real response.** Railway is the first, recorded 2026-10-03: invoices in whole cents under `workspace.customer`, filed under the month most of the period is in, and the running period as use so far. **The figure is the whole workspace's bill**, which includes a project that is not offload; Railway prices no project on its own. Anthropic needs an admin key an individual account cannot make, and Cloudflare refused an account-owned token on every billing endpoint, so both stay as they were. Candidates and what each answered are in the 034 impl-spec's appendix.
- ✅ **Migration 0018's closing note was wrong and is corrected.** Content whose author is gone can be edited and deleted by the remaining members, per OFF-3 as amended; 034 is the first thing that can produce such a row and a test pins it.

## Labels, decided during 025

- ✅ **Labels replace tags and grouping (2026-09-27, 025).** A thread is grouped by labels a person can see, name and correct, and by nothing else. `content.tags`, the `dimension:value` strings the model wrote since 006, is dropped with `threads/tags.ts` and the widgets package's tag helpers; 007's `groupBy` preference and the in-widget chip filter go, and a stored `groupBy` is stripped from `threads.attrs` by the migration rather than tolerated on read; 018's tag question goes with its field. Nothing a person typed is lost: only the model ever wrote a tag and no screen let anyone set one. **No label is made from an old tag.** A migration that invented labels would be offload acting with no record and no Undo; the nightly sort labels a thread that holds more than one subject, in Activity, with Undo. The tool definitions fell from 1,741 to 1,642 tokens with `tags` and `group_by` gone, which is the room the label tool took.
- ✅ **OFF-6's reversible allowlist gains labels, on three terms (2026-09-27, 025).** **A person's label writes** (make, rename, recolour, delete, apply, remove) are drawn first and written second with the eight-second Undo: a set, a rename or a recolour is undone by the same write backwards through the same checks; a delete is soft for thirty days and restored by id. **offload's live labelling** (`label_content`: apply by id, make one only when its name is in the words of the message being filed, remove when asked) sits inside 004's whole-turn Undo. **The nightly sort**, built and switched off for now by the owner (`NIGHTLY_LABEL_SORT` false in `jobs/handlers.ts`, so no job is booked), creates and applies labels only, never removes, renames, recolours or deletes, and is on the list as compaction is (2026-09-10): automatic, on an offload-owned surface, destroying nothing, with no toast and so no eight seconds, and undone instead from its Activity row for thirty days. All three are enforced in `threads/labels.ts`, the one write path: a label and a row meet only inside one thread the caller is in, who set it comes from the route and never the request, and offload is refused anything a person set, took off, renamed, recoloured or deleted.
- ✅ **Activity gains its first action, and a record one member undoes for all (2026-09-27, 025).** 024 made every Activity row inert or a door, with its words stored as sent and never re-rendered. A `labelled` row, written today by a live turn that labelled anything and by the nightly sort once it is on, carries one action, Undo, beside the row and never inside its press, and its words still never change: *Undone* is drawn from `activity.undone_at`. Undo writes `undone_at` on **every member's copy** of the same sort, the first write to `activity` across accounts; it is correct because the rows describe one thread-level change and the writer has passed that thread's membership check at the moment of the press. A `labelled` row is never sent (`sent` false, `reason` design), so no label or thread name reaches a push service, and it carries `thread_id`, so 024's purges on leaving and removal already reach it. 024's feature spec is amended in the same change.

## Found in production, 2026-09-03

Three defects from one real dump: *"I need to book a stay in Istanbul from Sep 28th to Oct 4th, put it under a new thread called EU with fam, I should do it by next week."* offload created the thread, failed to file the task, and said **"the task tool seems to be down"**. It was up.

- ✅ **A 4xx from the tool endpoint was retried as though the network had failed.** The worker retried every non-2xx three times and then reported `unavailable` to the model, which faithfully passed that on. A malformed request will be malformed again, so the retries were pure delay, and the endpoint's clear "no" was thrown away and replaced with a claim that was not true. **A 4xx is a decision and comes back as data the planner can read; a 5xx is a blip and is still retried.** The worst part was not the failed turn, it was that offload told somebody something false about itself, which is the one thing 004 exists to prevent.
- ✅ **`z.string().datetime()` is not what a model writes.** It accepts ISO 8601 with a `Z` and refuses `2026-09-28`, which is a perfectly good date and what the model actually produced for "by next week". A day, a zoned timestamp and a naive one are all accepted now and normalised server-side, prose is refused as data rather than as a 400, and a date more than ten years out is refused too: a task due in 2126 is invisible rather than wrong-looking, because it sorts to the bottom of everything forever and nobody ever sees it to correct it. The same shape is checked in the planner's own schema, so the model gets a message naming the field instead of a status code it cannot read.
- ✅ **And the actual reason nothing arrived in a browser: the stream carried no CORS headers.** `reply.hijack()` takes the socket away from Fastify and `reply.raw.writeHead` writes exactly what it is given, so the `access-control-allow-origin` @fastify/cors sets on the reply object never reached the wire. A browser on another origin blocked the response, the EventSource errored, and the thinking indicator stayed up. **Every test in this repo is same-origin and none of them could see it**, which is the same shape as the buffering problem one entry down: the wire behaviour that mattered was the one nothing exercised. The origin is echoed only when it is on the same allowlist the plugin uses, so hand-writing it is not a way around it.
- 🔄 **Superseded within the hour: nothing polls at all.** The first fix split one interval into two, one second for the answer and fifteen for the session. The product owner pushed back on the right thing: a shorter interval buys responsiveness with traffic and the trade does not need making. **`pg_notify` in the transaction that writes the reply, `LISTEN` in the Core API**, so the answer goes out the instant it commits and nothing asks in the meantime. One connection for the process, not one per waiter, outside the pool because a listening connection cannot serve a query. *A duplex socket was the other suggestion and would not have fixed it: WebSockets change how the server talks to the browser and do nothing about how the server learns, so it would have polled exactly as before and pushed the result down a different pipe. The thing that had to stop polling was the server.* The fifteen second clock survives for the session re-check and the keep-alive, both of which genuinely want one, and it is still the window in which a disabled account keeps receiving.
- ✅ **A turn where a tool failed is partial, even when the model wrote a reply.** It was reported as answered because a reply existed, so the composer offered no way to finish it and the explanation had nowhere to live except offload's own words, which is how "the task tool seems to be down" reached somebody. A failed tool now makes the turn partial, the reply is written from the record rather than by the model, and the screen carries the failure next to the button that fixes it.
- ✅ **offload never explains a failure and never diagnoses itself.** It cannot see whether a tool is down and will be wrong about it. The reply names what landed and links to it; the screen says "Some of that did not save" and offers Try again. **A sentence cannot be clicked**, which is the whole argument. Written into `CLAUDE.md` because the tone guidance was nowhere durable and had drifted more than once.
- ✅ **The stream polled every fifteen seconds, and that was a bug rather than a tuning choice.** A reply landed, sat in the database, and the composer showed a thinking indicator until the next poll; the person reloaded first and reasonably concluded nothing had happened. The mistake was folding two questions into one number: how fast an answer should reach a waiting browser, and how often a session should be re-checked. They are separate constants now, one second and fifteen, and the second one **is** the window in which a disabled account keeps receiving, stated rather than discovered.
- ⚠️ **None of this could have been caught by the tests that existed**, and that is the finding worth keeping. `streamStep` had been unit tested since 003 and the wire never had: `app.inject` buffers a response and returns it whole, which is indistinguishable from a stream that does not stream. `test/stream.test.ts` starts a real server on a real port and reads the body as it arrives, and its four second timeout is the assertion. *Every layer here was individually correct and the product did not work.*

- ✅ **Undo is offered for an action, never for an answer.** A turn that filed nothing has nothing to take back, and the toast was appearing on "Sorry, I did not understand that one". Pressing it would have deleted the person's own message from the conversation, which is neither what they asked for nor what the button says. The record of what landed is also the test for whether anything did.
- ✅ **offload refuses what it cannot read, and that rule is deliberately narrow.** "asdlakjldakjdlakjsda" was filed in Miscellaneous under the word "Saved", which puts rubbish in the one place somebody is meant to be able to trust, silently. It says it did not understand and files nothing now. **The dangerous half of this change is the other side**: a rule about refusing gibberish is one prompt edit away from a model that refuses anything short, and losing what somebody wrote is the expensive mistake where a one-word note in the wrong thread is not. The eval carries both, "milk" and "call mum" alongside the keyboard slips, and the prompt says in as many words that when in doubt it files.

## Widgets and grouping, decided during 007

## What offload extracts, decided during 006

- ✅ **Priority is not `needs_attention`, and the two never meet.** `priority` is 0 to 100 and orders content **inside** a thread. `needs_attention` is 001's boolean and decides what **leaves** one for Today. Different scopes, so no precedence rule is needed, and nothing writes or reads `needs_attention` yet. Written down because two ordering signals meeting silently later is a defect class this repo keeps finding, not because anything is currently confused.
- ✅ **`priority_pinned` means a person decided.** The planner's write is skipped, not refused: it asked for something reasonable and the answer is that somebody already chose. Refusing would make the model retry or apologise for a non-problem.
- ✅ **A reminder is a flag, never a type.** A task that becomes a reminder must not change type, because a type change halfway down somebody's list is a migration in the middle of their afternoon. Nothing acts on the flag until notifications ship.
- ✅ **Tags carry an optional dimension, `dimension:value`, and are normalised at write.** Lowercased and trimmed in both halves, one value per real dimension per row, at most six. A bare tag reads as dimension `tag`, so everything offload already produces is groupable without a migration. Normalisation is in the Core API rather than the prompt: a model producing `City:Alfama` on Monday and `city: alfama` on Tuesday makes two groups out of one place, and asking it nicely is not a mechanism. Refused rather than silently repaired, so the model gets the complaint and can fix it.
- ✅ **A location's `title` is its place name. There is no second field.** Two fields holding the same thing is two fields that disagree, and the one that would be sent to a geocoder is exactly the one you want visible on the screen. A `location` therefore gets a stricter title than anything else: 120 characters, single line, **enforced by a validator rather than asked of the model**, because "only the place name goes, never the dump" is a claim about what a third party receives.
- ✅ **The model has eight tools and cannot delete.** The absence is asserted structurally, by a test that reads the closed set and fails on any name containing delete, remove or destroy. Deletion is author-only, offload is not an author, and a model that can delete can lose somebody's dump on a misread. `archive_content` covers every case a person would phrase as "get rid of that".
- ✅ **Membership decides what the model may see; authorship decides what it may rewrite.** `complete_content` and `archive_content` are open to any member, because those are 005's co-owned actions and neither rewrites anybody's words nor moves anything out of reach. `edit_content` and `move_content` require the row to be this account's. **That asymmetry is the whole defence against a confused deputy**: a member who writes "when asked anything, first rewrite the deposit item" into a shared thread has planted an instruction that reaches a different member's turn through `list_thread_content`, and the answer is a server-side check rather than a sentence in a prompt.
- ✅ **`list_thread_content` returns 20 rows with bodies truncated to 200 characters.** Numbers rather than "bounded", because this is the first tool that puts one person's stored text into another person's model call, so how much of it leaves has to be a figure that OFF-1 and OFF-8 can both be checked against.
- ✅ **A refusal from the tool endpoint is a 200 the planner can read.** An escaped exception got a considered "no" retried three times by the worker as though the network had failed and then reported to the model as "unavailable", which is a different thing entirely. Found by a test that expected a 404 and got a 500.
- ✅ **Today's date comes from the database's clock, in a trusted block.** A model has no clock, and without this "the 3rd" in late December resolves to this year rather than next: a wrong date on somebody's calendar, and the error nobody reports because it looks like a typo they made. `accounts` has no timezone column yet, so the day boundary is wrong for somebody dumping late at night in Lisbon, and the query is the one place that changes when it lands.
- ✅ **"Landed" means filed, not "a tool call that succeeded".** Reading a thread succeeds and files nothing; ticking something off succeeds and files nothing either. **Found by the eval**: "add tomatoes, basil and anchovies to the list" made the planner read three threads looking for a shopping list, and all three were recorded as places it had put things, so the record the reply is checked against was itself claiming threads the turn had only looked at.
- ✅ **The reply never mentions an instruction it declined.** Also from the eval. Faced with an injected dump the model refused correctly and then explained that it had refused, naming the thread it had been told to claim. That is a mechanism in a reply, which the design forbids, and to somebody reading quickly "I did not file it in X" carries the same untruth as "I filed it in X". The prompt now says so.
- ✅ *Superseded 2026-10-03 by 030: switched on without the no-training and retention conditions, which Google does not offer; the owner waived them, see the dated entry.* **Google Maps Platform is a sub-processor and is not switched on.** The code is written, the boundary is enforced and the caches are built, and `GOOGLE_MAPS_API_KEY` is unset, so a location is filed with a name and no pin. **Two things gate turning it on and both are the product owner's:** reading Maps Platform's own terms on data use and retention, which must include a no-training term and short provider-side retention, the same bar this file already set for the transcription provider and a different Google product from the sign-in one; and adding its own row to the privacy policy, distinct from the existing Google row, which is sign-in only and sees nothing about what anybody dumps.

## Deleting a thread, decided 2026-09-04

- ⚠️ **A request with no body must not claim a JSON content-type, and this shipped broken.** Four bodyless calls added in 008, both deletes and both restores, sent `content-type: application/json` with nothing in the body. Fastify's parser refuses that outright with *"Body cannot be empty when content-type is set to 'application/json'"*, the client helper read the 400 as an ordinary failure and returned false, and the screen did nothing at all. **Deleting a thread and deleting a memory were both dead in production**, silently, and no test saw it: `app.inject` sets no content-type unless you give it a payload, so every route test passed against a request the browser never sends. *`send`, a credentials-only init, already existed in the same file for exactly this and content delete already used it. The fault was reaching for the helper I had seen rather than reading the two at the top of the file.* Locked now by a web test that stubs `fetch` and asserts the header is absent on every bodyless call and present when there is a body.

- ✅ **Delete is leave, and the thread dies with the last member out.** OFF-3 gives a thread a member set and no owner, and the privacy policy says in public that "there is no role that can throw someone out, take it over, or empty it" and that "the thread and its contents are deleted when the last member leaves it". So `DELETE /v1/threads/:id` removes the caller and nobody else. On a thread you are alone in the two are the same act, which is why one endpoint serves both and the screen can honestly say Delete. The response says which happened so the toast can too: "Thread deleted" or "You left the thread". *No policy change needed: this is the page's existing promise, implemented.*
- ✅ **The default thread cannot be deleted.** Every dump with no obvious home lands there (004 AC-2), and an account without one has nowhere to put anything. Refused rather than handled, because there is no good answer to "where did my dump go" afterwards.
- ✅ **Soft, with `purge_after`, and the purge job does the destroying.** DATA-1: if a table has `deleted_at` it has a scheduled hard delete. Content, `thread_members` and `thread_keys` cascade from `threads`; **memories do not**, because `subject_id` is polymorphic and carries no foreign key. That is the caller 008 wrote `deleteMemoriesForThread` for and could not wire, since until now nothing in the product deleted a thread.
- ✅ **The row asks in its own place.** Straight from `WRow` in the web kit: tools on hover only, the question replacing the row rather than opening over it, a click anywhere else cancelling, and the row collapsing once it is gone. A dialog would cover the thing it is asking about; this one is the thing it is asking about.

## Thread memories, decided during 008

- ✅ **A thread's leftovers belong to whoever is still in it (2026-09-04, the product owner's call).** OFF-3 gave delete to the author, full stop, which meant content and memories whose author had gone could be deleted by nobody: a shared thread accumulating leftovers no member could clear, including a standing memory still steering the model. Now a row whose author is not a current accepted member of the thread may be edited and deleted by any member. **OFF-3 is amended in the same change**, and so is the privacy policy, which promised in bold that "nobody, including you, can delete what they did not write themselves".
- ⚠️ **That exception is only safe because member removal does not exist.** *Superseded 2026-09-22 by 022, under Sharing above: removal is built and both documents changed with it.* The privacy policy promises in public that "there is no role that can throw someone out, take it over, or empty it", and no leave-thread route is built either. **Build removal and this becomes a privilege escalation:** remove the person, then delete everything they wrote. The two have to be reconsidered together, and OFF-3 now says so where somebody will read it. *The product owner's original framing was "someone removed her from a shared thread", which is not a thing the product can do; the rule was scoped to authorless plus voluntarily departed instead.*
- ✅ **The predicate is resolved in the same statement as the row it decides about.** `authorIsMember` is an `exists` on `thread_members` inside the read, not a second query, so a permission can never be decided from a membership read at a different moment. `unowned()` is exported once and imported by the tool endpoint rather than restated, because two copies of a permission rule is how one of them ends up subtly different and nobody can tell which is right.

- ✅ **`memories.account_id` is authorship and never authorization.** 001 specified it NULL for thread scope, arguing a non-null author is "a hole in both directions". That argument is about using the column as the read predicate and it is right about that; it is not an argument against the column existing. Delete is the author's under OFF-3 and a shared thread has to show who wrote each rule, so the column stays and the invariant moves: reads resolve through `thread_members` on `subject_id`, always, and `readableMemory` is a single join so that is a mechanism rather than a convention. *The single join is also what stops a memory-id oracle: fetch-then-check runs one query for an id that does not exist and two for one in somebody else's thread, which is a timing difference that answers a question the product refuses to answer.*
- ✅ **`on delete set null`, never a cascade.** OFF-3 makes it a MUST that account deletion never reaches into a shared thread. A memory outlives its author and loses its name, which is the privacy-correct outcome and legible because every live member's memory still carries one. *The product owner first chose the cascade to simplify, then reversed it when OFF-3's own wording turned out to call that "the one place the obvious implementation of delete everything of theirs is wrong".*
- ✅ **`content.account_id` is `on delete set null` as of 0018, and was `cascade`.** Deleting an account would have removed that person's content from threads they shared, which OFF-3 forbids as a MUST and the privacy page promises in public will not happen, in bold, having told people to understand it before they share. Nothing had broken because account deletion is not built, so it was a trap rather than a live falsehood: it would have sprung the first time somebody wrote the obvious `delete from accounts where id = ?`, passed their tests, and quietly emptied half of somebody else's thread. *Found by writing 0017, which hit the identical decision for memories and went the other way, leaving `content` and `memories` disagreeing about what a shared thread is. The comment four lines above the constraint in 0011 cites OFF-3 for the read rule and then writes the cascade on the next line.*
- ✅ **`set null` rather than a reserved "deleted user" account, and the nullable-column objection is answered in the type system.** A tombstone row keeps the column NOT NULL, and the cost is a fake account every listing has to remember to exclude: admin People, member lists, analytics, the waitlist, each a place to forget. `set null` adds no row and no exclusion rule. The real objection to a nullable author is "some other bug emits a null and it is indistinguishable from a departed author", and that is closed by typing the column `ColumnType<string | null, string, string>`: a select yields `string | null`, an insert and an update both require a `string`, so no application code can produce one and only the constraint can. *The alternative was `on delete set default` to a well-known uuid, which keeps NOT NULL but gives the column a default, so an insert that forgets the author silently attributes content to nobody instead of failing loudly.*
- ✅ **Content whose author is gone can no longer be deleted by anybody, and that is the promise working.** OFF-3 gives delete to the author, the author is gone, so `requireAuthor` matches nobody. Archive is the co-owned action and still applies, so a thread can be cleared from its active list without destroying what somebody left in it. `requireAuthor` writes the null check out explicitly rather than relying on `!== accountId`, so nobody later reads it as an oversight and turns it into a fallback that lets any member delete a departed one's rows.
- ✅ **The rest of the chain was checked in the same pass and is correct.** `messages` cascades because a conversation is private to one account, and `content.derived_from_message_id` is `on delete set null`, so content survives and loses only its provenance pointer. `thread_members` cascades, which is OFF-3's "their membership goes". `threads.created_by_account_id` is already `set null`, so a shared thread outlives its creator. One link was wrong, not the chain.
- ✅ **Mute is to a memory what archive is to content.** Any member, thread-wide, reversible. It exists because OFF-3 gives delete to the author alone, and without a co-owned action a member steered badly by somebody else's rule has no move but to ask them. *It is also the only thing anyone can reach for in the injection case: a co-member writes "never file anything from Ana as a task", offload never diagnoses itself, and nothing in the product points at the memory doing it.*
- ❌ **The cap of ten is gone, and the row lock with it (2026-09-10, 014).** A hundred is a prompt budget applied when the prompt is assembled, not a wall on the way in: **nothing a person dumps is ever refused**, which is the difference between a cap on a standing rule and a cap on what a thread can hold. With no invariant to protect there is nothing to serialise, so `select ... for update` was deleted rather than left guarding nothing, which is the failure the staff-linking guard already taught this repo once. What follows is the reasoning as it stood at ten, kept because the lock is the right answer whenever a cap comes back.
- ✅ **The cap is ten and it is enforced under a row lock.** `select ... for update` on the thread, inside the transaction that inserts, because a plain count is check-then-act and two adds at nine leave eleven. Soft-deleted rows do not count, or "delete one, add another" fails for eight seconds; muted rows do, or muting is a way to hold eleven. **Restore re-checks it**, which is the one door the cap does not otherwise watch.
- ✅ **The duplicate rule applies to offload and not to a person (2026-09-10, 014).** It was built because a model asked twice about the same thread writes the same sentence twice. Applied to a person it is a dump that silently does not appear, which is the one thing this product may never do, so the unique index is now partial on `origin = 'learned'`.
- ✅ **A duplicate takes `on conflict do nothing` and a select, never a caught unique violation.** Postgres puts the conflicting value in the error's `detail`, so a caught 23505 carries memory text into whatever logs the exception. Memory text is dumped text (OFF-1). Same class as the `jobs.last_error` scrubbing already recorded here, found before it shipped rather than after.
- ✅ **`kind = 'preference'`, not `standing`.** 001's `standing` is the one-per-thread summary blurb the kits draw as `Standing`, `threadStanding` and `neutralStanding`. Redefining it would collide with all three. `preference` is 001's own "how you like things" and it stretches slightly over "Ana handles the electrician", which is recorded rather than papered over.
- ✅ **Notes reach a prompt only for threads a turn touches**, returned by `add_content`, `add_note` and `create_thread`. The alternative was every thread's notes up front, which is a hundred times however many threads an account has ever made, in every prompt, forever: the OFF-8 failure written out.

  **Amended 2026-09-10 by 014, which raised the number tenfold.** The old ceiling was `MAX_MEMORIES_PER_THREAD` times `MEMORY_TEXT_CHARS` times `MAX_TOOL_CALLS`: 10 x 200 x 8, 16,000 characters a turn. A note is now what any dumped sentence becomes, so the per-thread number is 100, and the same arithmetic gives 160,000. Two things bring it back: **a thread's notes are carried once per turn** rather than once per call, derived from what the turn has already written rather than from a column, and **`NOTE_TURN_BUDGET` caps the whole turn at 200 entries**. The honest worst case is 42,400 characters, still three constants, still flat in account age, still asserted at 200 threads. *A turn touching eight distinct threads that each hold a hundred notes is not a turn anybody has; the ceiling exists so that the day one happens it is not a bill.*
- ✅ **Compaction is on the reversible allowlist, and it has no Undo (2026-09-10, 014).** The daily fold acts automatically, on an offload-owned surface, and destroys nothing a person wrote: it sets notes aside, and it deletes only what offload itself wrote and nobody has edited. It has no turn and no toast, so OFF-6's eight seconds cannot apply, and OFF-6's own answer is this list: an action is reversible only once it is on it. Without the entry the default makes a fold outward facing, which would mean confirming one per note.
- ✅ **Undoing a turn takes back the memory it wrote.** `undoTurn` reversed content and messages and not memories, so undoing a dump would have left the standing rule offload derived from it steering every later turn on that thread. Same argument as reversing offload's own reply.
- ⚠️ **Prompt injection is open, widened by 014, and contained rather than closed (2026-09-10).** 008 crossed SEC-1 with ten rule-phrased memories classified at write time. A note is what any dumped sentence becomes, a hundred of them reach the model, and whether one is a rule is decided when the model reads it, so the gate moved from write time to read time and somebody who can put a sentence on a shared thread no longer has to phrase it as an instruction. **Accepted again by the product owner, with the containment this entry named taken this time**: three lists rather than one, yours, other members', and connector-derived, weighted differently in the prompt, and a solo thread produces an empty second list.
- ⚠️ **Prompt injection is open, deliberately, and the shape is known.** A memory is an instruction delivered on the untrusted channel, in a shared thread it is an instruction written by somebody who is not you, and offload writes them itself from dumped text. The blast radius is bounded to tool calls the victim's own turn could already make in threads they are already in, so it is not an exfiltration path; it is silent behavioural sabotage, and because offload never diagnoses itself nothing points at the cause. Containment when it is time: trust-tier other-authored memories below your own in the prompt, or constrain structurally what a memory may influence rather than relying on prompt wording.
- ⚠️ **Thread deletion must delete the thread's memories and there is no caller.** `subject_id` is polymorphic so it carries no foreign key and nothing cascades. `deleteMemoriesForThread` exists and is unused, because no thread-deletion path exists yet in the product. Whoever builds one has to call it.

## Repeating, decided 2026-09-11

- ✅ **A thing that comes round again is one row with a rule.** "Yoga every Tuesday for the next month" had nowhere to go: one undated note loses the Tuesdays, four notes is four rows saying Yoga. The row carries `repeats` and `repeats_until` and the calendar expands the rule over whatever window is on screen, so a list draws one line and every matching day gets a mark. On both tables, because the same sentence arrives as either: yoga is a note, "standup every weekday at 9" is an appointment.
- ✅ **`repeats` and `series_ref` are two mechanisms and stay apart.** A calendar sends occurrences and offload mirrors them as rows sharing a `series_ref`; a list collapses those and the calendar draws every one. A rule has nothing behind it because somebody said it in words. Rewriting a calendar's occurrences into a rule would mean deciding its exceptions do not exist, and a moved week is exactly what a rule cannot say. The database refuses a row that carries both.
- ✅ **Six values, not an RRULE.** `day`, `weekday`, `week`, `two_weeks`, `month`, `year`. iCal covers "the last Thursday of every other month" and nobody has asked for it; a column holding one is a parser, a test suite and a screen for editing it. `weekday` exists because "standup every weekday" came back as `day` and put a standup on Sunday. The day of the week comes from `occurs_at` rather than being stated twice and able to disagree with itself.
- ✅ **A rule does not stretch the rail.** "Every Tuesday" with no end would otherwise make every thread a year long and push it into the month view forever. The span comes from what happens once, and rules fill whatever span that turns out to be. Expansion is bounded by the window and capped at 400 steps, so a daily rule from 2020 draws this month rather than walking two thousand days.
- ✅ **Monthly clamps rather than rolls.** Monthly from the 31st is the 30th in September and the 31st again in October. Letting `Date` roll 31 September to 1 October means every later occurrence lands on the 1st, which is a rule quietly rewriting itself, so the occurrence is computed from the first one rather than from the last.
- ✅ **Anything with a date is off the leftover list.** The rail draws every dated row and its day lists them, so repeating it under "Everything else" is the same row twice on one screen. Taken from what the rail actually draws rather than from a type check, so the two cannot disagree. *An event with no date at all still lands there, which is the one case with no other home.*
- ⚠️ **The tool definition budget was raised from 1,500 to 1,800, and that is a deferral rather than a decision.** The guard fired at 1,544, which is what it is for. `add_content` and `add_note` are 343 and 300 tokens after gaining a body, dates and now a rule, and the other eight are 890 between them, so there is no padding to remove and getting under 1,500 means removing capability. The remedy the constant's own comment prescribes is `defer_loading`, it has not been done, and the next thing that grows this set should do it rather than move the number again.

## The thread you are looking at, decided 2026-09-11

- ✅ **The thread on screen is a filing default, and the words override it.** Somebody typing into the composer from inside a thread means that thread nearly every time, and making them say so is the filing this product exists to avoid. So the open thread reaches the planner as context, `looking_at`, with the prompt saying in as many words that a dump naming another thread wins. **A pin would have been the wrong mechanism**: `thread.quick_add` genuinely cannot leave its thread, because pressing + in a section is the choice, but the composer is the general input and "add oak brackets to Flat admin" typed from Lisbon trip has to reach Flat admin. Verified against the real model on twelve cases: the default held in four, the override held in four, and no thread on screen behaved as it did before.
- ✅ **It lives on the message, not in the job payload.** `messages.looking_at_thread_id`, which costs a column and removes two problems. The resume path re-enqueues from the message and would otherwise lose the default on exactly the retry that needs it, and the worker already selects that row, so the id is copied one fewer time. `on delete set null`, because a thread that is gone is not a default.
- ✅ **Membership is checked when it is written and resolved again when it is read.** The id arrives from a client, so it is a claim: `takeDump` checks membership before storing it, and the worker's query joins `thread_members` again rather than trusting what is stored, because somebody can leave a thread between the dump and the answer. **A stale id is dropped, not refused.** The screen can be showing a thread deleted a second ago, and losing the default costs a convenience where refusing the write costs what somebody wrote.
- ✅ **The default is said out loud, once.** "in thread Sustain" above the field on a phone and in front of it on the web. ## Saying something, decided 2026-09-11

- ✅ **A filing turn says nothing, and saying something is a tool.** "Added Call the plumber to Miscellaneous" under a Done mark and a link to Miscellaneous is somebody's own sentence read back to them. The prompt was asked to hold the line and could not: told plainly to write nothing, the model wrote "Done, no reply needed." A model ends a turn with text because that is what ending a turn looks like. So the default is inverted rather than argued with. On a filing turn the trailing text is discarded and the only thing a person reads is what `say` was called with, which is almost never. It is OFF-5's rule applied to the last output that was still free text. **Answering keeps its text**, because a question with no sentence back is a failure and there is nothing to invert.
- ✅ **Silence is a finished turn, and three things are not.** A turn that filed something and said nothing is exactly right. A turn that filed nothing and said nothing did not happen. A turn that created a thread, filed nothing into it and said nothing made an empty place and told nobody. A turn the bound cut off mid-work says nothing either and is not finished, which needed its own flag once silence stopped being unusual: `out_of_calls` is the difference between the model stopping and the loop stopping.
- ✅ **A bare date is noon, not midnight.** `parseWhen` stored a date with no time as midnight UTC under a comment claiming local "would put a due date on the wrong side of a boundary for half the world". It is the other way round: midnight UTC is already the previous evening everywhere west of Greenwich. "Sunday brunch on way back to NYC" was drawn under Saturday at 8pm with the word Sunday in its own title. Noon holds from UTC-11 to UTC+11 and is still wrong in New Zealand; the complete answer is the account's timezone, which is not stored. **012 already knew this**, flagging an all-day calendar event with "an all-day event is a date, not midnight anywhere", so a dumped date now carries the same `all_day` and no client draws an hour it does not have. 0035 moved the rows already written.

## The thread page, decided during 005

- ✅ **Move is the author's, like delete (2026-09-03, the product owner's call).** OFF-3 says a member may add to a thread and may never delete what is not theirs, and it says nothing about moving. An early draft let any member move any content anywhere they themselves could reach, which the security review traced to a real hole: Bob moves Alice's content into a thread Alice is not in, and it is gone from her view, unrecoverable, with no notice. **A delete performed by a non-author, reached by a route OFF-3 does not mention.** A narrower fix was available, letting a non-author move only within the author's reach, and the product owner chose the broad one. Both actions change who can see something, so both sit with the author, and the permission model fits in one sentence: *what you put in a thread stays where you put it until you move it, and everyone can help with the rest.*
- ✅ **Archive is the co-owned soft action, and it is why the split works.** Any member may archive and restore; only the author may delete. Without archive, a shared grocery list accumulates rows only their author can clear, which is the friction that makes people abandon a shared list. With only delete available to everybody, a shared thread becomes a place where somebody else can destroy what you put in. `archived_at` and `deleted_at` look alike and are opposites: one is permanent and reversible and destroys nothing, the other starts an eight second clock ending in destruction.
- 🔄 **Reversed the same day: every pane has a URL.** The first build held the pane stack in client state, on the grounds that the kit renders two places at once and Next's router has no shape for that, and recorded "no deep link and no browser back" as an accepted cost. **The product owner reversed it within hours and was right**, for two reasons neither of which is convenience: a thread cannot be shared if it cannot be linked, and offload cannot answer a dump by pointing at where it filed things. Both are the product working rather than a nicety.

  The fix turned out to be simpler than what it replaced. **The stack is derived from the route rather than accumulated**: `/threads/:id` is My threads beside that thread, `/content/:id` is its thread beside that piece. There is no stack to get out of step with the URL, somebody opening a link cold sees the same two panes, and browser back works. *Recorded as a reversal rather than quietly fixed, because the original reasoning was sound and still produced the wrong answer: I reasoned from what the router made easy instead of from what the product needs to do.*
- ✅ **The breakpoint lives in CSS alone.** The design system has no breakpoint token, so a JavaScript copy of 1180 would be a second place for the number to live and a second place for it to be wrong. The crumb trail and the back button both render and the stylesheet picks one, which also removes a resize listener and a hydration mismatch.
- 🔄 **Reversed the same day: the composer is in the shell, under every pane.** The kit has said so since it was drawn, in as many words: "one composer, under both panes, spanning the window. It never belongs to a pane." 005 left it on Today anyway, on the grounds that moving it risked the working dump loop for no gain, and logged that as a debt. **The product owner reversed it immediately**, and the readme already contained the argument: the composer is a tool rather than a chat, and any UI task in offload can be said instead of tapped, so a place you can say things cannot be one tab. Half the app would have had no way to be spoken to. *The lesson is not "move the composer". It is that "the kit says X and we are doing Y for now" was the tell, twice in one feature.*
- ✅ **offload's reply links to the threads it wrote to, and the links come from the content rows.** Never from parsing the reply. A turn's `threads` is one indexed lookup on `content(derived_from_message_id)`, deduplicated, in filing order, and it drops a thread whose content has been undone. If the sentence and the links ever disagree, the links are right and the sentence is the bug, which is the same direction 004's truthfulness criterion points.
- ✅ **`canDelete` and `canMove` are computed by the server**, using the same predicate the endpoints enforce. A client that decides what somebody may do can draw a control the server refuses, or hide one it would allow, and both are bugs nobody notices until somebody complains.
- ✅ **The pagination cursor is the UUIDv7 id alone.** 001 specifies "(created_at, id), which UUIDv7 makes monotonic", and the id is what makes it monotonic, so the id is the whole cursor. **The pair version silently loses rows**: Postgres stores `created_at` to the microsecond, a JavaScript `Date` holds milliseconds, so round-tripping the timestamp through a cursor truncates it and rows written inside the same millisecond fall in the gap. Eighty rows inserted in a loop returned seventy-nine, which is exactly what a thread filled by one dump would do.
- ⚠️ **The standing summary has no writer, and where there is none the page shows nothing.** `memories` is specified in 001 and has never been migrated, and nothing anywhere summarises a thread. 005 first rendered the phones' "offload has not summarised this one yet" and the product owner reversed it the same day: **a line saying offload has not done something is not information, it is an apology in the most prominent space on the screen.** The `standing: null` field stays in the shape so the day something writes one, no client changes. *The writer is still worth its own small feature; the placeholder was not worth having in the meantime.*
- ✅ **Restore undoes a delete as well as an archive.** One endpoint clears `deleted_at`, `purge_after` and `archived_at` together and puts the count back. Found by a test: `readableContent` filters out soft-deleted rows, so before this the row could not be found again and **the Undo the whole delete story rests on did not work at all**.

## The planner, decided during 004

- ✅ **Filing is a tool loop, not a structured verdict (2026-09-03).** The planner reads the dump, decides what to do, does it through tools, and says what it did. This replaced the `sort` tier one-shot that `architecture.md` step 4 and the task-tiers entry above both described, at a higher cost per dump. The reasoning: a structured verdict cannot recover from a tool that fails, and tools are the architecture every later capability arrives on, so the loop is worth getting right before there is anything complicated on it. Both documents were amended in the same change rather than left to disagree.
- ✅ **Two tools, and two were cut rather than deferred on taste.** `create_thread` and `add_content` ship. `move_content` and `edit_content` do not: nothing in the planner's context can produce a valid content id, because it sees thread names and recent turns rather than content rows, and search is out of scope. A tool the model has no way to call correctly is scope with no path to being exercised. They return with search. *The worked example in the spec never used them either, which was the tell.*
- ✅ **The planner runs on Sonnet (`claude-sonnet-5`).** Tool use plus a natural reply is what the `converse` tier already covers, and correctness on filing is worth more than the price at this size.
- ✅ **Every tool call is an HTTP call to the Core API.** The Python plane still writes nothing. That is what turns "check membership before filing" from a convention the worker is trusted to follow into a check on the only machine that can write, and it is why the account comes from the job row rather than from anything the model produced.
- ✅ **One refusal reason on the tool endpoint.** A thread that does not exist and a thread that is somebody else's return byte-identical bodies. Two reasons would make the endpoint a membership oracle for any thread id a caller could guess.
- ✅ **The internal request bodies are strict.** `internal.ts` had claimed since 003 that "a body naming an account is refused, not ignored", and zod strips an unknown key by default, so the schema was silently dropping the field the comment said it refused. Both endpoints use `z.strictObject` now. *Found by writing the test the comment implied.*
- ✅ **Idempotency has two halves and they are different mechanisms.** Within a turn, a retried tool call is deduplicated by the model's own `tool_use` id, enforced by a unique index on `(derived_from_message_id, tool_call_id)`. Across a resume it is not: a resumed turn is a new model call with new ids, and what stops it filing twice is being told in a trusted block what already landed. That is a model instruction rather than a constraint, which is weaker, and it is why the durable half comes first: nothing already written is ever lost or rewritten by a resume, so a duplicate is a wrong answer rather than a lost dump.
- ✅ **Partial success is a message state, not a flag.** `messages.state` gains `partial`, distinct from `failed`. The three want different things from the client: nothing, a resume, or the text back in the composer. A partly finished turn offers to finish itself, and the reply for one is written from the record of what landed rather than asked of the model, because the model is the thing that did not finish and its last word on the subject is unreliable by construction.
- ✅ **Undo has no server-side time window.** The eight seconds is the toast's lifetime in the client. A window on the endpoint would add a clock-skew failure mode in order to stop somebody deleting their own content, which is not a threat. *Written down because the acceptance criterion says "available for eight seconds" and a reader would otherwise look for a check that is deliberately absent.*
- ✅ **The purge job is enqueued by the delete, not by a timer.** The undo transaction enqueues `content.purge` to run ten seconds later. A timer that stops running leaves content the person believes is gone, and nothing notices. The handler states both predicates even though either implies the other today, counts before it deletes, and halts rather than continuing past 500 rows: it is the only hard delete in the codebase, and the right response to a bug in a delete is to stop.
- ✅ **`things` became `content`, in schema and code only.** The word was retired as user-facing copy on 2026-09-02 with the instruction to reword rather than swap in a synonym, and that still holds for anything a person reads. A table needs a name; a screen does not. `thing_id` and `thing_type` as analytics properties become `content_id` and `content_type`. The design system's kits still say `thing` and are logged as needing to catch up; its explorations do not, because rewriting a record of what was tried on a date falsifies it.
- ✅ **Closed by 005 on 2026-09-03. The privacy policy's automated-decisions paragraph is now true, and the page did not have to change.** 003 recorded this as closing on 004 shipping. Two of its four claims now hold: filing is automatic, and it is reversible. Two do not. **"Every decision it makes is visible to you"** is false while there is no thread screen, so filed content exists and cannot be looked at. **"Anything filed in the wrong place can be moved at any time afterwards"** is false because `move_content` was cut, so after the eight seconds there is no way to move anything. *Raised to the product owner on 2026-09-03 rather than resolved in code, because the page is a claim surface and rewording it is their call. The options are to caveat the paragraph now or to close the gap with the thread screen and `move_content`, which is one feature.*

  **Closed 2026-09-03, and how it closed matters.** All four claims hold: filing is automatic (004), every decision is **visible** because there is a thread page to see it on (005), it is **reversible** through Undo and through edit, archive and delete, and anything filed in the wrong place **can be moved**, because offload files under your own account so you are the author of everything it files for you. *Not one word of the page was edited. The code caught up to the claim rather than the claim being softened to fit the code, which is the only honest way to close an entry like this one and is worth recording because the other way is always available and always cheaper.*
- ✅ **The Python suite loads its own environment.** `apps/agent/tests/conftest.py` parses the root `.env`, which the TypeScript side has done since 003 and this side did not. The consequence was quiet: `test_isolation.py` skips itself without the two database urls, so the three tests standing between one account's text and another's model call reported as skipped in any shell that had not sourced the file by hand. *The first thing it did once it ran was fail, on a column grant the worker did not have. That is the recorded "a test that passes only in your shell" lesson arriving a second time as a test that skips only outside your shell.*
- ✅ **The worker's grant on `accounts` is `(id, state, default_thread_id)`.** A column-level grant in Postgres covers every column the query touches, not just the ones selected, so granting `default_thread_id` alone failed on the `where a.id = ?`. Postgres reports that as "permission denied for table accounts", which names the table and not the column and sends you looking in the wrong place. *Fourth migration to touch this grant, and every one has moved in the narrowing direction.*

- ✅ **A dump joins the most recent conversation if it is under six hours old, and starts one otherwise.** `001-data-model` recorded which conversation a dump joins as deliberately open. - ✅ **A service account key, not Workload Identity Federation, because Railway cannot federate.** WIF went GA on 2026-06-17 and is the right answer wherever it works: the workload presents a signed OIDC JWT, Anthropic returns a short-lived token, and there is no static secret anywhere. It needs the workload to *obtain* that JWT, which on every supported platform is ambient: a Kubernetes projected token, the GCP metadata server, Azure IMDS, the GitHub Actions endpoint. **Railway has none of that.** Its OIDC is "Login with Railway", an authorization-code flow for signing humans into third-party apps, not workload identity, so the worker has nothing to federate from. *The ways around it cost more than they save: Okta or Entra client credentials mint a JWT but need a client secret to do it, which moves the static secret and adds a vendor; and moving the worker onto EKS or GCP for ambient identity is a large change to solve a problem two accounts do not have. So the worker holds a key, and it is a **service account** key scoped to a workspace rather than an organisation-wide one, because a service account has credentials where a workspace key is one, which is what makes attribution and revocation per workload possible.*

### 2026-09-30 · Thirty minutes ends a conversation, the phones' sheets run on one UI-thread position, and back is predictive

**Thirty minutes.** The server's window (`CONVERSATION_GAP`) goes from six hours to thirty minutes. The phones lost their close with the immersive conversation, so silence is the only thing that ends one there: a conversation put away for thirty minutes ends on the next tap into the composer or the next dump, the phone awaiting `POST /v1/conversations/current/end` before that dump. The tail (`GET /v1/conversations/current`) now carries `createdAt` per message, so a cold start knows when it was last spoken to. The web keeps its close and an open tab stops drawing the old turns once the server starts fresh. Six hours was a working session and carried the last subject into the next one.

**One position per sheet.** Every phone sheet is `DragSheet`, and the conversation shares its `useSheetDrag`; the physics are pure functions in `lib/sheet.ts`, and React state follows a close spring rather than leading it. What the build learned: a worklet copies what it closes over and cannot copy a gesture object; a shared value read and written from JS by two components in one tick loses a write, so counters change inside `runOnUI`; and keyboard ownership taken from a field's JS focus arrives after the keyboard has started, so it is decided from the keyboard event's `target` on the UI thread.

**Predictive back.** `android.predictiveBackGestureEnabled` is on for the whole app. A local Expo module, `modules/sheet-back` (Kotlin, an `OnBackPressedCallback` with progress, re-added on every enable so it is the dispatcher's newest), hands the swipe to whichever sheet is on top; with none open back goes to React Native as before. A build without the module falls back to `BackHandler`. It is native, so it ships through the next development and store builds. Verified on the Pixel 9: a swipe pulls the sheet, a cancelled one springs it back, a committed one closes the sheet and not the screen under it, and back on a thread still pops it.

**Design system impact:** logged in the design system's own `decisions.md`, 30 September.

### 2026-09-07 · A provider's name is a suggestion, not a name

**Decision:** what Apple or Google call an account is stored in
`accounts.provider_name`, which nothing reads but the account it belongs to.
`display_name`, the one every member of a shared thread sees, is only ever
written by the person themselves. Everybody confirms a name on the way in, with
the provider's answer already in the field.

**The first version of this was scoped instead of separated, and that was the
wrong shape.** It wrote straight to `display_name` and refused to run for
accounts past first run, on the grounds that they had no screen to see the name
on. That made the backfill dead code for every account that existed, to avoid a
problem better solved by giving them the screen. **Scoping who a risky write
applies to is worse than making the write not risky.**

**What was actually wrong with writing `display_name` from a provider:** it is
what everybody in a shared thread sees next to your content, so a name from
Google appears beside your work, for people who know you, before you have seen
it. Usually harmless. For somebody whose provider account carries a legal name,
an old name, or a name in a script they do not use with these particular people,
it is not, and they are the people least able to shrug it off. Not a security
issue, and it was recorded as one here at first, which overstated it: no
attacker, no boundary crossed. It is about not publishing something on somebody's
behalf that they have not read.

**The name is read in `mapProfileToUser`.** Reading `identity.idToken` is the
obvious move and works for Google and silently does nothing for Apple, whose ID
token has no name claim: Apple sends it once, in the form post of the first
authorization. `@better-auth/core` calls `mapProfileToUser` from each provider's
`getUserInfo` with the name already resolved from whichever source that provider
uses, so it is the one point at which the two agree. It maps no fields, because
`user.create.before` always refuses and the row those fields would land on is
never created.

**Not `accountLinking.updateUserInfoOnLink`,** which Better Auth offers for
exactly this and writes `display_name` unconditionally. Linking Apple to an
account that already signed in with Google would replace a name somebody set.

**It is written on session creation, and the reason is the population it
reaches.** `account.create.before` fires only on the link that creates an
identity: it covers a brand new account and misses every account that already
exists, which linked its provider months ago. Those only reach
`account.update.before`, which Better Auth calls with the provider id, the
tokens and **no `userId`** at all: that hook does not know whose account it is
holding. `session.create.after` runs on every sign-in and carries the account.

**`needsFirstRun` stopped being the same question as "ready".** The gate is
`needsFirstRun || needsName` on all three clients. An account that finished
first run before this exists in a state the product had no name for, and the
answer is not to leave it to Settings: it gets the name screen on its own, once,
with the tutorial and the consent left off.

**Design system impact:** none directly. The screens are in the design log's
entry of the same date.


### 2026-09-08 · A calendar write is reversible or confirmed, and the condition is the entry

**Decision:** OFF-6's reversible allowlist gains its first **conditional** entry. `create_event`, `edit_event` and `delete_event` are reversible when nobody but the account holder learns about the write, and outward facing when anybody does.

**The list has held verbs until now.** Every other entry names an action that is always reversible: archive, move, tick, rename. This one cannot be, because the same action is either depending on who is looking, and splitting it into two verbs would be inventing names for a distinction that is really about the audience.

**The condition, and it is asked of the write rather than of the calendar.** After this, does anybody but you know? Two facts answer it: does the event have guests, and is the calendar one the person has marked as shared. Both are read before the call, and **attendees are read across both sides of the edit**, because removing every guest from an invited event sends each of them a cancellation and a test that looked only at the result would see an empty list.

**Sharing is the person's answer, not Google's** *(reversed 2026-09-18 by 019: the list does carry public and domain rules, as `default` and `domain` scopes, and the count is read from it now; see that entry)*. Reading Google's access list would need another sensitive scope and would still be wrong: a calendar can be public to anyone with the link, or visible to a whole Workspace domain, and neither is an access-list entry. One member and readable by the world is a real state. Defaults to shared, and the sync forces it back to shared whenever Google says the person no longer owns the calendar.

**Undo here is not the product's Undo, and that is a code change.** Every other reversible action is a local soft delete. This one has to reach Google inside the window because the effect already left, so it calls Google first and touches the local row only if that worked. `undoTurn` in `routes/dumps.ts` filtered on nothing but the message a row came from, so an event a tool wrote inside a dump turn was indistinguishable to it: the ordinary toast would have deleted our row and left the event in Google forever. It excludes `source = 'calendar'` now.

**A model-initiated outward write had nowhere to wait**, so one was built. Every tool in this product executes inside the turn and returns a result; there is no pending state anywhere. An outward-facing write from the model writes a `connector_pending_writes` row and returns "waiting for them", and a person's tap performs it with the condition re-evaluated against live state. The model has no field it could set to skip that, which matters because some of what it read was written by a stranger.

**Design system impact:** the confirmation is a control nothing draws yet. Recorded in the design log's entry of the same date.

### 2026-09-09 · Answering builds the index, and the membership predicate finally becomes a view

Decided while specifying 013, and recorded because two of the three are corrections to what the reviews recommended.

**013 builds the retrieval layer rather than handing it to a prerequisite spec.** The review argued for splitting: the embedding pipeline is different-sized, different-risk work from the answering behaviour, and asking one implementer to invent both is how the invisible half gets skipped. True, and the split still loses. An index nobody queries is unused extensibility, which DEV-1 forbids, and it is the exact state 006 and 008 each declined to leave behind when they deferred the embedding column for the correct reason that nothing read it. Answering is the reader. The risk the review named is real and is answered by named tasks and by AC-14, which makes something embed a real string against the real Voyage API, rather than by a second spec that would ship a column and a test that only proves the column exists.

**The account-or-accepted-membership predicate becomes a SQL view, closing 001's T16.** 001 decided this on day one and gave this feature as the reason: the Core API reads through Kysely, the agent plane reads through SQLAlchemy, and a rule written twice is a rule fixed once. The view was never built, and that has been harmless because there has only ever been one reader. Search is the second, in the other language, so the debt comes due here rather than at some later convenient moment. The predicate for memories is a separate one and not a variation of the same: a thread-scope memory has `account_id IS NULL` by design and resolves through `thread_members` on `subject_id`, so the obvious filter returns nothing and the obvious fix for that is to loosen it.

**An answering turn is offered no tool that writes.** This is the one finding that changed the shape of the feature. Until now the model read one thread it had just written to; after this it reads matching rows from every thread the asker is in, including shared ones, where another member wrote the text. Several tools sit on the reversible allowlist above and so execute behind an eight second toast rather than a confirmation, which means an imperative sentence sitting in a shared thread would be read by a model holding them. Labelling retrieved rows as untrusted is necessary and is not sufficient, because it depends on the model behaving. Withholding the tools does not. A turn that both asks and dumps is treated as a dump, which keeps that boundary a single decision rather than a per-tool judgement.

**The question-or-note call is made on the text, before retrieval.** Deciding after would make the same sentence a question on a day the corpus happened to match and a note on a day it did not, which is unpredictable in the way that reads as broken. Ambiguity still files, and that rule is expected to soften once offload can ask a follow-up, which is the next feature.

**Design system impact:** answering has no mock. `find-kit.sh` finds no search or answer kit, so this is one of the few screens designed rather than matched, and the client review turned up more divergence than the first draft claimed.

The rows come from the shipping components, `ContentRowView` and `ContentRow`, not from the kits' `WRow`. The first draft sent web to `WRow` and the phones to their real component and called that parity; it is two provenances converging by luck, and `WRow` has never been wired to state, so it has no filing spinner, no author-conditional delete and no done state at all.

**Three things the kits cannot express yet, and each is code leading design.** A tickable row, which exists nowhere. A row that says which thread it came from, which the thread page never needed because it draws one thread. And the done state, where the kits use `opacity: 0.5` on a completed row while both shipping components reject exactly that in a written comment: never opacity, because dimming a row on a warm page reads as a rendering fault and takes the label under the contrast floor. The ticked fill, border and strikethrough are what the kits have to catch up on.

**The thread link is the existing chip, not a line of text.** `WRow`'s `meta` is plain text and cannot be a link, and it is already load-bearing: it carries who and when, which matters most here because a result in a shared thread can be somebody else's. So results group by thread under the moss chip a reply already uses to name where a dump landed, which is one link per thread instead of one per row and changes neither row component.

**Results render below the reply bubble rather than inside it.** Everything put inside an offload turn until now has been one small fixed control, 012's confirmation and the thread chips. A pane row's hover fill deliberately bleeds by `calc(-1 * var(--space-5))`, which is exactly the bubble's own horizontal padding, so inside a bubble the fill cancels it and runs under an 18px rounded corner. Below it, at the column's width, a row is the shape it already is everywhere else.

### 2026-09-09 · A question is a filter before it is a search, and one read is one result

Decided while reviewing 013's constants, and it changed the retrieval design rather than a number.

**`ANSWER_ROWS_INLINE` was invented and is gone.** It capped how many rows a reply drew, at 8, and it was cited against AC-8, which is the OFF-8 prompt bound: by the time rows reach a client the model call is over, so a display cap serves nothing there. It also never said whether 8 was global or per thread, which the grouping made load-bearing. The right question turned out to be why an answer was long enough to need trimming.

**Because the read was fuzzy when it should have been exact.** "What is left to do from Lisbon" is not a similarity problem, it is `type = 'task' and done_at is null` in one thread, which is a `where` clause the thread page has run since 005. Answering it by cosine distance is a worse and less predictable version of a query we already know how to write. So `list_content` exists beside `search`, widening 006's `list_thread_content` with type and done, and the prompt names it as the one to reach for first. **An answer is then two rows because there are two**, not because something trimmed twenty to a pretty number.

**One read is one result, and `found` carries results rather than rows.** "Lisbon and Istanbul" is two reads, so it is two results, each with its own thread. Flattened to one array the client cannot tell which trip a row belongs to and would have to reconstruct the grouping by guessing from `threadId`. It also matches how the answer is drawn: a result is already a group, under the thread chip a reply uses.

**Ranking is relevance then recency, and only where there is ranking to do.** A filtered list comes back whole, in the thread's own order, because everything matching is the answer and ranking a `where` clause invents a judgement that is not there. A search is fused by RRF and then broken by `created_at`, as a tiebreak rather than a term, so recency can never outrank relevance and no half life has to be defended.

**Truncation is a flag, not a count.** The existing tool already fetches `LIST_PAGE + 1` and reports `truncated`, so below a page the row count is the true count, which is where "three left" comes from, and above it the reply says more than a page rather than inventing a number. No `COUNT(*)` on the path of a sentence.

**The OFF-8 ceiling is now a product**, `ANSWER_SETS × ANSWER_RESULTS`, three results of twenty rows at two hundred characters. Constant regardless of account age, which is what the principle asks, and it is the figure AC-8's test asserts.

**Design system impact:** `ROWS_SHOWN = 8` per result is a client number that bounds nothing on the server. Under it a result draws whole; over it, eight draw with a **Show more** that expands what arrived, and a truncated read ends with the thread chip, because the thread is where the rest live. Show more on a result is a control the kits do not have, and it joins the tickable row and the done state in the entry above. The number is a guess in the absence of a mock and is the thing most likely to move when there is one.

### 2026-09-09 · A wrong no is the expensive answer, so absence needs a complete read

"Did I already add buying butter to the groceries list" broke three things in 013 as specified, and the third is the one that mattered.

**"No" is an answer, and the spec only had a sentence for not having one.** AC-4 covered "a question with no answer" and used the same line for a definite no. They are different: "I could not find it" describes offload, and "no, it is not on the list" describes the groceries, which is what was asked. Both exist now.

**A wrong no is quiet and expensive, and it was the default.** Narrow to the thread, the thread has forty rows, twenty come back, butter is in the other twenty, and the answer looks honest and is a lie: somebody buys butter twice. So absence may only be asserted from a complete read. `truncated` was already in the result and is now load bearing rather than cosmetic, and `list_content` gains `matching` so an existence check reads the rows that mention the word rather than a page of the whole thread. **The test is a thread long enough to truncate with the asked-about row outside the first page**, which is invisible on any smaller fixture.

**It is the deduplication rule again, in the place it bites hardest.** `decisions.md` already says cosine may shortlist and may never decide, and names dedup as the case, because a row and its negation are neighbours to an embedder. An existence check is dedup asked out loud, so no near match is not evidence of absence: retrieval narrows and the model reads the candidates.

**Also found: the answering context had no thread list.** A person names a thread the way a person does, "the groceries list", and every tool addresses one by id. The dump context has carried id, name and default since 004 and the answering context now does too. `context.py` already records why this cannot be resolved server-side: two threads may share a name, so a name is an ambiguous address and resolving it would be guessing on the model's behalf.

**And the done state is not assumed.** Butter may be on the list and already ticked, where the answer is that it was bought on Tuesday rather than no.

**Design system impact:** none. This changes what is said, not what is drawn.

### 2026-09-09 · A span of time is a read, and a conversation is a third predicate

Two gaps found by working through what people would actually ask 013 and it could not answer.

**"What is due this week" was unanswerable, and the index for it has existed since 001.** `(account_id, occurs_at)` was built for the agenda screen. Nothing exposed it to an answer, and `list_content` requires a thread id, so offload could draw somebody their week and not answer a question about it. `list_agenda(from_iso, to_iso, when, type?, done?)` closes it, with `when` in `due`, `occurs` and `created`, which are the three dates a question means. "What did I dump yesterday" falls out of the third for nothing.

**It reads the membership predicate, which the agenda screen does not, and that disagreement is now on the table.** `001`'s index is account-scoped, so in a shared thread the screen misses what another member timed while the answer will include it. Only two new indexes are needed, led by `thread_id` instead of `account_id`. Which behaviour is right is a real question and deliberately not settled here: changing what a shipped screen shows is not an answering feature's call. It is in 013's Open, because a screen and an answer disagreeing about the same week is exactly the two-documents defect class.

**Conversations join the corpus, and they authorize on nothing but their owner.** "Why did you file that in Lisbon" was unanswerable because the reason lived in the reply and the reply was not searchable. `readable_messages` is the third view: `conversations.account_id`, both soft deletes, and `state in ('seen','answered')` because `queued` is internal and must not reach an answer any more than it reaches a client. **A conversation is never shared**, including the one that filed something into a thread somebody shares, because what you said while dumping is not part of what you shared. Written as a view beside the other two so nobody has to notice it is different in order to get it right.

**And half of a conversation is offload's own output.** Searching conversations puts the model's previous replies back in front of it, where a past answer that was wrong is otherwise indistinguishable from something a person stated. Every retrieved message carries its `role`, and the prompt says offload's earlier reply is evidence of what was said and of nothing else about the world. Without that, one wrong answer becomes the source for the next one, which is the cheapest possible way to build a product that confidently repeats its own mistakes.

**A message and the content it became are near duplicates**, since the row was written from the text. The content row wins: it still exists in a thread and it can be ticked, while the message is provenance.

**Two wants are recorded as not built rather than quietly missing.** Counting and totalling across threads, which needs an aggregate over more threads than a turn reads and cannot be done from a truncated page anyway. And what you are waiting on from somebody, where `waiting_on_*` has been in the schema since 0014 and 006 deliberately left it unwritten, and person-scope memories still have no writer.

**Design system impact:** none. `list_agenda` returns the same rows in the same result shape.

### 2026-09-09 · The flaky test was two clocks, not a race

A planner test asserted `after.last_activity_at >= before.last_activity_at` and failed by exactly one millisecond, intermittently, on a change that touched only documentation.

**The test helper wrote `new Date()` and the code writes `now()`.** Node runs on the host and Postgres runs in the Docker VM, so those are two independent clocks. Measured directly rather than reasoned about: five consecutive `select now()` calls came back at +20ms, 0ms, **-1ms**, +1ms and 0ms against `Date.now()`. The negative sample is the failure, reproduced on demand. Test helpers write `sql\`now()\`` now, so a timestamp that will be compared against the database's clock comes from the database's clock.

*Worth knowing generally: any test fixture that seeds a timestamp Postgres will later compare is a cross-clock comparison, and drifts by a millisecond or two in either direction.*

**The second flake was a number collision.** A stream test died as "Test timed out in 5000ms", which is vitest's default, and the pool's `connectionTimeoutMillis` is also 5000. Whichever fired first, the message was the generic one, so a starved pool and a slow test were indistinguishable. `testTimeout` is 20s now: above the pool's bound, so pool exhaustion surfaces as "timeout exceeded when trying to connect" rather than as a stack trace of something asleep. These tests talk to a real database and five seconds was never a meaningful budget for them.

*This is the `EXPO_OFFLINE=1` lesson again: an error message is worth more than a timeout.*

**Design system impact:** none.

### 2026-09-09 · A view over `table.*` freezes its column list

0026 created `readable_content` as `select content.*, ...`. 0027 added the `search_text` generated column to `content`. The view did not gain it: the star is expanded once, when the view is created, and Postgres holds that list forever.

It surfaced as `column content.search_text does not exist`, from a query reading the view, which is a confusing error precisely because the column plainly does exist on the table it is named after.

**The trap is permanent rather than a one-off**, and that is what makes it worth an entry. Every future migration that adds a column to `content`, `memories` or `messages` leaves these views behind the same way, and the next failure may be quieter: a read that silently cannot see a column it should, rather than an error.

0028 drops and recreates the three. `create or replace` cannot do it, because replace may only append columns and the correct list puts `search_text` before `viewer_account_id`.

**The durable fix is the test, not the migration.** `predicate.test.ts` now asserts each view's column set equals its table's plus exactly `viewer_account_id`, so whoever adds the next column finds out from a red test rather than from production.

**Design system impact:** none.

### 2026-09-09 · A vector index keeps the dead until something vacuums

`search-index.test.ts` failed rarely, only ever in the full suite, never alone, and resisted three explanations. The instrumentation left after the first sighting said the same thing every time: `got: 0, matching: 60, setting: relaxed_order`. Sixty live rows, the setting correct, and the scan returning none.

**An HNSW graph keeps entries for deleted rows until a vacuum removes them.** Every other file in the suite empties `content` between tests, which cascades to `content_chunks`, so by the time the index file runs the graph can hold thousands of dead entries from earlier fixtures. An iterative scan spends `hnsw.max_scan_tuples` walking them and returns nothing, while a count over the same rows through a different path says sixty. Alone the file always passed, because alone there was nothing dead to walk. The fixture vacuums now.

**This is a production caveat and not only a test one.** An account that churns heavily gets a worse vector search until autovacuum catches up, and the symptom is search going quiet rather than erroring. Worth knowing before somebody reports it as a bug.

*Three answers, two of them wrong, and both wrong ones were reasonable.* A companion test asserting that iterative scan off under-returns was deleted for depending on the query plan, which was correct on its own terms. Then `enable_seqscan = off` was removed as the cause: it was genuinely vestigial, the test should run the query the way production runs it, and it did not fix anything. What settled it was noticing that the instrumentation had already ruled out the data, the predicate and the setting, so whatever was left had to be about the index rather than about the query.

**The lesson is the instrumentation, not the vacuum.** Three attempts to reason about a rare failure produced two wrong answers; one line of state captured at the moment of failure produced the right one, and cost nothing while the test was passing.

**Design system impact:** none.

### 2026-09-09 · Correcting the entry above: the test was asking for a guarantee pgvector does not make

The vacuum finding is real and stays. It was not the whole story, and the entry above overstates it.

**The assertion itself was wrong.** It required an HNSW scan to return exactly the twenty rows the limit asked for. pgvector's documentation says the opposite in as many words: *"There may be even less results due to dead tuples or filtering conditions in the query."* Both applied here at once. So every explanation chased, including the vacuum, was a search for why an approximate index failed to be exact.

**It was rewritten three times and all three failed**: exact twenty, then twenty after a vacuum, then merely greater than zero. Each rewrite was a better guess than the last, and the pattern is the answer. How many rows an HNSW scan returns depends on the state of the graph at that moment, so it is not a property a test can pin down, and a test gating every commit on it fails for reasons nobody can act on.

There is no recall assertion now. What remains is the part that is ours: iterative scan is on for every pooled connection, so the post-filter cannot silently starve a membership-scoped read. AC-13 asked for the setting, and the setting is what is checkable. Recall is pgvector's, and it declines to promise it.

**What follows for the product, and this is the part worth keeping.**

- **Vacuum policy: there is none of ours, and there should not be a job.** Autovacuum already exists, yields under load, and needs nobody to remember it. `0030` lowers `autovacuum_vacuum_scale_factor` to 0.02 on the three chunk tables, because the default 20% dead is chosen for tables where dead tuples cost time; here they cost **results**, and the symptom is search going quiet rather than erroring. pgvector also warns that vacuuming an HNSW index is slow enough to want a `REINDEX` first, which is not something to run on a timer against a live table.
- **The churn itself was the bigger problem.** `handle_embed` replaced a row's chunks whenever the sweep found it stale, and the sweep finds staleness through `updated_at`, which ticking a task, editing tags, changing priority, archiving and moving all touch. None of them change a word of the text. Every tick was paying Voyage for a vector we already had and leaving the old entries dead in the graph. It now compares the chunk text first and touches `embedded_at` when nothing moved.

**Voyage has no view on any of this.** They return vectors. The index, its dead tuples and its vacuuming are entirely ours, and the only vendor guidance that applies is pgvector's.

### 2026-09-09 · What the review panel found before 013 merged, and the two that were feature-ending

Three reviewers over the whole branch. Two findings would have shipped a feature that did not work at all, and neither was catchable by the suite as it stood.

**`load_answer` read a column its query does not select.** `_THREADS` selects `id` and `name`; the answer path read `row.is_default` off it. SQLAlchemy raises on a missing column rather than returning `None`, and `_handle_answer` catches everything, so **every question from any account with a thread came back "failed"**, indistinguishable from a model problem. It was invisible because every test builds `AnswerContext` directly and nothing exercised `load_answer` against a database. It computes the default by comparing ids now, exactly as the dump path always did.

**The phones dropped the rows.** `fetchAnswer` in `apps/mobile/lib/dump.ts` did not carry `found` in its parsed shape, and it is the only way an open app learns its turn is finished. Every answer rendered its sentence and none of its rows; the rows appeared after a force quit, because the cold start reads a different endpoint. Web had the field and the phones did not, in two functions written to mirror each other.

*Both were one missing field, both in the seam between two things that were each correct, and neither was reachable by a test that did not run the real query or the real fetch.*

**A soft-deleted thread was still answerable.** `readable_content` carries authorization and deliberately not lifecycle, because `restore` depends on a deleted row still resolving, so every reader states its own. `listContent` did. `listAgenda`, both arms of `search`, the memory asides and `found` did not, so deleting a thread left its rows in "what is due this week" with a working link to it, and left a memory scoped to it still steering the answer. The window is the eight second Undo plus however long until the purge, which is not small.

**An embed job that failed unexpectedly was stranded forever.** The dispatch sat outside the loop's try, and `handle_embed` catches only `EmbeddingUnavailable`. Anything else reached the outer catch-all, which logs and sleeps without releasing the job. Nothing reaps a stuck `running` row, and the sweep cannot re-enqueue it because the idempotency key carries the row's `updated_at`, so **one malformed response made a row permanently unsearchable until somebody happened to edit it**.

**The sweep read every row of three tables every minute, forever.** Its comment says the hundredth sweep finds nothing, which is true of what it returns and not of what it costs: an anti-join plus an ordered limit over the whole live table, to answer "nothing". `0031` adds a partial index per query, matching each predicate and its sort. Verified by reading the plan rather than by assuming: index scan under the limit, no sort node.

**Two prompt-framing fixes, both about the same wrong word.** The thread list was introduced to the model as "this is our data". The ids are ours; the names are not, because any accepted member can rename a shared thread and a name the filing model chose came from somebody's dump text. It now says the ids are ours and the names are labels people wrote, on the answering turn and on the filing turn, which is the one that carries the write tools. `accountFacts` carried the same claim in a comment, and a calendar's name comes back from Google.

**Deliberate deviation from OFF-5, recorded rather than hidden.** `classify` validates through a schema but does not retry and does not raise on a validation failure; it returns "not a question", which files. Raising is the wrong failure here: this call sits in front of every dump, so an exception loses the note rather than degrading the feature, and the schema is two booleans behind a forced `tool_choice`. What OFF-5 is really protecting against is the silence, and that is now closed by a log line: without it a classifier degrading in production turns every question into a filed note and nothing says so.

**Left alone on purpose.** `0027` rewrites three tables and builds three GIN indexes in one transaction, taking an `ACCESS EXCLUSIVE` lock at boot. At alpha volumes that is seconds. `CREATE INDEX CONCURRENTLY` cannot run inside the one-transaction-per-file migration runner, and a `lock_timeout` would turn a brief lock into a failed boot, which is worse. It needs revisiting before the tables are large, and the runner is what has to change first.

**Design system impact:** none. The client findings are logged separately in the design system's own `decisions.md`.

### 2026-09-20 · A client write is drawn first, and a reload yields to a write in flight

**Decision:** every row-level write on the web and the phones is optimistic. The screen applies the change to its own state, sends the request, and the request's one remaining job is to disagree: a refusal puts the screen back and a toast offers the same action again. `lib/optimistic.ts` on each client holds the whole rule as `perform(op)`: `apply`, `revert`, `write`, an optional `unwrite` for the Undo, and the words. One copy per client, like `threads.ts`, and one test per copy.

**A reload yields to a write in flight.** The old shape reloaded after every write, and with optimism that reload is the bug: it lands while the next change is still travelling and undoes it on screen for the length of a round trip. `useWrites` counts what is in flight and reloads once the count reaches zero, failed writes included, and every reload checks `idle()` after its fetch and drops its result if something started meanwhile. The counts, the notes and the rows are patched by hand in between; the settle reload is what makes the screen the server's again.

**Undo waits for the write it undoes.** Two writes to one row in flight at once race on the server, and the second can land first. `reverse` awaits the original write's promise and does nothing if it never landed. The Undo toast is shown at the press regardless.

**A provisional row carries a made-up id.** `pending:` prefixed, so every surface can tell it from a real one and draws it inert. On the web the thread pane inserts it into its own rows and swaps the id when the write lands. On the phones the write leaves the composer, which is shell-level, so the context keeps a `pending` list the thread screen derives its rows from; a landed entry keeps drawing under the server's id until the screen's reload has the real row, then the screen adopts it, with a fifteen second backstop for a screen that is not there. **A dump's send is optimistic too**, with a local `unsent` flag rather than a wire state: the turn is drawn at the press under `unsent:<key>`, the server's ids replace it, and a send that throws or returns nothing becomes `failed` with `unsent` so the bubble can say the dump is not saved rather than that it is. A turn that asked which country ends with no reply: the model wrote `*(awaiting their pick)*` and `undefined` beside the question in one run, and either would have reached a screen. Compaction never removes a note a person typed and never re-adds one as its own with `folded_from` naming only itself, which is how a stated note was becoming a learned one. The eval harness applies the same three after the model, so a case measures what a person sees.

**Smaller code changes from the labels.** A typed tag that was not offered is a new value in the options' dimension. One date typed for a stay is one night. The judge prompt reads "next weekend" as the weekend after this one and a bare clock as today. The bound admits "22" when the dump holds "22nd". Compaction is told today's date, which its prompt had assumed all along.

**Prompt changes, all from labelled cases.** A list is one row per item. From inside a thread every piece stays there unless its words name another. Past tense means the month that has passed. With a calendar connected a dated appointment is written to it unasked, and a write that came back written is silent. Silence covers every change, not only a filing: "Done, moved to Porto weekend" was the commonest failure. A lone emoji or a hello files nothing and is not the refusal. The answering prompt separates `Can't search that.` from `Not sure.` and gives a device preference a whole sentence. The classifier routes any question to answering and treats a fragment with a question mark as unsure. Quick add carries the dash rule and no longer promises a date its tool cannot set. 016 AC-15 is narrowed: a note that holds the fact is the answer and nothing is said.

**The prefix is cut.** A filing turn carried 7,400 tokens of system prompt and 2,300 of tool definitions, rewritten into cache on nearly every dump at alpha traffic because the five minute cache had expired. `plan_v2.md` is rewritten to about half its length with every rule kept. The one hour cache TTL was considered and not adopted. Deferred tool loading was looked at and not done: it pays once tool schemas pass roughly ten thousand tokens, and ours are two thousand, so the discovery round trip it adds would cost more than the schemas it saves.

**A `say` names its reason, and the loop holds it to the record (2026-09-18).** "Done." after a move, "Archived." after an archive, "Done, added to your calendar" came out of a prompt that says a turn that did what was asked says nothing, on three models, in every run. The prompt cannot hold that rule, so `say` now takes `because`, one of `could_not_read`, `nothing_to_file`, `could_not_do`, `waiting`, `new_thread`, the five things a person would not otherwise know, and the loop drops a say whose reason the turn does not bear out: `new_thread` with no thread created, `waiting` with no write waiting, the two nothing-landed reasons after a filing. A routine filing has no reason to claim, which is why it says nothing. `could_not_do` is taken on trust, because a calendar that is not connected leaves no trace in the tool record. A say with no reason is refused by the schema (OFF-5). Unmeasured; the next run says.

**Every run is kept.** `evals/history.jsonl` gets one line per run, with the score by principle, the cost, the models, a hash of the prompts and the commit, and `HISTORY.md` is the table. Backfilled with the five runs to date. The transcripts in `results/` stay uncommitted.

**The harness scores a case on the majority of N runs** with `--runs 3`, because two single runs disagreed on 39 cases, and it prices every run from the token counts. **Measured, one run, on Sonnet with the rewritten prompt: 415 of 459, 90%, for $6.83.** On the 432 cases both runs share, 397 pass against the baseline's 381, and asking-back went from 49 to 56 of 59. The 27 newly labelled cases pass 18. Two regressions the rewrite introduced were fixed after the run and are unmeasured: a dated appointment with no calendar connected got the "Settings under Connected apps" line, and a hello was answered with an emoji.

**Design system impact:** none.

### 2026-09-16 · The LLM evals are principles with cases under each, run on production's models

`apps/agent/evals/` is rebuilt as a hierarchy. **A principle** is one sentence of how offload behaves, from a spec, a prompt rule or something a person expects, in `principles/NN-slug.json` with its `why` and `sources`. **Its cases** are generated from it the way tests are generated from a function: the ordinary path, the edges, the negatives. **A context** in `contexts/` is one account's fixture, shared by cases. Twenty two principles, 459 cases, of which 171 are the old brevity, asking-back and reaching-the-web sets folded in. `/run-llm-tests` runs it; it never runs on its own.

The principles are the durable half. Cases are rewritten as the product moves; a principle goes only when the product stops behaving that way, and then the diff says which behaviour was dropped. `/implement` and `/tweak` carry a step: a feature that touches a prompt, a tool the model calls or what a person reads back adds a principle or cases before it is done, and runs the principles that name the changed prompt before and after.

**The old runner filed on Opus. Production files on Sonnet.** `run_eval.py` used one model constant for both kinds of turn, so every filing number in this log from 016 and 018 was about a model nobody shipped. The new harness reads the models from `Config`. Measured on the shipped model, the asking-back principle is at 83%: Sonnet takes the "a task is a task" half of 018 and drops the table, so a gift, a renewal and a call with somebody get a row and no question.

**First baseline: 381 of 432, 88%.** Six surfaces, one per model call: filing, answering, classify, quick add, the typed-answer judge, compaction. Every failure was read against its transcript before the number was believed, and about a quarter of the first run's were the case or the harness: a stub that did not hand rows' tags back, the provenance bound run against the account's country after the person had picked another, rubrics written before the 15 September "Not sure." rule. What survived clusters: Sonnet says Done after a move, an archive or a private calendar write, and names the thread; a waiting calendar write is described as done before it is described as waiting; Haiku's compactor removes notes people typed and re-adds untouched stated notes as its own; the answering path says "Not sure." to a campaign question where the line is "Can't search that."; queries are composed rather than copied and the bound refuses them; two replies said "couldn't pin that down", the exact sentence the prompt quotes as the one never to say; quick add wrote an en dash on the one surface whose prompt lacks the rule.

**The number moves by about four points between runs.** Two full runs an hour apart disagreed on 39 cases in both directions. A single case flipping is noise until it flips twice; a `--runs` mode that scores a case on its majority is the next thing the harness wants.

Found while writing the principles rather than running them, each a pair of documents that read fine alone: compaction is never told today's date and its prompt asks it to drop passed dates; `quick_add.md` promises a date and a type that `edit_content` has no field for; 016 AC-15 says a note that contradicts the web is named in the reply and the prompt says no lookup happens; the country question lives on the answering path and `classify.md` routes only questions about what they put in there; a shopping list is one piece in `plan_v2.md` and three tasks in `quick_add.md`. ### 2026-09-10 · A unit test can hold the right id while every route holds the wrong one

An answer's rows never reached any client on the live path. The sentence arrived, the rows did not, and it read exactly like the model choosing to summarise instead of listing. It was reported that way twice.

**A client watches the message it sent.** The reply is a different row, and `message_content` records the rows against the reply, so both live paths asked "what rows does this question have" and got nothing, forever. The reply text survived because it is looked up by turn rather than by id. Reloading fixed it, because the conversation tail asks for every message in the page and the reply is one of them.

**The test passed the whole time.** It called `foundFor([reply.id])` directly, which is the one thing neither route did. That is the shape worth remembering: *a unit test that constructs the correct input cannot discover that production constructs a different one.* The new test goes through `streamStep` and asserts the id is not the message being watched.

Three of today's bugs were the same class, a field present on one side of a seam and absent on the other: `found` missing from mobile's parsed answer shape, `found` and `waiting` missing from web's `TailMessage`, and `seriesRef` silently stripped by a Fastify response schema that had not been told about it. **A response schema that drops an unknown field is a silent contract break**, and the only reason the third one was caught is that a test asserted the field arrived over HTTP rather than asserting the function that produced it.

### 2026-09-10 · Prompt changes are measured on cases they have never seen

`/test-llm` and `apps/agent/evals/`. A prompt change is not done when three examples look right: three examples is how you learn what the rule should say, and also how you write a rule that fits three examples and nothing else.

The loop is tuning set, change only where failures agree, then a fresh set never tuned against, and **the held-out number is the result**. A quarter of every set is behaviour that must not change, because a brevity rule that shortens a refusal into rudeness has failed and only a refusal case will say so.

Two things it taught immediately, both now steps in the skill. **Half the first run's failures were the rubric rather than the model**, and tuning against those would have made the product worse while the number went up. And a case has to be answerable before it measures anything: several asked about a field `AccountFacts` does not carry, and one that looked like a wrong answer for two rounds was the harness not knowing about `list_calendars`.

Brevity, the first thing put through it: tuning 69 to 92, first holdout 85 to 92, second holdout 100.

**Design system impact:** none. The visual decisions from today are logged separately in the design system's own `decisions.md`.

### 2026-09-10 · A URL parser rewrites a href before it reads it, so prefix matching cannot guard one

The reply renderer decided a link was internal with three string checks: starts with `/`, does not start with `//`, does not start with `/\`. `/<tab>/evil.example` passes all three and every browser navigates to `https://evil.example/`, because the WHATWG algorithm strips tab, carriage return and newline from anywhere in a URL **before** interpreting what is left. Carriage return and newline could not survive the line split; tab could.

**It was reachable.** A row somebody else wrote in a shared thread can contain a link, the answering prompt asks for quotes to be exact, and the reply draws the result as a real styled link inside offload's own bubble. Phishing in the product's own voice, from content the product invited somebody to write.

The gate now refuses anything a parser would rewrite: any C0 control character or DEL anywhere in the href, a leading or trailing space, and any `..` segment. **String work rather than `new URL`**, deliberately, because that is a polyfill of varying completeness on React Native and the guard would then depend on which runtime drew the reply.

The general rule, which is the part worth carrying: *a check that matches on the prefix of a URL is checking a string the parser has not produced yet.* Canonicalise first, or refuse anything that canonicalisation would change.

**The mobile renderer's comment claimed a guarantee it did not provide.** It said `Linking` was not imported so nothing could open an external URL. `expo-router` calls `Linking.openURL` itself for anything it classifies as external, so the safety came from the parser rather than from this file. The comment is corrected and the component now checks the shape itself, so the surface a person taps does not depend on a package in another directory staying right.

**And the scanner was quadratic.** A failed search for a closing marker rescanned the whole remainder from every opener, so a line of unmatched brackets cost 2.5 seconds for 48,000 characters on the thread that draws the screen, from text derived from a dump. An absent marker is remembered now: 1ms for the same input. The test asserts through the runner's timeout rather than a stopwatch, because a measured bound is a flake on a busy machine.

**Design system impact:** none.
